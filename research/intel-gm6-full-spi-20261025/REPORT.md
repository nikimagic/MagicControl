Дополнение того же дня: **точный FPTW64.exe побайтно найден в официальном
BIOS-пакете GIGABYTE G5KE FB05**. Источник, размер2481304, SHA и проверка
равенства: [отдельный протокол происхождения](../fpt-official-origin-20261025/REPORT.md).
Это уточняет прежнюю границу «только локальный BIOS Unlock» ниже; путь
первоначальной переупаковки в наш RAR не установлен. Повторная загрузка AMI
также дала прежнюю5.17.00.0153 без изменения EXE/SYS.

25.10.2026. Только файлы, подписи, исходники и статическая декомпиляция.
FPT/AFU, их драйверы, BIOS/EC helpers и аппаратные команды не запускались.
Продукт и рабочие portable не менялись; версия остаётся0.1.189.

## Результат

**Наш FPT16.1.25.1871 — обоснованный кандидат для полного чтения SPI GM6.**
Это установлено не по похожему названию процессора: в сохранённом inventory
GM6 LPC имеет8086:7A0C, и исполняемый FPT действительно включает этот ID в
свою таблицу платформ. В обоих32МиБ эталонах Descriptor даёт host read для
Descriptor/BIOS/ME/GbE/DevExp2. В коде есть отдельная ветка дампа всего flash.
Работа на текущем GM6 и допуск драйвера Windows пока не измерены.

Кандидат будущей команды, **не запускался**:

```
FPTW64.exe -d full-spi-pass1.bin
```

Без ограничения `-bios` это запрос всего доступного SPI. Имеющийся
`BIOS Unlock/1.backup.bat` уже содержит именно общую форму этого вызова.
Наличие BAT не доказывает, что присланный backup был получен именно им.

Источник идентичности: Users_logs/logs_GM6IR0C(15).zip,
dumps/dump-20261024-171634-0/inventory.json. Сохранены:

VA1401742C0. Запись21,file-offset173FD0:

|---|---|

## 3. Descriptor: разрешения и все16 регионов

Источники:

- Непатченый backup.fd32МиБ, SHA256
  2039277e2adfc54ec11983fd5822dcc070648b41217fe86b57a3f5779f2f7722.
- Патченый new.fd32МиБ, SHA256
  ac379a0bfbf9aa079e92d4e386b4f80eafbbe72f3f23b66a8d1f8c0ce53a5e12.

Descriptor обеих копий побайтно одинаков: SHA256
e6e3d8ca5bd0521a8d2d2eca4fbc8dfaae51045bd2cc9c6d1440118872ff1b06.
FRBA40h, FMBA80h, FCBA30h. **FLMSTR1(host)=FFFFFFFF** в обеих копиях:
по IFD2 read mask bits8..19 все нужные регионы доступны. Это состояние
сохранённого Descriptor; текущие live FRAP/PRR/locks не считывались.

|Регион|Начало–конец, hex|Размер|Host read в файле|
|---|---|---:|---|
|0 Descriptor|00000000–00000FFF|4096|Да|
|3 GbE|00001000–00002FFF|8192|Да|
|2 ME|00003000–003DCFFF|4038656|Да|
|9 Device Expansion2|003DD000–00FFFFFF|12726272|Да|
|1 BIOS|01000000–01FFFFFF|16777216|Да|

Остальные11 регионов выключены по base/limit. Регион9 присутствует — это
дополнение к прежней таблице, где рассматривались только Descriptor/BIOS/ME/GbE.
В старых двух файлах он целикомFF. FLCOMP=093030F6, один flash component,
density code6 соответствует32МиБ; это декларация сохранённого Descriptor,
не свежий JEDEC-опрос. В первом GbE bank checksum64слов=BABA, область непустая.
Текущие MAC/серийные данные в отчёт не выводились.

Разбор FMBA, bitfields и FLCOMP сопоставлен с первичным кодом
[coreboot ifdtool.c](https://raw.githubusercontent.com/coreboot/coreboot/main/util/ifdtool/ifdtool.c)
и [ifdtool.h](https://raw.githubusercontent.com/coreboot/coreboot/main/util/ifdtool/ifdtool.h).
Форма MN2 сверена с классами MN2_Manifest_R1/R2 в
[исходнике ME Analyzer](https://raw.githubusercontent.com/platomav/MEAnalyzer/master/MEA.py).
Эти источники не запускались на оборудовании и не заменяют живое измерение.

## 4. Цепочка чтения в нашем FPT

Статический Ghidra12.1.4 разбирал сохранённый PE как данные. Исследовательские
типы декомпилятора приблизительны; ключевые условия сверены с .asm/байтами.

1. Главная функция140008A40 разбирает аргументы и вызывает140007280.
2. Dispatcher140007280: операции22h–28h ведут к1400033B0. Ветки записи
   C–1Ah ведут к другой функции140004870.
3. DumpFlashToFile1400033B0 при length=0 берёт flash_size−start. Общий dump
   начинается на0; буфер предварительно заполняетсяFF, затем идут чтение и
   сохранение через14001F530. Объём не зафиксирован16МиБ BIOS-регионом.
4.14000F320 выполняет guard, проверки protected ranges/доступа и вызывает
   14000FAE0 с mode0 — чтение.14000ECA0 рассматривает RPE PRR84..94 и
   host read permissions FRAP50 при Descriptor-valid, отдельно от write path.
5.14000FAE0 mode0 читает блоками до64байт, выбирает адрес/длину, запускает
   SPI read cycle и забирает данные из FDATA. Режимы программирования/стирания
   в той же общей функции отдельные; одно имя Flash Programming Tool не
   превращает запрос-D в flash-запрос.

Важная точность: даже чтение SPI использует временные записи управляющих
регистров контроллера для запуска read cycle. Это не запись/стирание firmware
и не изменение EC ROM-ID; данная работа вообще их не исполняла. Отсутствие
всех возможных побочных действий каждой внутренней функции здесь не заявлено.

### Почему одного exit0/32МиБ мало

В1400033B0 есть отдельная ветка для региона9: при определённом отсутствии
read permission часть буфера остаётся исходнымFF, а остальные участки читаются.
Следовательно, размер результата сам по себе не доказывает чтение каждого
байта. В старом эталоне этот регион тожеFF, но это не измеряет новое состояние.
В будущем протокол должен сохранять вывод FPT, фактическую карту и сообщения
о пропущенных/недоступных диапазонах, отдельно от формы получившегося файла.

## 5. Драйвер и границы будущего запуска

Подтверждена цепочка:1400166C0 →14001B370 →14001B8B0.
14001B580 извлекает resource118(RCDATA) в WNPDriver.sys; обычный путь —
Windows/System32/Drivers, запасной — SystemTemp.14001B8B0 создаёт/запускает
службу WNPDriver;14001B370 открывает IntelCseWNP.14001BD20 останавливает,
удаляет службу и SYS при очистке. Это не выполненная в исследовании трасса.

FPT может остановить уже существующую одноимённую службу. Будущая интеграция
обязана проверять чужой WNPDriver до запуска, как AFU проверяет свой драйвер.
Запуск EXE является запросом загрузки kernel driver; его не следует маскировать
под обычное чтение локального файла. Настройки защиты менять не требуется по
плану: отказ драйвера должен остаться отказом с журналом.

## 6. Что проверять в будущем полном чтении

Это план, не выполненный аппаратный опыт:

1. Точная фактическая плата GM6, vendor/BIOS, SHA EXE/драйвера, права, питание,
   отсутствие конкурирующего WNPDriver; неизменённые настройки защиты.
2. Только фиксированный `-d` в уникальный новый файл, без flash/unlock/reset.
   Полные stdout/stderr, argv, PID, времена и код завершения.
3. Размер по реальному чтению flash, Descriptor signature, все16 base/limit,
   host-read и отсутствие сообщений о пропуске областей; непустые ME/GbE,
   формы ME partitions/manifests, GbE checksum и UEFI volume headers.
4. Второе независимое чтение. Сравнивать SHA и диапазоны различий: runtime
   NVAR/ME data могут измениться между проходами, это не автоматически
   повреждение и не основание объявлять файлы побайтно одинаковыми.
5. Сохранить оба исходных результата. Полным текущим SPI называть результат
   только при подтверждении области чтения, а не по длине/одинаковым хэшам.

Отдельные `-desc -d`, `-me -d`, `-gbe -d`, `-bios -d` являются селекторами
диагностического чтения, но не заменяют единого полного чтения. Эти команды
тоже не запускались. Нового backend/кнопок/билда в этой работе нет.
