# NVFlash5.867: область --save и проверка полного EEPROM

Дата:25.10.2026. Исследованы **точные Windows/Linux payload нашего0.1.195**.
Исполнялся trusted Ghidra над файлами; NVFlash, его help/list/read/check,
драйверы и аппаратные операции не запускались. Код коллектора не изменён.

## Вывод

Обычный `--save file.rom` сохраняет подготовленный/выбранный ROM-образ по его
вычисленной длине. Называть этот путь гарантированным чтением всей физической
SPI-микросхемы нельзя. Образ может включать больше одной PCI ROM-части и
служебные данные; сводить его всегда к одному VGA/EFI блоку тоже неверно.

В нашей5.867 существует отдельный **`--entire`**. Для обычного `.rom` пути он
пропускает обработку, выполняемую при обычном сохранении, и передаёт в запись
диапазон **`offset=0, length=capacity`**. Capacity берётся из EEPROM descriptor,
но **ограничивается16МиБ**. Это подтверждено отдельно в обеих ОС.

`--full` и `--entire` — разные флаги. `--full` меняет подготовку/выбор образа;
ветку сохранения по физической ёмкости включает `--entire`. Наличие подписи
`--full` или одинаковые хэши обычных VBIOS-файлов не заменяет проверки ёмкости.

Для известной выбранной EEPROM объёмом не более16МиБ успешное чтение всего
запрошенного диапазона с `--entire` — нужный путь к полному адресному дампу.
Факт полноты на конкретном ноутбуке требует ещё runtime evidence распознавания
чипа, диапазона/ошибок и файлов. В этом сеансе такой аппаратной evidence нет.
Одна основная EEPROM GPU не означает все микроконтроллеры/микросхемы платы.

## Документация NVIDIA

Найдено руководство с авторством NVIDIA/Mark Stephen Krueger от14.11.2006:
[публичная копия](https://pdfcoffee.com/nvflash-nvidia-firmware-update-utility-pdf-free.html).
На страницах7–10 описаны сохранение firmware image и compare, на18–19 —
идентификация EEPROM через check. Это старый документ на зеркале, не найденная
актуальная официальная публикация manual5.867. Его не использовали как
доказательство новых флагов и лимитов конкретной5.867.

Встроенная справка **самой5.867**, извлечённая статически, описывает save как
чтение EEPROM с сохранением в файл. Hint для compare различает raw binary
comparison и verify, моделирующий преобразования flashing process, включая
merging/certificate finalization. Извлечённые адреса/текст:
`option-capacity-hints.json`, `windows-embedded-help.txt`.
Подробное поведение `--entire` ниже установлено кодом, не старым руководством.

## Точная Windows цепочка

EXE SHA256:
`c0620a7be0ffdad3782d9ddf238d1a19c31b587cbcfee7036819c8a50e2d89cd`.

1. В dispatcher `140ce7f60` инструкции `140d0fb03..140d0fb40` получают
   option `entire` по строке `1411dd4f0` и сохраняют boolean в stack33e.
   `140d0fb47..140d0fb84` отдельно получают `full` (`1411de09c`, stack33f).
2. Вызов `140d0fd1e..140d0fdc3`: app vtable `1411d69f8+98` →
   `140cc6e80`; `entire` передан12-м аргументом, `full` —11-м.
3. `140cc6e80` передаёт их соответственно10-м/9-м аргументами controller
   Save. Его vtable `1411bbc98+2a0` и derived `1411bd9d8+2a0` содержат
   один адрес **`14022bd70`**.
4. `14022bd70` получает EEPROM interface и capacity через `1401ad830`,
   затем reader `vtable+208` → **`1401ce200`**. Тот вызывает EEPROM
   `+78`; просмотренные concrete EEPROM vtables ведут в **`140484df0`**.
5. `140484df0` ограничивает requested length ёмкостью, создаёт буфер,
   читает начальные4байта, выделяет полный буфер и вызывает raw reader
   **`offset0,lengthC`**. Например, backend `14049e340` проходит диапазон
   блоками до0x100; альтернативные backend-ветки включают memory/API и иной
   транспорт. Специфику конкретного ноутбука без его runtime выбора не угадываем.
6. В Save handler, при `entire=false`, вызывается дополнительная подготовка
   `+2e8` (`1402359c0` либо derived `14027ec60`). Затем файл сохраняется
   через image `+410` длиной image `+360` или специальной `+840`.
7. При **`entire=true`** этот postprocess не вызывается; инструкции
   **`14022c9ec..14022ca18`** берут capacity через `1401ad830` и вызывают
   image `+410` с нулевым offset и capacity в качестве длины.

Из Save handler также видно условие `!full && !entire`, при котором может
выбираться подобраз по внутреннему identifier0x85. Назначение этого ID здесь
не присвоено без отдельного доказательства. Поэтому ни VBIOS-only для всех
layout, ни full-physical для обычного --save не утверждаются.

Артефакты: `phase1/14022bd70.c/.asm`, `phase3/1401ce200.c`,
`phase1/140484df0.c`, `phase6/14049e340.c`, `phase4/140cc6e80.c/.asm`,
`phase5/140dc7e30.c`, `phase6/140ce7f60.asm`. Виртуальные переходы проверены
по самим64-битным указателям PE, а не только по guessed types декомпилятора.

## Независимая Linux цепочка

ELF SHA256:
`754693fb8f833be75601f95cb08a6e0cf538053cce84ab69020ec74ae96a6e70`.

1. Main dispatcher `0089a996` в `008b6c98..008b6cbc` проверяет `entire`
   (`00cfcb6b`) и сохраняет boolean в R12. `full` проверяется отдельно
   по `00c3ed89`; boolean сохраняется в EBX.
2. `008b6e0a..008b6e62` передают R12 как12-й аргумент app helper.
   App vtable **`00d01c80+a0` → `007ef876`**; assignment vtable
   подтверждён constructor `007db86d`.
3. Helper `007ef876` передаёт `entire`10-м аргументом controller Save.
   Body vtable **`00caf2d0+2a0` → `005bc5eb`**. Этот thunk содержит
   только `SUB RDI,10; JMP 005bb6c2`, сохраняя прочие аргументы.
4. Save handler **`005bb6c2`** имеет такое же различие: обычный путь
   вызывает postprocess, выбирает image length через `+368`/`+848`;
   `entire` выбирает **`0056f094`** capacity и сохраняет `offset0,lengthC`
   через `+418`.

Артефакты: `linux-phase2/0089a996.asm`, `linux-phase5/007ef876.c`,
`linux-phase5/005bc5eb.asm`, `linux-phase1/005bb6c2.c/.asm`,
`linux-phase1/0056f094.c/.asm`, `linux-phase6/007db86d.c`.

## Лимит16МиБ

Windows **`1401ad830`**, Linux **`0056f094`** вычисляют:

```text
S = descriptor.u32[0x78] * descriptor.u16[0x7C] * 128
C = min(S, 0x1000000)
```

Это реальные offsets/арифметика; названия единиц отдельных полей не придуманы.
При превышении лимита печатается marker **`Limited the part size `**, затем
` to the max of buffer size `. Таким образом, файл16МиБ может быть ограниченным
буфером чтением более крупного чипа. Для label полного физического EEPROM
нужно знать исходное S/ёмкость конкретной распознанной детали, а не только C.
Неизвестный/override EEPROM не даёт доказательства физической ёмкости.

## Как проверять полноту при будущем разрешённом запуске

Это план, **команды здесь не исполнялись**. N берётся из проверенной PCI binding.

```text
nvflash64.exe --index=N --check
nvflash64.exe --index=N --entire --save spi-pass1.rom
nvflash64.exe --index=N --entire --save spi-pass2.rom
nvflash64.exe --index=N --compare spi-pass1.rom
```

Для Linux используются те же операции у проверенного x64 ELF.

Критерии полного адресного дампа выбранной EEPROM:

- Exact PCI identity до/между/после чтений; распознанный EEPROM ID/модель.
- Её подтверждённая ёмкость S из descriptor/JEDEC/model data согласована с
  datasheet детали. Файл не должен оцениваться только по PCIR image length.
- S не превышает16МиБ; нет marker ограничения размера, fallback на unknown
  EEPROM, `romin`/внешнего ROM-источника или ошибок/пропуска чтения backend.
- Оба entire-файла имеют размер ровноS и одинаковые SHA256.
- Дополнительная raw compare сверка должна завершиться успешно; её success
  не заменяет проверку физической ёмкости и длины охваченного диапазона.
  `--verify` с преобразованиями flashing image не используется вместо raw compare.
- PCI/вендорная структура проверяется как отдельный признак корректного
  содержимого. Заполненность/одинаковые хэши сами по себе не доказывают S.

Если S>16МиБ, один entire-файл этой ветки5.867 не получает full-physical label.
Способ чтения остальных адресов или другой backend требует отдельного разбора;
сейчас никакие override/offset/reset/protection/flash команды не предложены.

## Состояние MagicControl

Текущий0.1.195 отправляет только обычный `--save`, два раза. `--entire`,
`--check` и `--compare` **в collector пока не подключены**. Его label
`nvflash_saved_vbios` / `physical_spi_complete=null` сохраняет правильную
границу доказательства. Это исследование не меняло UI, reader argv, runtime
payload, рабочие portable, EC или ROM-ID; аппаратного дампа в сеансе нет.

Ghidra initial analysis был ограничен по времени; большие dispatcher C
не полностью декомпилированы. Критичные места проверены по assembly, raw
literal addresses, constructor assignments и vtable bytes. Это точные выводы
для двух указанных SHA5.867, не универсальное обещание для всех выпусков NVFlash.
