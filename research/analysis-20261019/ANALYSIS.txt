Сборщик не посылал write IOCTL. Это RAM-снимок, не образ прошивки flash.
Valid-маска подтверждает ответ транспорта; OEM SYS способен скрыть отдельные

Это не признак зависшего драйвера или конфликта с нашей программой:
не было ни busy wait, ни повторов, ни длинных readBlock.
Точную длительность каждого wait текущий лог отдельно не измеряет.

0x402/403    6400                OEM BIF_DC, проектная ёмкость.
0x404/405    5300                Кандидат полной ёмкости рядом с BIF_DC.

6400мА·ч ×15,48В =99,072Вт·ч.
5300мА·ч ×15,48В =82,044Вт·ч.
5300/6400×100 =82,8125%.
Это согласуется с Windows99,07/82,04Вт·ч и точным health82,8125%.
Совпадение напряжения, заряда и независимых пересчётов ёмкости подтверждает
привязку батарейного блока значительно сильнее, чем одно правдоподобное число.

Стандарт Smart Battery Data1.1 задаёт Temperature в0,1К и CycleCount как WORD.
Если ecBt1Temperature хранит эту стандартную величину,3030/10−273,15=29,85°C.
Но стандарт SBS сам по себе НЕ доказывает формат OEM RAM. Пока это сильный
кандидат: нет второго снимка с изменением температуры и независимого getter.
Аналогично68циклов — именованный OEM-кандидат, Windows его не подтверждает.
Следовательно, Win32=1 означает отсутствие Windows getter, а не отсутствие
батарейных данных в EC. Read-only OEM fallback теперь обоснован для разработки,
но его ещё нельзя выдавать за проверенный динамический датчик.

3. ВЕНТИЛЯТОРЫ: RAMFAN1.5 ВЫГЛЯДИТ СОГЛАСОВАННО, RAMFAN2 — НЕТ

ProjectID=26, BIOS-ID raw=0xC6. Это другая плата, не GM6 ProjectID25.
0x78E=0xFC: RamFan1.5 capability bit6 установлен.
0x7C8=0x60: LC fan-table capability bit5 тоже установлен.
Наличие обоих битов не выбирает активный менеджер вентилятора.

Константы именно Eluktronics OEM:
CPU up/down/duty:0xF00/0xF10/0xF20.
GPU up/down/duty:0xF30/0xF40/0xF50.
Содержимое этих шести окон согласовано: пороги растут, есть255-маркеры,
все duty чётные и лежат0–180. При OEM scale2 максимум записанной кривой90%.

Raw CPU up: 54 59 63 67 67 70 73 76 81 83 255 255 255 255 255 255
Raw CPU duty:0 60 60 70 90 90 100 110 140 160 180 180 180 180 180 180
Raw GPU up: 54 54 58 62 62 64 67 70 73 76 255 255 255 255 255 255
Raw GPU duty:0 0 60 70 90 90 100 110 140 160 180 180 180 180 180 180

Наоборот, RamFan2 трактовал бы0xF50 как температурные пороги второго физического
вентилятора: среди них получились140/160/180°C, а следующие температурные
окна содержат метаданные/нули и не образуют согласованную кривую.
Это структурный аргумент за формат1.5 данного банка, не разрешение на запись
и не доказательство выбранного OEM менеджера. Защищённый MyFanCtrl constructor
в GCUService ещё не восстановлен; читать его Runtime exception как рабочий код нельзя.

Для графических точек OEM1.5 есть смещение индексов: raw Up[i] соответствует
следующему переходу, Down[0] резервный. Нельзя просто склеить одинаковые индексы
Up/Down/Duty и получить готовый безопасный fan-curves.csv.
Экспортированы отдельно сырые байты и условная интерпретация, без применения.

Кандидаты текущих показаний, по OEM парам старшего/младшего байтов:
CPU=(0x464<<8)|0x465 =0x0A94=2708RPM.
GPU=(0x46C<<8)|0x46B =0x0A55=2645RPM.
0x75B/0x75C=99/99; при scale2 это49,5/49,5%.
Это согласованные чтения, но пока один неатомарный снимок. Нужно проверить
динамику с повторным high/low/high чтением, прежде чем называть их live-getters.

0x726=0,0x727=0x80,0x7C6=0,0x751=0. В трактовке GM6 custom/override/commit
биты не активны. Перенос этой трактовки на HYDROC остаётся гипотезой.
Default перед дампом не задавался. Содержимое RAM нельзя объявить заводской
таблицей flash или активной кривой: RAM может сохранять неактивный набор.
Файл settings/fan-curves.csv совпадает с разрешённым packaging-файлом владельца;
сырая RAM HYDROC имеет другие значения. Сборщик его в EC не записывал.

4. ПОДСВЕТКА HYDROC: ЕСТЬ ОСНОВАНИЕ ИСКАТЬ ITE/HID

0x766=0x93: bit2 НЕ установлен. Родной LM_EC_RGB допускает SingleZone EC
именно при0x766.bit2=1. Прямой EC SingleZone writer Wujie/GM6 сюда не подходит.
0x73C=0x18 — subtype, но это не готовый RGBKB_Type enum.
Родной LM_Manager сначала пробует ITE HID, затем EC fallback.
В LM_ITE_RGB для UsagePage0xFF03:
- firmware major32 + subtype24 даёт MEZone_3nd_98;
- firmware major34 + subtype24 даёт MEZone_3p1nd_101.
Без HID VID/PID/UsagePage и ответа firmware-version выбирать вариант нельзя.
Семейство ITE имеет VID0x048D и отдельные PID клавиатуры/световой полосы.
Дальнейшая диагностика должна перечислять реальные HID-интерфейсы и getter
версии, а не переносить регистры яркости/цвета старой SingleZone платы.

5. PCH, INTEL GPU И NVIDIA: РАЗДЕЛИТЬ ОШИБКИ И ОГРАНИЧЕНИЯ API

PCH: зависимость присутствует и прошла этап чтения файла/проверки ожидаемого
хэша; PawnIO open тоже прошёл. Ошибка возникает именно в pawnio_load.
Это не общее отсутствие PawnIO: через него уже работают IntelMSR и I801.
Внутри модуля load запускает main: поиск разрешённого PCI-контроллера и MMIO map.
Возможны отказ валидации/инициализации, отсутствие разрешённого PCI ID,
ошибка MMIO. Точный HRESULT loader сейчас теряет; выбрать причину нельзя.
Нужны HRESULT pawnio_load, версия SYS и перечень LPC/thermal PCI устройств.
Менять белый список PCI или адрес MMIO наугад по одному CPU нельзя.
ACPI ECTZ/TZ00=69,05°C не подписываются как PCH: смысл зон не установлен.

Intel IGCL: legacy GetTelemetry Size1024 Version1 успешен, INVALID_ARGUMENT нет.
GetV2 export отсутствует в ControlLib1.0.213.0 — это нормальный fallback.
Отсутствие мощности в intel.json объясняется первым замером нового reader:
для производной энергии требуется второй. В timeline вычисления появляются.
Отсутствующие Intel temperature/VRAM/fan поля имеют supported=false.
Расчётная IGCL мощность23,382/15,651/18,870Вт близка к CPU RAPL
23,243/15,990/18,469Вт в трёх последовательных срезах. Чисел мало, но это повод
отдельно проверить физический домен счётчика gpuEnergyCounter; не считать
доказанным, что весь этот расход относится только к встроенному графическому ядру.

NVIDIA HYDROC: NVML45–46°C,12,889–17,635Вт; GetPowerUsage/field185/field186
согласованно дают правдоподобный порядок величины. PnP D0 до/после запроса.
Windows primary=NVIDIA, Intel secondary; primary не является режимом MUX.
NVAPI channel1≈45,25–45,625°C,channel2=52°C. Для RTX50 смысл channel2 не доказан:
его нельзя автоматически назвать Memory Junction или Hot Spot по карте RTX40.
GetThermalSensors discovery=-1 не является итоговым отказом: fallback v2=0.
PowerManagementLimit=Not Supported — ограничение API, не сбой температуры.

8. ПРИОРИТЕТЫ ДАЛЬНЕЙШЕЙ РАБОТЫ

1) Read-only HYDROC battery/RPM: именованные кандидаты с exact identity,
   raw/status и проверкой серии чтений; не заменять факты Windows молча.
2) PCH: сохранить точный HRESULT загрузки и PCI identity прежде изменений модуля.
3) Дополнить дамп HID inventory/firmware getter для ITE клавиатуры HYDROC.
4) Для управления FANs установить активный OEM менеджер/статусы RAM,
   owner и подтверждение Default; поддержка1.5 не равна разрешению setters.
5) Пассивную часть дампа сделать достаточной для динамики: текущий HYDROC
   пакет длится7секунд и даёт4fast+1slowсрез. Этого мало для состояний сна GPU,
   температурной динамики батареи и проверки максимальных оборотов.
6) В power logger сохранять исходные GPU power каналы и убрать немеряемые
   утверждения controls-stable=yes. Проверку GUI0.1.71 провести по новой версии.
