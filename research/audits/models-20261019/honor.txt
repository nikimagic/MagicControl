3. КОНКРЕТНЫЕ ЗАМЕЧАНИЯ

H1 [P2] Watchdog ошибочно сообщает «автоматика восстановлена» при отказе от владения.
  SRC/FanControlWindows.cpp:36–40 возвращает void после owned=false,
  releasePending=false при несовпадении manual/targets. В catch watch():67–70
  после automatic() безусловно добавляется текст «автоматика восстановлена».
  Если внешний writer сменил targets между первым ownership snapshot и ошибкой
  GTMP/WMI, automatic() правильно не пишет чужое состояние, но статус говорит
  об успешном Auto. При releasePending после partial failed rollback совпадение
  обоих attempted targets тоже не гарантировано; автоматический return не
  доказывает Auto и не должен превращаться в success.
  Основание: EC_ASM:46239–46277 — manual bit реально удерживает фиксированный
  режим; чужие targets с bit1=1 остаются Manual. Фактического сценария не запускали.
  Предложение: typed cleanup result {restored,already_auto,ownership_lost,failed},
  раздельный readback/status. Не предлагать восстанавливать чужие targets.

H2 [P2] Linux battery rollback скрывает собственную ошибку и не проверяет результат.
  src/platform/linux/huawei-wmi/HuaweiControlLinux.cpp:70–71:
  после частичной sysfs write/readback failure catch пытается writeThresholds,
  проглатывает её исключение и заново выбрасывает исходную ошибку. Нет проверки
  restored==before, записи журнала или явного «откат не подтверждён».
  Пара writeThresholds() может менять два файла:39–43. Если end write не прошла
  после успешной start write, батарея может остаться с частично изменённой парой,
  а UI сообщает лишь исходную ошибку. Это доказанный пробел error path, не
  наблюдавшаяся аппаратная потеря данных. Windows уже сообщает обе ошибки.
  Предложение: общий bounded verify/rollback результата пары с сохранением
  обоих failure statuses, без слепого повторения и без смены внешнего дизайна.
  Источник аппаратной семантики: FACTORY_DSDT:713–745, OEM180002c20.c:57–61.

H3 [P2] Стабильное штатное disable0/0 блокирует выход из него через battery API.
  SRC/ControlWindows.cpp:19 отвергает end<1; read():48 оставляет chargeWritable=false.
  setChargeThresholds():85 всегда сначала вызывает этот getter, поэтому явная
 95/100 из корректного0/0 отклоняется до setter. Linux thresholds():36 и
  setChargeThresholds():69 имеют ту же границу.
  FACTORY_DSDT:721–724 штатно пишет0/0 по команде отключения защиты, а GBTT:743–744
  возвращает именно эти raw поля. Следовательно0/0 бывает допустимым состоянием
  firmware, хотя в процессе commit оно также может быть транзиентным.
  Предложение: сохранить raw pair+typed disabled/transient/thresholds state,
  отличать стабильное0/0 повторным чтением и разрешать явный95/100 с точным
  rollback-смыслом. Не отображать0/0 как100% и не возвращать его через нормализацию
 0/100→95/100. Не включать SmartCharge самовольно.

H4 [P2] Honor FANs обходит общий DeviceOperation gate при применении.
  src/gui/windows/FansPage.cpp:819–830 не вызывает tryBegin; huawei-ветки
  selectEcManual():835 иselectPreset():858 возвращаются до общих busy checks
 836/859. Проверяется только локальныйbusy/старыйhlylState.writable.
  В отличие от SETs start():919–920 иGM6apply():798 нет held reservation на worker.
  Другой запрос SETs/BIOS может стартовать, пока уже запущено явное Honor fixed,
  и операция не публикует общий busy. ISA mutex защищает одну I2EC транзакцию,
  поэтому это не доказанный byte-level race, но не сериализует полную цепочку
  temperature HWMI→I2EC→result и последовательность dumpDefault→snapshot.
  Диагностический Default создаёт отдельный HlylFanController (DiagnosticDumpWindows:47),
  поэтому его Impl mutex тоже не совпадает с GUI экземпляром.
  Предложение: использовать тот же DeviceOperation reservation при dispatch,
  удерживать до результата; watchdog/cleanup не блокировать бесконечно и не
  отменять safety release из-за обычной UI операции. Не добавлять отдельный UI.

H5 [P2] Ошибки части HWMI getters исчезают из дампа/статуса.

  Следствие: отсутствие RPM/порога трудно отличить от unsupported/timeout/неверного
  ABI и проследить по logs; null не выдуман в0, но диагностическое доказательство
  потеряно. OEM WmiUtil180002a90.c:64–67 и180002760.c:67–74 имеют отдельно

H7 [P3] Resume HIGH проверяет чужие младшие bits03FC как часть brightness guard.
  SRC/BacklightWindows.cpp:79 допускает resume mismatch level0/duty0 только
  при value.shadow==0x80, хотя обычная ветка и ownedStateEqual():46 используют

  эксперимент не является OEM-обоснованием расширения runtime writes.

4. ПРИМЕНИМОСТЬ УЖЕ ОБЩИХ ЗАМЕЧАНИЙ

S1 Unknown U2 [P2] cancellation/deadline fastprovider относится и к Honor:
  SensorRecorder общий; HWMI имеет bounded GetCallStatus, но PawnIO/ADL/Storage

S3 Unknown U6/GM6-03 [P3] SSD source misattribution применимо к WDC Honor:

 35.85/36.85SMART отдельныеrows; это подтверждает разные способы декодирования,
  не обязательно ложность температуры и не два диска.
S4 Unknown U1 Radeon partial-provider coverage [P2] формально касается eGPU/
  нескольких AMD adapters; у exactHonor известна одна iGPU. Старые ADL adapter
 0..3 могут быть разными display/output handles однойiGPU, не четырьмя GPU.

5. ГИПОТЕЗЫ И СЛЕДУЮЩИЕ ПРОВЕРКИ (НЕ ВЫПОЛНЯЛИСЬ)

- Статически исправлять H1/H2/H4/H5 можно без изменения внешнего вида.
  H3 требует typed disabled pair, сохранения raw rollback-смысла и разграничения
  transient0/0; не менять firmware политику по догадке.
- Для H6 перед аппаратной пробой нужен общий адаптер, а не одноразовый scripts
  sweep. Максимум100% с measured RPM и30с observation, Auto/readback/ошибка
  cleanup отдельно. Не переносить SFND1102/EC0A18 других Honor или RPM scaling.
- Для H7 получить только свежий read-only snapshot после реального сна;
  ничего не писать ради доказательства lowerbits гипотезы.
- Сопоставить watch ownership loss/partial rollback с журналом, но не ломать
  транспорт/датчик физически ради теста. Проверять состояния модели отдельно.
- Таймаут ненулевой и выключение по бездействию — отдельная проверка; getter0
  и успехSKBT не доказывают, что клавиатура реально погасла черезNсекунд.
- Доведение АКБ до100% и действие resume/sleep SmartCharge требуют долгого
  наблюдения в согласованном сеансе; сборка/readback не заменяют это.

ИТОГ
Exact Honor поддержан собственными HWMI/I2EC/SMU адаптерами и общей UI-механикой;
наиболее конкретные пробелы — falsecleanupstatus, Linux battery rollback,
валидное0/0, пропущенный DeviceOperation gate, потерянные HWMI ошибки и отсутствие
30секMax в дампе. P1 аппаратный отказ в ходе статической ревизии не доказан.
Исходники/настройки/portable не изменялись. Рабочая версия осталась0.1.75.
