ГРАНИЦЫ РЕВИЗИИ
Прочитаны действующие исходники приложения, exact active OEM decompilation,
сохранённые отчёты пользовательских журналов и состав portable. Аппаратные
команды, GUI, OEM EXE/DLL, драйверы и тесты не запускались. Исходники,
конфигурация, аппаратные настройки и portable не изменялись.
Единственный результат этой работы — настоящий отчёт.
Внешний эталон ВСЕХ карточек и вкладок — Wujie. Аппаратный адаптер модели
не даёт основания создавать собственную страницу или менять геометрию/скролл.

2. МАТРИЦА ПЯТИ ОБЛАСТЕЙ

2.1 Драйверы / ABI / identity / сериализация
Реализовано:
- Windows: прямой \\.\ACPIDriver, IOCTL read 0x9C40A488/write 0x9C40A48C,
  вход EcPacket 8 байт, выход16; проверяется длина ответа. OEM AcpiCtrl:
  all-active/020000EA-MyECIO.AcpiCtrl.cs:64–66,185–225,350–391.
- src/platform/windows/uniwill-acpi/BackendWindows.cpp:23–41,104–125,156–196:
  один Global\\MagicControl.EcTransactions.v2 между процессами/сессиями;
  EcAccess::Transaction и короткие операции дополнительно используют этот gate.
- src/devices/mechrevo/gm6ir0c/ControlWindows.cpp:171–188:
  exact profile, Project25/RAM1.5, feature/protocol guard; активные GCUService.exe
  или AiStoneService.exe запрещают запись. OEM процессы не останавливаются.
- Батарея пользуется тем же backend transaction mutex, но отдельным typed API.
- PawnIO — отдельный источник Intel MSR/I801/PCH. ACPIDriver не считается
  заменой PawnIO и не даёт доступ к AMD SMU на этой Intel-плате.
Подтверждено прежними журналами: EC чтения; часть command readback и Max cleanup.
Неизвестно: точный хэш текущего установленного SYS; реакция на новую его ревизию.
Linux: src/platform/linux/BackendLinux.cpp:6–21 явно не предоставляет GM6 EC.
Это намеренная граница возможностей, а не незаметно работающий setter.

2.2 Датчики CPU/GPU/RAM/SSD/батареи
Реализовано:
- Intel CPU family6 B7/BA/BF: DTS valid31/TjMax и RAPL 0x611 с rollover32,
  единицами0x606 и интервалом; allowlist в SensorModuleWindows.h. Ни MSR-write,
  ни перенос AMD power override не используются. Код:
  src/platform/windows/pawnio/IntelTelemetryWindows.cpp:20–79.
- NVIDIA NVML: точные UUID/PCI, источник мощности, raw выбросов, повторный
  запрос, поля185/186, отдельные ошибки API и PnP before/after. NVAPI-дополнение
  подбирается по PCI; RTX40 дополнительные каналы не переносятся на RTX50.
  src/platform/common/NvidiaGpu.cpp:159–265;
  src/platform/windows/NvidiaSensorsWindows.cpp:86–145.
- DDR5: Intel I801 + SPD5118, SHA модуля, Global Access_SMBUS mutex;
  SMBus0x50–0x57, только read-транзакции; в обычном UI два хаба,
  в диагностике до8. Serial SMBIOS не объявляется доказанным serial хаба.
  src/platform/windows/pawnio/IntelMemoryWindows.cpp:9–69.
- SSD: Storage property и NVMe SMART composite + отдельные sensor1..8;
  все найденные диагностические датчики идут отдельно. Температура59°C
  дополнительного сенсора не заменяет composite около28°C и не означает
  автоматически другой диск или контроллер. Конкретные физические позиции
  vendor-defined сенсоров без документации Kingston неизвестны.
- Battery Class: raw BatteryTemperature, Win32 ошибка, декодирование десятых K;
  CPU/PCH/ACPI зоны не подставляются как температура батареи. Health — full/design,
  нулевой CycleCount не выдается за подтверждённые0 циклов.
- PCH и ACPI thermal источники отдельные, не батарея и не RAM.
Подтверждено архивом logs_GM6IR0C.zip 0.1.69 (отчёт log-review-20261019.txt):
  CPU46–83°C, RAPL13.147–76.264Вт; GPU37–48°C;
  DDR5 hub50:28–47.25°C, hub52:30.25–50.25°C; SSD23.85–31.85°C.
  BatteryTemperature: Win32=1 во всех252 образцах, температура недоступна.
Это подтверждение старого сеанса, НЕ физический тест новой0.1.75.
Неизвестно: конкретное состояние runtime D3 при каждом выбросе590006мВт;
  PnP MostRecentPowerState сам по себе не доказывает runtime D3cold или MUX.
Intel GPU IGCL уже имеет V2 и legacy compatibility shapes, включая
INVALID_ARGUMENT/INVALID_SIZE; прежняя ошибка не равна отсутствию реализации.
Код src/platform/windows/IntelGpuWindows.cpp:124–149. Успех новых форм на этом
экземпляре не доказан текущим статическим просмотром.
Linux использует native sysfs/hwmon/NVML; наличие общего UI не доказывает
равенство доступных датчиков Windows и Linux на конкретной машине.

2.3 FANs / Manual online / link / restore
Реализовано и сверено с exact OEM:
- RPM CPU464:465, GPU46C:46B (не X5 GPU46D); PWM75B/75C делится на2.
  OEM all-active/02000285-MyControlCenter.FanInfo.cs:8–42;
  наш ControlWindows.cpp:187–199,211–219 использует high-low-high и несколько проб.
- RAM1.5 CPU F00/F10/F20, GPU F30/F40/F50; Up[i]=next transition,
  Down0 сохраняется, Duty*2; commit7C6.2 после заполнения, respective7C5.7.
  OEM FanTable_Manager1p5.decompiled.cs:625–714,1176–1188;
  MyFanTableCtrl.decompiled.cs:139–159; наш ControlWindows.cpp:59–74.
- Default снимает RAM/custom/light/Boost без обнуления таблиц и без подмены CSV.
  Max меняет только751.6; Manual включает native RAM. SETs OEM режимы используют
  точные Office/Gaming/Turbo references и возвращают PL overrides к0.
  OEM MyFanManager_RamFan1p5.decompiled.cs:2537–2623;
  наш ControlWindows.cpp:281–318.
- Online: один контроллер, независимые saved Manual CPU/GPU, linked CPU-кривая
  по max(CPU,GPU),1с, гистерезис3°C,85°C=>100% обоим. Свежие DTS/NVIDIA
  обязательны. Датчик потерян — попытка вернуть захваченные поля.
- Снимок владения включает точные маски/таблицы; перед каждым шагом и возвратом
  expected проверяется. Чужое изменение не перетирается старым дампом.
  При исходно неактивной RAM возврат не очищает таблицы нулями.
- Native режимы не сбрасываются при выходе. Только online возвращает своё
  предыдущее управление. Max probe приостанавливает online и делает cleanup.
- Общий fan-curves.csv целиком используется для всех моделей; editor не
  перезаписывается аппаратной RAM. UI общих FansPage/контролов сохранён.
Подтверждено: exact протокол и часть пользовательского readback/cleanup.
Не подтверждено новой физической пробой: every online/link/failsafe переход,
  автономное исполнение таблиц в каждой версии EC и максимальные RPM.
Примечание: онлайн-защита работает в процессе приложения; она не является
  автономной аппаратной защитой при зависании процесса/завершении питания.

2.4 Батарея — native policy, readback, rollback, save, restore
Реализовано корректно по exact активному OEM:
- BatteryProtection2:0 Performance,1 Balanced,2 Healthy. Read-modify-write
  только7A6.bits4–5 (00/10/20); это не доказанные100/95/85%.
  OEM battery-active/GCUService.MySystem.BatteryProtection2.cs:267–314.
- Общий NativeBatteryController с отдельной exact identity GM6 и отдельным
  gm6ir0c-device-settings.ini. Соседние биты, FANs, PL,7B9/7D0 не меняет.
- Unknown комбинация3 запрещает запись; сохраняется только явный выбор.
  save/readback failure пытается откатить собственные биты, если значение ещё
  наше; при появлении OEM rollback не навязывается, ошибка журналируется.
  src/platform/windows/NativeBatteryWindows.cpp:64–112.
- Worker восстанавливает только имеющийся BatteryProtection ключ после старта
  и подтверждённого сна; без ключа нет startup-write. Ошибка restore журналируется
  однократно, режим не переприменяется каждым опросом.
  NativeBatteryWindows.cpp:37–56,129–130; MainWindow.cpp:443,869.
- Три кнопки используют общую карточку с заголовком/геометрией Wujie;
  меняется смысл/данные native policy, не создаётся своя вкладка.
Подтверждено: маски/вызовы OEM и сохранённый OEM HealthProtectionStatus.
Неизвестно: фактические верхний/нижний пороги каждого режима, алгоритм firmware,
  остановка зарядного тока и поведение на конкретном AC/USB-C источнике.
Нет основания обещать численные проценты или считать отсутствие температуры
батареи отсутствием физического датчика в её BMS.

3. РЕАЛЬНЫЕ ДЕФЕКТЫ / ФУНКЦИОНАЛЬНЫЕ ПРОБЕЛЫ

[P2 GM6-01] Стабильность RPM ошибочно названа подтверждённой физической реакцией.
src/platform/common/FanMaximum.cpp:11–34: beforeRpm записывается, settled
проверяет последние4 положительных RPM на30й секунде с разбросом<=3%/100RPM.
Рост/изменение от baseline и достижение максимума эта проверка не устанавливает.
src/devices/mechrevo/gm6ir0c/ControlWindows.cpp:277–278,230: settled+restored
делает fanResponseConfirmed=true, далее интерфейс говорит «реакция ... подтверждена».
Плато2500RPM при игнорируемом Boost пройдёт ту же проверку, что Max6000RPM.
OEM MyFanManager_RamFan1p5.decompiled.cs:2616–2622 — лишь команда751.6;
all-active/02000285-MyControlCenter.FanInfo.cs:21–42 — отдельная тахометрия.
Последствие: ложная уверенность в аппаратном исполнении/полноте калибровки.
Предложение: разнести commandReadback,stablePlateau,observedResponse,maxKnown.
Не требовать роста всегда: baseline уже мог быть Max. Если реакции не отличить
от исходного состояния, отмечать неизвестно/уже Max, а не physical confirmed.
Это дефект диагностики уверенности; небезопасность самого masked Boost setter
данной находкой НЕ доказана.

[P2 GM6-02] Потеря сохранённого Intel Manual черновика может скрываться успехом.
src/gui/windows/SettingsPage.cpp:457: после setPower открывается с trunc
gm6ir0c-power.txt, запись в ofstream не проверяется, финализация тоже;
исключения stream не включены. При запрете записи/полном диске/обрыве
старый файл может остаться пустым/частичным, UI сообщает успешную операцию.
Чтение на следующем запуске SettingsPage.cpp:294 не восстанавливает эти числа.
OEM MyFanManager_RamFan1p5.decompiled.cs:2655–2668 подтверждает только запись
PL1/PL2/PL4 в EC; долговечность нашего локального txt — отдельная обязанность,
такого txt/ABI в OEM нет. Ошибка относится к приложению, не к доказанному PL.
Предложение: общий атомарный проверяемый writer (образец PortableSettings.cpp:40–57),
явная ошибка «применено, но не сохранено»; не сообщать firmware failure,
если фактический set/readback был успешен. Не менять внешний вид карточки.

[P3 GM6-03, shared monitoring] Источник основного SSD показания неверно меняется
на NVMe SMART в диагностике, даже когда значение взято из Storage property.
src/platform/windows/MonitoringWindows.cpp:425 запоминает property temperature.
При diagnostic=true SMART дополнительно запрашивается;450 не заменяет имеющееся
число, но451 безусловно меняет item.source на NVMe SMART при любом item.celsius.
Достаточно разных успешных property/composite значений, чтобы число и источник
в базовом поле разошлись. Даже invalid composite не мешает такой подмене source.
OEM-сопоставление не применимо: это стандартный Windows/NVMe путь, не EC OEM.
Последствие: затрудняется разбор именно спорных28/59°C и точного происхождения.
Предложение: менять source только при присвоении соответствующего значения;
отдельно сохранять property и SMART readings с именем/индексом/единицами.
Данный статический дефект НЕ означает, что число59°C ошибочно.

[P2 GAP GM6-04] В dump нет свежего штатного запроса внутренних factory FAN tables.
Это функциональный пробел относительно запроса владельца, не ложная маркировка
текущего JSON: существующий ram_note корректно предупреждает об ограничении.
src/platform/windows/DiagnosticDumpWindows.cpp:26–64,83–100:
Default снимает commit; снимок показывает текущую RAM, рядом добавляются
компилированные OEM references из старого архива. Это не текущие factory tables.
Точный активный OEM уже содержит реальный механизм, не заглушку:
FanTable_Manager1p5.decompiled.cs:861–880 снимает APExist, запрашивает Gaming2,
Office3,Turbo1 и возвращает APExist;
883–916: F5F=mode,F5D=FD,F5E=C9, до10 опросов с500мс,
готовность когда оба маркера изменились, затем GetEcFanTable.
Предложение: отдельная явная диагностическая операция строго GM6 под gate,
OEM ownership guard, сохранением/возвратом APExist и контролем readiness,
с полным журналом/сырыми ответами. Не запускать этот пишущий handshake из paint,
обычного polling, preview или под видом полностью read-only snapshot.
Отказ/timeout должен оставлять factoryTable=null и exact статус.
Образ EC flash и выдаваемая firmware RAM-таблица — разные артефакты.

4. ГИПОТЕЗЫ И НЕОБХОДИМЫЕ ДАЛЬНЕЙШИЕ ПРОВЕРКИ

- Фильтр NVIDIA использует maximum/enforced/default envelope. Если все три
  недоступны, исходный590006мВт не отбрасывается только по этому правилу
  (NvidiaGpu.cpp:181–191,204–211). Это явно видимая граница, но такой набор
  ответов в нынешнем сеансе GM6 не установлен; отдельно проверить degraded API.
- Разделить GPU Runtime D3, recent PnP D-state, MUX/OEM policy78B и фактический
  display routing. Не устанавливать режим GPU на основании одного PnP поля.
- Прогнать на владельце только после отдельного поручения online/link,85°C
  защиту, потерю температуры, пробуждение, OEM-конфликт и точный restore.
  Статическая OEM-карта не доказывает физическое исполнение каждой команды.
- Измерить зарядный ток/верхнюю и нижнюю границы трех native battery modes.
  Пока7A6 readback подтверждает выбор firmware policy, не его процент.
- Температура батареи Win32=1 — реальное ограничение Battery Class в архиве.
  Не сканировать случайные EC адреса ради похожего числа; нужен exact BMS/OEM путь.
- Имя GCUBridge не добавлено в blacklist автоматически: артефакт действительно
  существует, но независимый EC writer GCUBridge без GCUService здесь не доказан.
  При дальнейшем разборе проверить его полномочия, не выдавать одно имя за баг.
- Старые research README содержат исторические «не подключено/ещё не проверено».
  Решения в этом отчёте сверены с кодом0.1.75, а не только с этими формулировками.

6. ПЕРЕКРЁСТНОЕ ДОПОЛНЕНИЕ: SETs CPU ПРЕСЕТ ПЕРЕПРИМЕНЯЕТ FANs

[P2 GM6-05 / common X1] Подтверждён прямой побочный эффект SETs на FANs.
Независимая проверка после чтения common.txt:X1:
src/gui/windows/SettingsPage.cpp:824 — карточка «Производительность Intel CPU»;
1357–1358 — writePerformance непосредственно вызывает gm6Controller->setMode;
src/devices/mechrevo/gm6ir0c/ControlWindows.cpp:281–290:
  stopOnline(); putTables(factoryCurves[mode],false); custom/light=0;
  mode751; Intel overrides=0; RAM commit=1.
putTables (59–74) переписывает FAN RAM и respective. Это не только смена CPU PL:
Manual online прекращается, пользовательская RAM-кривая заменяется OEM reference,
а раздельное управление принудительно меняется на совместное.

Родной OEM действительно так связывает whole-system profile с FANs:
MyFanManager_RamFan1p5.decompiled.cs:825–843 выбирает default/custom fan table;
2537–2604 меняет native mode/custom/light. Поэтому низкоуровневая последовательность
не объявляется случайным переносом X5 регистров или выдуманным OEM поведением.
Но это самостоятельный вопрос от разрешённого поведения нашей CPU-карточки.

В репозитории есть противоречащая контрактная документация:
- AGENTS.md:108–110 прямо запрещает запись вентиляторных таблиц из SETs,
  называет это согласованным пользовательским поведением, без исключения GM6.
- src/devices/mechrevo/gm6ir0c/README.md:71–75 прямо описывает GM6 SETs как
  полноценный OEM режим, связанный с FANs; POWER_MODES.md:3–6 ссылается туда.
  Это описание существующей реализации/аппаратной семантики, но в доступном
  контексте нет прямого пользовательского разрешения отменить общее правило.
- FAN_MODES.md основной запрет адресно описывает Wujie; его конкретные регистры
  и реализацию нельзя автоматически перенести на GM6. Данный вывод опирается
  на общий AGENTS.md и фактическую связь вызовов, а не на перенос карты Wujie.
- Требование владельца о Wujie как внешнем эталоне само по себе касается UI;
  оно не доказывает согласованное исключение для изменения FANs из CPU-карточки.

Вывод: X1 подтверждён как контрактная ошибка приложения и противоречие docs,
а не опровергнут совпадением с OEM. Предыдущий раздел2.3 описывал реализацию,
но не означал, что связанное whole-system действие согласовано владельцем.
Физическая неподтверждённость не нужна для этого вывода: stopOnline и RAM writes
видны прямо в исходниках.

Предлагаемое направление (в этой ревизии не выполнялось): отделить CPU-only
API/подтверждённые параметры PL от комплексного OEM setMode и сохранить FANs,
online intent и actual-state. Не обещать независимый native preset, если его
исполнение ещё не доказано, и не заменять его молча догадкой по мощности.
Согласовать противоречивые README/контракты. Внешний вид, порядок карточек,
геометрия и скролл Wujie должны остаться неизменными.
