2. МАТРИЦА ПЯТИ ОБЛАСТЕЙ
========================
SYS/EC:
  Реализовано: отдельная read-only диагностика 000–FFF; exact SMBIOS/PnP/
  service/SYS hash; узкий battery-only writer 7A6.4–5.
  Подтверждено на экземпляре: 4096/4096 байт, стабильные identity probes,
  установленный родной SYS совпал с pin. Это EC RAM, не образ firmware/flash.

Датчики CPU/GPU/RAM/SSD/АКБ:
  Реализовано: DTS/RAPL, IGCL, NVML/NVAPI, SPD5118, Windows Storage/NVMe,
  Battery Class, ACPI zones; независимые raw/status/null.
  Подтверждено: CPU, GPU, оба RAM hub и оба SSD читались в 0.1.69.
  Неизвестно: PCH module load failed; температура АКБ Windows не предоставлена;
  не заявляется, что найдены все физически существующие датчики.

FANs:
  В OEM: RAM Fan 1.5, режимы, boost, factory mailbox, LC.
  У нас: HYDROC fan getter/setter/Default/Max/mailbox не подключены.
  Подтверждено: native путь следует из реальной фабрики OEM и EC identity.
  Физическое управление MagicControl на этой модели не подтверждено.

Native battery protection:
  Реализовано: общий NativeBatteryController для GM6/HYDROC, отдельные guards
  и INI, read/set/readback, masked rollback, save, startup/resume queue.
  Подтверждено: адрес/маски/enum восстановлены из точного OEM.
  Не подтверждено: наш setter на экземпляре и физическая остановка заряда.

Подсветка:
  В OEM: ITE HID-first, затем guarded EC SingleZone fallback.
  У нас: общая SETs-карточка, но HYDROC RGB getter/setter ещё отсутствуют.
  Неизвестно: точные VID/PID/usage/page/FW клавиатуры этого экземпляра.

8. РЕАЛЬНЫЕ ДЕФЕКТЫ
====================
P1: в проверенной HYDROC ветке не найдено доказанного произвольного EC/HID
writer или переноса чужой карты. Это статический результат, не гарантия всегоПО.

[P2-HYD-01] Дамп теряет собственный сохранённый BatteryProtection HYDROC.
src/platform/common/DiagnosticDump.cpp:526–532 копирует фиксированный список,
в нём gm6ir0c-device-settings.ini, но нет hydroc16g2-device-settings.ini.
HYDROC пишет именно второй файл: NativeBatteryWindows.cpp:37,101–102.
Следствие: actual7A6 есть в EC, saved/requested из прошлого запуска в bundle
нет; нельзя сопоставить выбор и фактическое состояние/restore после сна.
Предложение: общий реестр профильных файлов; сохранять оба вида данных раздельно.
OEM:020001D1-...BatteryProtection2.cs:424–426,442–472,506–518 различает
хранимый HealthProtectionStatus, применение и resume.

[P2-HYD-02] Единичный transient отказ после resume поглощает restore.
NativeBatteryWindows.cpp:48 сбрасывает pending до open/apply; :55 лишь логирует
catch. Если driver/device/EC gate временно не готовы после сна, поздний
успешный пассивный read не повторяет saved apply. До нового resume/startup/
клика сохранённый профиль может остаться неприменённым.
Это доказанный статический путь ошибки; на экземпляре не воспроизводился.
Предложение: bounded retry только типизированных transient not-ready/busy,
с deadline/backoff, новой identity/ownership проверкой и отменой явным действием.
НЕ повторять OEM-owner отказ, неизвестный mode/INI, сменившийся SYS/identity.
Намеренно работающий OEM — политика владения, а не основание для takeover.
OEM:020001D1-...BatteryProtection2.cs:424–426 — resume setter. Retry предлагается
для нашей надёжности, не приписывается OEM как уже доказанный алгоритм.

[P2-HYD-03] «Общий EC counter0→0» в отчёте — константа, не измерение.
DiagnosticDumpWindows.cpp:120,122 выставляет writesBefore/After=0;
DiagnosticDump.cpp:452 подписывает это общим счётчиком, включающим независимый
контроллер. NativeBatteryController использует другой IEcBackend; его записи

Предложение: явно scope=diagnostic_backend и writes_requested=0; global=unknown
либо общий реальный transport counter с phase/time. Полностью пассивный режим
требует отдельной политики pending restore, если пользователь её согласует.
OEM:020000FA-AcpiCtrl.cs:251–274 различает Read/Write, но не доказывает наш counter.
D69 уже печатает этот текст, хотя нового battery worker тогда ещё не было.

[P3-HYD-04] Неверный provenance primary disk reading в diagnostic sensors.jsonl.

Ограничение вывода: обычный reader при уже известном property-value не вызывает

Предложение: сохранять source выбранного значения либо явно выбирать composite
вместе с value; независимые дополнительные каналы не объединять.
OEM reference неприменим: это наши Windows Storage/NVMe API, не OEM команда.

[P3-HYD-05] Intel HYDROC подписан в SETs как AMD/APU/SMU.

9. ЧТО ОСТАЁТСЯ ГИПОТЕЗОЙ / СЛЕДУЮЩИЕ ПРОВЕРКИ
===============================================
- FANs/RGB не подключены намеренно. Восстановленные тела дают план реализации,
  но не доказательство работоспособности нашего управления на экземпляре.
- Battery enum/readback не доказывает физическое прекращение заряда. Нужно
  отдельное согласованное временное наблюдение saved/actual,AC/DC,SOC,current,
  voltage/chargeflow. Не назначать native режимам100/95/85 по аналогии с Wujie.
- Для PCH сначала точные load HRESULT/PCI identity. Не подменять его ACPI zone.
- Для клавиатуры нужны path/VID/PID/usage/page/reportlength/FW/subtype;
  не брать первый похожий ITE и не путать lightbar с клавиатурой.
- Factory mailbox потребует полного rollback flags/table/LC и ownership.
  Native SetFanMode целым байтом не переносится буквально. Max30с позже —
  native Boost/100%duty с реальным RPM feedback, не выдуманная цель15000RPM.
- Свежего минутного дампа0.1.75 на HYDROC нет. Исправить полноту/provenance,
  затем получить новый bundle и отдельно проверить новую реализацию батареи.
- Disk hash не аутентифицирует загруженный kernel image. Противодействие
  злонамеренному kernel hook не было задачей этой ревизии.

ИТОГ
====
Read-only EC в пользовательском HYDROC работает; CPU/GPU/RAM/оба SSD уже имели
live данные. Native battery API подключён и ограничен отдельными guards,
но физический эффект ещё не подтверждён. FANs/RGB исследованы, не подключены.
Найдены дефекты полноты дампа, transient restore, write-counter, provenance,
подписей и диагностической причины PCH. Исправлять общие механизмы с сохранением
внешнего вида Wujie; исходники этой ревизией не менялись.

ABI и право применения:
Точный HYDROC SYS dispatcher знает read0x9C40A488/write0x9C40A48C;
цепочка GCUService/DefaultTool → AcpiCtrl → \\.\ACPIDriver → ACPI EC.
DefaultTool reader принимает DWORD address4 и берёт младший байт ответа;
writer — DWORD addr/value8. Наш read4/output16 и write8/output16 сохраняют
защитный запас на ширину ACPI integer. Native wrapper4МиБ — не требование
протокола. Дополнительные MMIO/PCI/IO/custom IOCTL не разрешены нашим HYDROC API.
Совпадение transport ABI с10.48 не доказывает взаимозаменяемость SYS, карт
регистров, capabilities или право FANs/RGB записи. Текущий HYDROC pin допускает
только e984...; SYS6e360... будет отклонён. Защиту не снимать ради комплекта.
