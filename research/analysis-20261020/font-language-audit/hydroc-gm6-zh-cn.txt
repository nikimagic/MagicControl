MagicControl — HYDROC/GM6 + Simplified Chinese UI audit
Date: 2026-10-20. Static source audit only. Production/UI/config unchanged.
Report owner: /root/hydroc. Common loader and Traditional Chinese are separately assigned.

SCOPE AND METHOD
Read AGENTS.md and docs/LINUX-UI-PARITY.md. Reviewed the complete shared
Localization.h catalog, Windows localization adapter and relevant GM6/HYDROC
status-producing paths, shared cards, Windows/Linux SETs/FANs/GPU pages,
model labels and text measurement paths. Used static literal/catalog inspection;
no application, GUI, hardware, build, tests or OEM code was run.
Line numbers below refer to the inspected source snapshot.

CATALOG COVERAGE: CONFIRMED FACTS
src/gui/common/Localization.h:14–216 has 201 Entry records, each with Russian,
English, Simplified and Traditional slots. All 201 Russian keys are unique under
ordinal comparison; all Simplified slots are nonempty. Case variants such as
Загрузка/загрузка and spelling variants with …/... are separate keys.
This proves field coverage for the catalog, NOT complete UI localization:
there is no exhaustive UI-key enum or compile-time lookup requirement.
translate():219–239 greedily replaces known Russian fragments; unknown parts
remain literal. Matching is case-sensitive and limited by Cyrillic word boundaries.
English-only source strings are returned unchanged by :220.
Simplified entries reviewed use simplified characters (驱动/电池/内存/固件/
键盘/设置/颜色/转储); no definite traditional-character leakage was found.
This is a language review, not a glyph-cmap or native-speaker certification.

[P2] ZH-05 — Desktop Linux OSD notification path bypasses shared localization
src/gui/linux/OsdService.cpp:124–136 notify() passes next.title/detail directly
to org.freedesktop.Notifications.Notify. No translate call in this path.
By comparison src/gui/windows/OsdPopup.cpp:193 uses localizedDrawText and
Linux in-app canvas text goes through Ui.cpp:74.

Confidence high for this path; no desktop notification service was executed.

[P3] ZH-06 — Cycle details and English mode captions are not fully localized
SettingsPage.cpp:800–816 mixes cataloged "Цикл 6" with absent lowercase words
"цвет", "каждые", "пауза", "режим", "аппаратная радуга", "пресет EC".
Case-sensitive matching means existing "Цвет" / "Каждые" entries do not cover
those dynamic fragments. Prefer full templates:
"六色循环 · 第 {index}/6 色 · 每 {seconds} 秒切换"
"六色循环已暂停：等待确认背光状态"
"当前亮度：{level}/4 · 模式：{mode}"
"硬件彩虹效果"; "EC 预设 {index}".
src/gui/linux/FansPage.cpp:394 and Windows FansPage.cpp:303–312 contain
Default/Manual/Max/Manual\nonline; Linux SettingsPage.cpp:154 uses Manual.
These have no Russian bytes and translate():220 returns them unchanged.
If the product policy is a fully Chinese UI, propose captions 默认 / 手动 /
最大转速 / 在线手动 (last may retain a two-line presentation without redesign).
Plainly adding English Entry keys will still not work with the current early exit.
If these English labels are an intentional user-approved product convention,
keep them and explicitly document that exception; internal enums/files unchanged.
Confidence high on coverage; caption-policy choice is not a functional defect.

[P3] ZH-07 — Technical wording refinements, not blockers
Localization.h:38 Веб-камера ->网络摄像头 suggests network/IP camera.
For a laptop webcam, prefer 摄像头 (or 内置摄像头 only if known internal).
:46 Мульти ->多色 is broad. For the confirmed native rainbow effect2 in
KeyboardBacklight.cpp, 彩虹 better explains the action. Apply only to that
semantic action; do not relabel an unrelated multicolor effect globally.
:65 Штатное управление EC ->EC 自动控制 adds an assumption about algorithm.
Prefer EC 固件控制 to preserve "firmware owns control", regardless of its curve.
:70 OEM hysteresis ->OEM 回差 is understandable engineering Chinese; OEM 滞回
is a clearer temperature-control convention. This is a consistency suggestion,
not a proven mistranslation. Keep one term across both tooltips and status text.
:185 current "EC 读回已确认更改。" is comprehensible; prefer
"更改已通过 EC 回读确认。" without claiming physical response.
Clock/CPU/GPU/VRAM/PWM/PL1/PL2/PL4/EC/ACPI/NVMe/SMART/DTS/RAPL/PawnIO,
API result names, hashes and hardware IDs may appropriately remain Latin.
No need to invent translated names for HYDROC-16 G2 or GM6IR0C.

FONT/LONG-MODEL OBSERVATIONS — NO CONFIRMED CLIPPING CLAIM
DeviceHeader.h:15–20 centrally supplies both model labels:
"MECHREVO · JiguangX GM6IR0C", "Eluktronics · HYDROC-16 G2".
These are hardware/product identities and should remain byte-for-byte; do not
translate JiguangX to another model name or shorten HYDROC identification.
"Unknown" is explicitly the user's chosen display name (LINUX-UI-PARITY.md),
so retaining English is intentional, not a missing Simplified translation.
Windows MainWindow.cpp:1734–1743 measures localized status text; SettingsPage
:612,618,856–857,890 measures translated captions with actual selected font.
Linux Ui.cpp:62–83 translates before Pango layout and ellipsizes non-wrapped text;
AboutPanel.cpp:117–145 measures model names/current-language note and uses
single-line ellipsis, not arbitrary model wrapping. This is good architecture.
NotoSansSC family is shared in Fonts.h:14–15; Windows Layout.h:35–39 uses it
when enabled, otherwise Segoe family; Linux Ui.cpp:50–69 uses it when enabled,
otherwise GTK system family. Generic loader/fallback certification belongs to
other agent; this report does not claim every glyph fits at all DPI or that all
system fonts cover Chinese. No actual GUI/measurement/render was run.
Changing a translation may require checking current-font/DPI measured text;
keep shared geometry/scrollbar and use measured text/ellipsis as documented.

PRIORITY / BOUNDARY
No P1 device-command defect found in this static language review.
First localize complete safety/availability/rollback templates, then properties
outside ordinary labels, then cycles/mode captions and terminology refinements.
Full-key or typed-message coverage avoids per-model dictionary forks and mixed
Russian/Chinese fragments. Raw vendor/Win32/HRESULT/API strings should remain
available in diagnostics alongside a translated user explanation.
A static201-entry field check is not proof of complete UI-key coverage, rendering,
font fallback, desktop OSD behavior or physical hardware capability.
