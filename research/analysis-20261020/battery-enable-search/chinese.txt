GM6/HYDROC: китайские источники о включении процентного ограничения
Проверено в интернете20.10.2026. Только исследование, без production-правок,
запуска чужих скриптов, EC/WMI/UEFI вызовов, тестов, сборок или аппаратных проб.

Вывод
Найден предметный lead: платформа/ROMID/Stored Limit могут блокировать consumer
порога даже при успешном readback7B9. Но найденная физическая проверка относится
к AMD JIAOLONG, исходный разбор firmware — к Wujie14XA. Прямого доказательства
этой ветки в GM6IR0C Project25 N.1.05MRO09 либо HYDROC-16 G2 Project26
N.1.13ELU11 нет. Совпадение Project26 с JIAOLONG не делает платы одинаковыми.
Поэтому это направление статического поиска exact EC consumer, не разрешение
переносить7C3=4, ROMID770=4 или запись87F в эти модели.

Локальное исходное наблюдение (поручение root, не новый аппаратный тест):
GM6 logs(3):85/80 удерживаются, remaining/full86→87%, ток≈+1.6A,7C3=7.
Это противоречит утверждению «85/80 уже исполняется»; gate остаётся гипотезой.

Точный target заявлен в README и docs/RESEARCH.md: JIAOLONG Series-X6xR55xK,
Ryzen9 8945HX / RTX5070Ti, BIOS N.1.21MRO34 от29.01.2026, EC1.32,
Project0x1A=26 / BIOS ProjectTRX1. Это НЕ Intel GM6IR0C и НЕ HYDROC G2.
README ограничивает физическую валидацию одной этой конфигурацией; широкое
Tongfang/Uniwill applicability не является таблицей доказанных совместимостей.
Дата публикации README отдельно не установлена; ниже есть датированные пробы.

Исследовательские детали:

Строки2–4 identity,111–131 прямо заимствуют pseudocode из Wujie14XA:
сначала проверяются7C3/770, затем допустимость87F, только затем используется

Таким образом даже constants4/5 из родственного разбора не полностью совпали
с наблюдениями другого build. Stored-limit/mailbox и persistence на EC1.32
сам автор оставляет непроверенными (169–183). Exact EC1.32 code image/hash или
адресный disassembly consumer в прочитанном документе не предоставлены.

3. Точность WMI-примера: читать код, не переносить готовый скрипт
https://github.com/losewayy/uniwill-ec-charge-limit/blob/main/tools/wmi_stored_limit.ps1
Raw https://raw.githubusercontent.com/losewayy/uniwill-ec-charge-limit/main/tools/wmi_stored_limit.ps1
Строки24–34 используют root/WMI AcpiTest_MULong.GetSetULong:
READ=(uint64(0x0100)<<32)|address; WRITE=(uint64(value)<<16)|address.
Пример RESEARCH.md:86 напечатан другим hex числом: правильное вычисление
READ87F по скрипту даёт0x000001000000087F, а не0x010000000000087F.
Это статическая арифметическая проверка, вызов не выполнялся.
Скрипт прекращает работу при sentinelFEFEFEFE, но mismatch ProjectID лишь
печатает NOTE(44–46); адрес/значение произвольные, paired ownership rollback
отсутствует. Его нельзя считать нашим exact-board guarded adapter. Наличие
AML frontend не доказывает существование EC handler на каждой прошивке.

Интеграционные рекомендации автора:
https://github.com/losewayy/uniwill-ec-charge-limit/blob/main/docs/INTEGRATION.md
Там742.bit2 предлагается как gate observation. Фраза «единственный надёжный
признак» не принимается как доказательство physical cutoff: нужны ещё ток,
remaining/full и поведение при пересечении upper/restart. Документ называет
процедуру read-only, хотя detection flow содержит записи; не запускать его
под видом чистого чтения. Теоретический87F-path не объявлен измеренным.

Текущий первичный driver:
https://raw.githubusercontent.com/torvalds/linux/master/drivers/platform/x86/uniwill/uniwill-acpi.c
Строки278–280:7B9 low7 и REACHED bit7;221–226:770 — начало14байт ROMID.
339–341 разделяют несовместимые charge_limit/charge_modes capabilities;
3173–3175 force исключает CHARGE_LIMIT. Battery init1997–2020 заменяет0/invalid
threshold на100 только на поддерживаемых устройствах. Это не доказательство

Практический следующий шаг (вывод автора отчёта)
Сопоставить exact GM6/HYDROC firmware consumer7B9,7D0,742.bit2,7C3,770,87F и
WMI/DSDT OEMG/RKBC/WKBC. Обычный readback0xFF из H2RAM87F не доказывает, что
сам EC stored_limit=FF: может быть blind window, что требует разделять в логах.
Не добавлять platform/ROMID/87F writer по этим аналогам. Читать наличие метода
и exact identity статически можно; существование runtime handler остаётся
отдельной проверкой. Физическое исполнение подтверждать данными тока/ёмкостей,
а не только selected mode,7B9/7D0 или gate bit.
