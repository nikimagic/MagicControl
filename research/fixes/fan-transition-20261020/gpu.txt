Windows OS physical binding
GraphicsAdaptersWindows.cpp enumerates present display-class PCI devnodes with
read-only SetupAPI metadata. DXGI AdapterLuid is matched to the exact Windows
SDK DEVPKEY_Device_AdapterLuid binary property (GUID c50a3f10-aa5c-4247-b830-
d6a6f8eaa310,pid3, from ntddvdeo.h). A unique full PCI VEN/DEV/SUBSYS/REV
match is a fallback; names and one VEN/DEV are insufficient. Contradictory
hardware IDs, multiple matches, incomplete/capped SetupAPI or DXGI enumeration
refuse a physical grouping ID. Missing metadata remains a status, not guessed.
Canonical identity is windows-pnp:<exact device instance>. LUID is explicitly
session-scoped. PCI bus/device/function come from SPDRP_BUSNUMBER/SPDRP_ADDRESS;
device=high16, function=low16 validated bus<=255/device<=31/function<=7.
PCI segment is not reported and remains null, never assumed0.
No D3D/render device, D3DKMT GPU handle or workload is created for the new bridge.

Windows AMD binding
RadeonGpuWindows.cpp uses DeviceId + separately queried SubSystemId and
SubSystemVendorId; full PCI SUBSYS = (16-bit device<<16)|16-bit vendor.
RevisionId corroborates when reported. This addresses the exact5006 vs50061D05
mismatch without changing existing ADLX UUID or control resolution.
OS hardware tuples must be unique. With duplicate identical GPUs, an ADL
BDF must match a known exact OS location; a candidate with unknown location
cannot win merely by exclusion of a known mismatching device. Multiple equal
locations/unknown PCI segments remain ambiguous. A unique OS adapter match
without proven physical devnode retains osAdapterId but has no physicalId,
so it cannot collapse independent physical GPUs.
Raw ADL AdapterInfo bus/device/function remain separately sourced fields.
ADLX UniqueId is treated as opaque:25600 is NOT decoded as bus100 despite the
numerical resemblance. IADLMapping is not borrowed from a differently initialized
ADL context; the existing ADLX initialization/ownership is unchanged.

AmdTelemetryWindows now selects Board73 -> ASIC23 -> GFX30 for primary power;
all three independent typed domain readings and every raw PMLog ID are retained.

existing powerSource field and existing rendered source line. No domain is summed.

fallback keeps exact getter source. No unsupported return becomes a valid0.

Shared UI primary-power choice across same physical sources is Board > ASIC >
generic GPU > GFX > unknown; never numerical max/sum/nonzero preference.
The source and domain identify what the displayed number measures. Domains are
not asserted equal, nor independent quantities that can be added together.
