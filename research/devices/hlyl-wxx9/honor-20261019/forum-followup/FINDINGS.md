# Honor: дополнительный поиск по форумам и GitHub

19.10.2026. Объект — HUAWEI HLYL-WXX9-PCB, BIOS1.09, Ryzen5 4600H.
Это исследование после успешного RAM-дампа0.1.58, а не новая аппаратная проба.
Код приложения, драйверы, настройки и portable в этом проходе не изменялись.

## 1. Предметная находка: WMIC в ACPI-диспетчере HLYL

В [Huawei-WMI issue38, комментарии владельца HLYL](https://github.com/aymanbagabas/Huawei-WMI/issues/38#issuecomment-728877399)
ещё в2020 описаны GLIV status1 и отсутствие действия SLIV. Это совпадает
с нашими наблюдениями18.10, когда штатная кнопка работала, а WMI-яркость нет.

[Ответ разработчика](https://github.com/aymanbagabas/Huawei-WMI/issues/38#issuecomment-728918236)
указывает на счётчик WMIC и второй ACPI-вызов. Проверено по нашему заводскому
`Honor-diagnostics-20261018-4a4c9e25/acpi/SSDT-007-registry.dsl`:

- WMIC объявлен в строке88;
- WMAA начинается в строке229, увеличивает WMIC;
- STAT по умолчанию1;
- dispatch выполняется при WMIC==2, после чего счётчик сбрасывается.

Важно: WMAA находится в SSDT, а не DSDT. Отсутствие определения WMAA в одном
DSDT не означает отсутствия метода во всём комплекте ACPI.

В исходнике aymanbagabas/Huawei-WMI (локальный commit
8ec76c88b73c3df01afbfc4cab75cd06fb6cd702), huawei_wmi_cmd, предусмотрено до2
вызовов HWMI: второй выполняется, если status первого ненулевой.

Но это не доказывает, что Windows Session::call надо повторять дважды:
она вызывает OemWMIfun через COM/WMI, а не напрямую Linux wmi_evaluate_method.
Установленная WmiUtil11.0.0.0 также использует один ExecMethod в разобранном
тракте. В нашем дампе0.1.58 все66/66 чтений GTMP имели корректный результат,
подтверждённый RAM. Внутреннее число WMAA-вызовов Windows-провайдера в этом
проходе не трассировалось. Нет доказательства, что WMIC — причина GLIV-ошибки
BIOS1.09; у этой команды есть ещё свой обмен C4/C5 с EC.

Следующий обоснованный разбор — сопоставить этапы COM/WmiAcpi и WMAA, отдельно
для getter. Глобальные автоматические повторы setter по любой ошибке недопустимы:
ненулевой OEM status не универсально означает «ещё не исполнилось».
Рабочий native I2EC backlight не заменяется неподтверждённым WMI-путём.

Первичные комментарии сохранены в `huawei-wmi-38-comments.json`.

## 2. Температуры: названия точек всё ещё не раскрыты

[Исходник Huawei-WMI](https://github.com/aymanbagabas/Huawei-WMI/blob/8ec76c88b73c3df01afbfc4cab75cd06fb6cd702/huawei-wmi.c)
называет0 CPU,14 battery; для5/7/8/11 сохраняет TSLO/TNTC/CNTC/DNTC.
В комментарии есть соответствия TP08/TP02/TP03/TP05 на других платах,
но нет доказательства расположения этих датчиков возле DRAM, GPU или зарядника.

Наши CTMP/TSLO/DNTC/CNTC/TNTC/BTMP связаны с RAM0320/0323/0324/0325/0327/032B
и уже подтверждены свежим снимком. Это проверенные каналы, но не маркировка
физических точек на плате. Других подтверждённых temperature-getter веток
именно HLYL в просмотренных первичных GitHub-материалах не найдено.

Нельзя превращать похожую температуру CNTC в «температуру памяти» по корреляции
одного снимка или расшифровке одной буквы.

## 3. ОЗУ: onboard DDR4 и отдельный TSOD-путь

[Официальный FAQ Honor MagicBook Pro2020](https://www.honor.com/cn/shop/help/category-88.html)
указывает распаянную память и отсутствие замены/расширения. Страница объединяет
Intel и Ryzen варианты; числовые параметры из соседних пунктов не следует
переносить между ними. Распаянная память сама по себе не доказывает отсутствие
или наличие температурного датчика.

У нас на HLYL выключен существующий опрос DDR5 SPD-hub: это правильное разделение
протоколов. Нельзя просто включить этот код для DDR4 и считать результат
температурой памяти.

Есть отдельный документированный кандидат — JEDEC JC42.4/TSOD:

- [Linux jc42](https://docs.kernel.org/hwmon/jc42.html): собственные адреса
  0x18–0x1F, temperature input и идентификация чипа;
- [ST STTS2004 datasheet](https://www.st.com/resource/en/datasheet/stts2004.pdf):
  датчик температуры и4Кбит SPD EEPROM — разные функции одного устройства,
  есть отдельные read-only capability/manufacturer/device/temperature registers;
- [Linux i2c-piix4](https://docs.kernel.org/i2c/busses/i2c-piix4.html):
  несколько портов SMBus, пример привязки jc42 к определённому порту.

Вывод: RAM-окно EC и стандартный TSOD — разные пути. Чтобы добавить настоящий
RAM temperature, нужно доказать наличие TSOD и его принадлежность памяти именно
этой платы: идентификаторы, capabilities, корректный формат температуры и порт.
Таких аппаратных данных с нашего Honor пока нет. Нельзя выводить «датчика нет»
из пустого поля Windows или неопознанного SMBIOS.

Этот проход не включал SMBus sweep, принудительное включение контроллера,
переключение страниц SPD, записи в EEPROM/config/thresholds или установку драйверов.

## 4. ADLX: совместимость не устраняет отсутствующую DLL

[Документация AMD о совместимости](https://gpuopen.com/manuals/adlx/programming-with-adlx/adlx-programming-guide/specifications/compatibility/)
описывает legacy initialization с уменьшенной функциональностью;
[InitializeWithIncompatibleDriver](https://gpuopen.com/manuals/adlx/adlx-page_cpp_help_initialize_with_incompatible_driver/)
предназначен для такого режима, но подходит не всем GPU/драйверам.

На Honor0.1.58 ошибка возникает раньше: установленный runtime не предоставляет
нужную ADLX DLL, загрузчик даже не получает функцию Initialize. Само изменение
initialization-флага эту причину не исправляет. Старый ADL уже отдаёт температуру,
загрузку и частоту GPU. Кандидат для программы — передавать существующую ADL
телеметрию в Radeon dump/card как явно подписанный legacy fallback, сохраняя
отдельный ADLX status. Это изменение в этом проходе не выполнялось.

Номер пакета драйвера27.20.11032.1001 сам по себе не доказывает, какие новые
Adrenalin-релизы совместимы с OEM-платой. Установка другого драйвера не проводилась.

  Это первичный пользовательский отчёт о другой машине. На наш AMD HLYL/Windows
  такой вывод переносить нельзя; отключать службы по этой теме не требуется.
- [CSDN: MateBook16s2023/Deepin](https://blog.csdn.net/Deng_Xian_Sheng/article/details/142447145):
  относится к Intel-платформе2023. Вместе с ранее скачанным KLVG/SFND разбором
  полезно для сравнения, не является HLYL-картой EC.
- [Авторский опыт Ryzen5 4600H на什么值得买](https://post.smzdm.com/p/akx8k8de/)
  в индексируемом тексте говорит о6 температурных датчиках; просмотр страницы
  браузерным инструментом вернул пустой текст. Это не источник точных адресов.
- [Официальная страница товара2020](https://www.honor.com/cn/shop/product/10086403884951.html)
  имеет название Ryzen4800H, но FAQ содержит маркетинговую фразу о7 датчиках.
  Вместе с материалами про Intel/MX350 это не позволяет доказать дополнительный
  седьмой программно доступный канал именно нашей платы. Решение даёт AML/измерение.
- Honor Club, Chiphell, Tieba и PCBeta включались в поиск. Большая часть выдачи
  относится к другим годам/платам, не содержит EC-карты или первичных измерений.
  PCBeta недоступен веб-инструменту из-за robots.txt. Отсутствие результатов
  поиска не означает, что таких сведений не существует.
- Страницы tsight.io с явной пометкой AI GENERATED не использованы как
  аппаратные доказательства. Торговые карточки вентиляторов также не подтверждают
  регистры/масштаб RPM/назначение датчиков.

## Приоритет дальнейшей работы

1. Сохранить проверенные I2EC и6 OEM-каналов без новых предположительных названий.
2. Разобрать WMIC на уровне Windows-провайдера, прежде чем менять семантику WMI.
3. Для температуры памяти исследовать именно JC42/TSOD и топологию SMBus.
4. Для Radeon-снимка использовать имеющиеся ADL-данные с указанием источника;
   отсутствие ADLX и отсутствие GPU-телеметрии не равнозначны.

Поиск не дал новой подтверждённой карты управления или нового рабочего Windows
EC SYS для HLYL. Это не отменяет уже работающий PawnIO/I2EC, а ограничивает
применимость найденных материалов.
