# Honor HLYL: расширенная диагностика и OEM-управление вентиляторами

19.10.2026. HUAWEI HLYL-WXX9-PCB, BIOS1.09, Ryzen5 4600H.
Windows11, PC Manager11.1.6.31. Использованы библиотеки MagicControl0.1.58.
Штатное приложение не закрывалось; его настройки и бинарники не заменялись.

## 1. Разрешённая проба100% PWM

Отдельный Release-helper слинкован с уже собранными magiccontrol_platform/core,
использует существующий HlylFanController, его exact-board/BIOS/PWM guards,
watchdog80°C и штатный возврат автоматики. Никакого нового EC setter не создано.
Исходник helper и read-only collector сохранены в `helper/`.

До пробы: manual=false, targets0/0, PWM0/0, RPM0/0, CPU37°C. Honor работал
от батареи; перед проверками заряд86%, к расширенному сбору84%.
20 последовательных отсчётов приблизительно через1с после установки100/100%:

| Канал | Медиана последних5 отсчётов | Диапазон последних5 | Пик пробы |
| --- | ---: | ---: | ---: |
| Fan0 | 8015 RPM | 7986–8015 | 8015 |
| Fan1 | 5796 RPM | 5796–5796 | 5796 |

Во всех20 отсчётах actual PWM=100/100%, targets=100/100%, manual=true,
period=200. Температура CPU во время пробы37→35°C, порог watchdog не достигнут.
Это достигнутые обороты данной пробы на батарее, не паспортные пределы моторов.

RPM проверялись двумя трактами: OEM HWMI GFNS и чтением RAM03CC..03CF через
PawnIO I2EC. На установившейся скорости значения совпадают; максимальная
разница последовательных чтений во время раскрутки30/15RPM. Снимки не атомарные.
На торможении разница кратковременно больше, что ожидаемо для меняющегося RPM.
Различие каналов не возникает при форматировании/пересчёте в GUI MagicControl;
оптическая калибровка тахометров в эту проверку не входила.

После пробы подтверждены manual=false, исходные targets0/0. Через3–4с оба
RPM0/0 при CPU34–35°C. Отдельный поздний `mctl oem-fans` повторно подтвердил
flags0, period200, duty0/0, targets0/0. См. `native-output.jsonl`, `final-state.txt`.

Запрос10 000RPM не посылался: проверенный native setter управляет PWM,
а не целевыми RPM. При100% нет следующего допустимого PWM для «докрутки».

PowerShell5 не предоставил ExitCode завершённого helper (null в native-result).
Поэтому нулевой exit code не заявляется. Есть независимые маркеры restored=true,
полный dump_finished и позднее чтение исходного EC-состояния.

## 3. DDR4 / SMBus / TSOD

Контроллер подтверждён как AMD1022:790B, subsystem152D:1273, I/O base0B00,
исходный primary port0. Использован неизменённый подписанный SmbusPIIX4.bin:
SHA25691F9B4B1C39E3D399CE48477A89D8F6BD3E58A2241064A4DAEC3A1513DFF56E5.
Сверена публичная реализация ioctl из PawnIO.Modules0.2.11,
commit52a7e536dff3e53c96917a28caac5e0fa6510696. Это идентичность исходника,
а не утверждение, что локальный runtime пересобран из этого commit.

Под глобальными Access_SMBUS/Access_PCI прочитаны только JC42/TSE2004 ID
регистры на0x18–0x1F. Temperature register разрешён только при совпавшей паре
manufacturer/device, но такой пары не найдено, поэтому чтение температуры
не было достигнуто. В EEPROM/SPD/config/пороги записи не посылались.

- Primary0: на всех8 адресах HRESULT0x800701B1.
- Auxiliary1 (отдельный base0B20): на всех8 адресах HRESULT0x80070079.
- После закрытия probe primary port0 и base0B00 повторно подтверждены.

Порты2/3/4 не перебирались: неизвестная для платы маршрутизация не становится
разрешённой из-за общего запроса диагностики; источник отдельно отмечает
конфликт с программами и reserved ports. Отсутствие TSOD на самой плате
не доказано. Есть только отсутствие доступного идентифицированного датчика
через два проверенных пути. Файл `tsod-observation.json` содержит каждый ответ.

SMBIOS сообщает2×8ГиБ Samsung M471A1G44AB0-CTD, DDR4/2667. Это описание BIOS,
не доказательство физического форм-фактора/наличия SPD-датчика на плате.

## 4. Повторные WMI-getters и доступность источников Windows

Серия24 вызовов COM/CIM через Windows OemWMIfun:

- GTMP CPU, Fn, Turbo, keyboard timeout, thresholds, voltage/current:21/21 status0.
- GLIV0602:3/3 status1, длительность599/604/616мс. Повтор getter не устранил ошибку.
- Текущие Fn=false, Turbo=false, timeout0, thresholds70/90.
- GCVA20:7984мВ; GCVA30:-670мА, sign/magnitude корректно разобраны.

Это не трасса внутренних ACPI-вызовов WmiAcpi, поэтому число выполнений WMAA
на один COM-вызов не объявляется измеренным. Но наблюдений «каждый второй
getter успешен» в этой серии нет. Глобальные повторы setters не добавлялись.

Windows самостоятельно вернула14 строк ProcessorInformation,527 строк
GPUEngine и2 строки GPUAdapterMemory. Ошибка «Слишком много записей WMI» в
обычном дампе объясняется нашим ограничением512, не отсутствием счётчиков.
Полные527 строк этой диагностики сохранены в windows-performance.json.

System32 atiadlxx.dll7.20.10.1382 присутствует, подпись Valid, SHA256
3E528E4230830517FCA535A416A4056425012CB2A7495B61E24F4D7152602906.
amdadlx64.dll отсутствует, поэтому ADLX не доходит до инициализации.
NVML/Intel ControlLib отсутствуют; NVIDIA/Intel GPU у этой машины не обнаружены.
ADL уже предоставляет рабочие данные AMD. Вторая DXGI-запись сама по себе
не доказывает вторую физическую GPU; есть также Huawei Virtual Display Device.

StorageReliabilityCounter:SSD36°C, TemperatureMax84°C, Wear0.
84°C — исторический максимум провайдера, не температура пробы.
Поля PowerOnHours/total errors здесь не сообщены; это не подтверждение нулевых ошибок.
За выбранные25мин System не вернула соответствующих уровней1–3 событий;
это ограниченное окно, не доказательство отсутствия любых прошлых неисправностей.

WSL executable есть, зарегистрированных пользовательских дистрибутивов нет.
Linux/sysfs на самом Honor в эту проверку не входил; ОС не устанавливалась.

## 5. Как установленный Huawei-софт управляет вентиляторами

Прослежен конкретный Turbo-путь PC Manager11.1.6.31:

```
PowerManagerUIPlugin.dll: кнопки turboHighEnergyButton / balanceHighEnergyButton
  → payload1 байт 1/0, IPC0x46000E
  → PerfCommonPlugin.dll: TurboMode::OnReceiveModeChange
  → WmiUtil.dll: HwSDK::BiosWmi::SetTurboMode(bool)
  → OemWMIfun, command0x0F04, byte2=1/0
  → SSDT WMAA → DSDT STUB
  → EC TUBO (RAM0315.bit6), OEM event0x2A1/0x2A0
  → штатная EC-регулировка
```

Декомпилированные точки:

- UI RVA6A6D0: выбор кнопки вызывает RVA6AAB0 с1/0.
- UI RVA6AAB0: message0x46000E, length1, payload=1/0; RPM/PWM в сообщении нет.
- PerfCommon RVA3290: регистрирует handler0x46000E → RVA3930.
- PerfCommon RVA3930: проверяет length1 и вызывает SetTurboMode(payload>0).
- WmiUtil RVA31C0: собирает0x0F04 + bool в byte2.
- PerfCommon RVA37A0: читает GTUB; доступность UI требует AC и заряд>=21%.
- DSDT STUB в BIOS1.09 меняет TUBO только при AC. На батарее status0 сам по себе
  не подтверждает изменения — нужно читать GTUB/бит. Этот setter в диагностике
  не вызывался.

PerfCommonPlugin.dll11.0.0.0 реально загружен в MBAMessageCenter, подпись Valid,
SHA2566981FD789AEED1B396B3B129AEBAB1268CBA5D070E45BE780137D9C3BA7FF461.
PowerManagerUIPlugin.dll взят из той же установленной поставки, SHA256
1BC4D999A3111B023DAF80F43B9ABF3626AD2E7AAABCADEF92A31DBCDAFA4EC4.
UI-плагин во время чтения модулей не был загружен: цепочка UI подтверждена
статически, живое нажатие OEM-кнопки не имитировалось.

В исходной EC firmware1.09 fan-блок file1360F читает RAM0315.bit6 и выбирает
разные пути получения таблицы/указателя6A6/6A9. Далее1376F/137AC сравнивают
16-битные значения и меняют PWM1808/1809 небольшими шагами. Это штатный
алгоритм с обратной связью, а не передача8000 или10000 из OEM UI.
Точные физические единицы всех внутренних16-битных полей и полная структура
заводской таблицы этим описанием не объявляются окончательно восстановленными.

Итог для найденного штатного Turbo-пути: OEM задаёт режим, EC выбирает
регулирование. Наш проверенный manual I2EC — отдельный PWM override
042C.bit1 +0532/053C, не вызов этого OEM IPC. Вендорный GetFanSpeed читает
готовые RPM; он не setter. Прямой OEM setter произвольных RPM в разобранной
цепочке не найден, что не доказывает отсутствия всех иных скрытых интерфейсов.

SMU PM370003, STAPM/Slow/Fast31.5/31.5/31.5Вт, stale=false на батарее.

и её штатного отката; диагностические чтения не применяли настройки.

пересобиралось и GitHub-релиз не менялся.
