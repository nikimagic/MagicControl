# GM6IR0C: физическая кнопка режимов, OEM цикл и белый Custom

Статический разбор 21.10.2026. База продукта: commit `3c6234dfd3e53bad3e72d7bc50d196cc6754c7c2`, portable0.1.129. Никаких запусков приложения/OEM/драйвера, аппаратных чтений/записей, новых тестов или сборок не выполнено. Производственный код не изменён. Python прочитал только сохранённые файлы.

## Главный результат

1. **В0.1.129 на GM6 физическая OEM кнопка не обслуживается нашим приложением.** Общий `OemEventMonitor.cpp:54–56` допускает `AcpiTest_EventULong` только для `wu-jie-15-xpro`. GM6 подписывается лишь на `WmiMonitorBrightnessEvent`. Это подтверждено новым журналом, строки29–30. Следующая независимая проблема: даже при доставке события176 `MainWindow.cpp:1071–1072` возвращается без переключения профиля. Его ранний callback умеет только общий OSD, не OEM state machine.
2. В активном OEM найдена исполняющая цепочка `ULong=176 (0xB0)` → `WMIEC.WMIHandleEvent` → `MyFanCtrl.ModeSwitchChanged` → `MyFanManager_RamFan1p5.ModeSwitchChanged` → `SetModeSwitchChangeThread` → `SetModeSwitchChange` → `UserSet_Mode*` → `SetUserProfile` → `SetFanMode`, RAM fan table, CPU/GPU policy.
3. **APP presence741.0, Custom726.7, CustomerModeLight727.6 и RAM commit7C6.2 — разные поля.** OEM прямо включает727.6 только в Custom и снимает в трёх штатных режимах. Наш Manual/online ставит727.6 и726.7; Default снимает их. SETs CPU-only этого не делает.
4. Свидетельство владельца «с MagicControl всегда белый» не подтверждается как универсальное аппаратное состояние этим журналом: первые3мин18с `custom=false/ram=false`, затем есть Manual/online и `custom=true/ram=true`, краткий возврат Default, повторный Manual. Светодиод напрямую не измерен,727.6/741.0 в строке `mode=` не публикуются.

## Полная восстановленная цепочка

### EC/ACPI → WMI

В DSDT `ECXP` — SystemMemory окно `ECMA+0x400`, `ECMA=0xFE410000`. Поле `OSDF` находится на смещении0x7C внутри окна, т.е. наблюдаемый RAM адрес0x47C. Не заменять его Wujie-адресом0x78C.

`_Q53` (`DSDT.dsl:135174–135182`) после20мс получает `OSDF`, вызывает `AMW0.WMBC(0,3,OSDT)`, после ещё20мс очищает OSDF. `WMBC` (`133238–133260`) при Arg1=3 сохраняет Arg2 в **SAC1** и делает **Notify(AMW0,0xD2)**. `_WED(0xD2)` возвращает SAC1 (`133272–133292`). Это именно ветка **SAC1/D2**, а не похожая соседняя SAA1/D0.

OEM подписывается в `WMIEC.StartWMIReceiveEvent` на `Root\WMI`, `SELECT * FROM AcpiTest_EventULong`, читает `e.NewEvent.SystemProperties["ULong"]`. Case176 назван `OSD_FanModeSwitch`, вызывает менеджер, а не только OSD (`WMIEC.cs:139–144,303–311`). Native App создаёт подписку при инициализации (`App.cs:480`).

**Граница доказательства:** физический контакт спидометра → конкретный firmware producer OSDF=0xB0 не виден в DSDT/OEM. OEM consumer176 найден, сообщение владельца с ним согласуется, но изолированного сохранённого нажатия этой кнопки с записью события176 нет. Не объявлять этот последний участок измеренным. Встроенный без-CC трёхрежимный цикл находится внутри EC firmware; RAM-дамп не содержит его исполняющего кода.

### WMI → четыре режима OEM

`MyFanCtrl.cs:192–195` делегирует выбранному менеджеру. Для exact board Project25/некоммерческого RamFan1.5 выбран `MyFanManager_RamFan1p5`. `ModeSwitchChanged` (`719–789`) использует **сохранённый OperatingMode приложения**, а не читает очередной индекс из751.

В обычной Turbo-capable ветке: Office0 → Gaming1 → Turbo2 → Custom3 → Office0. `SetModeSwitchChangeThread` (`3331–3366`) сериализует команды семафором, держит200мс, запоминает последнюю быструю команду; это не10-секундный таймер. `SetModeSwitchChange` (`3368–3405`) вызывает:

| OEM индекс | Handler | Название |
|---|---|---|
|0|UserSet_Mode2|Office|
|1|UserSet_Mode1|Gaming|
|2|UserSet_Mode3|Turbo|
|3|UserSet_Mode4|Custom|

Есть специальные ветки: TurboModeSupport=0, AppType=3 и CustomId=39 изменяют цикл/набор. В сохранённом OEM SupportInfo (`samples/companion.log`) exact machine показывает CustomizeTarget52, TurboModeSupport1, Project25, RamFan1p5Support1. AppType читается из HKLM OEM/GamingCenter2, default1 (`manager:202`); значение реестра этого устройства отдельно не зафиксировано. Четырёхрежимная обычная ветка согласуется со свидетельством владельца, но AppType не подменён предположением.

### SetUserProfile: это весь системный профиль, не только CPU

`UserSet_Mode1/2/3/4` (`874–943`) обновляют OperatingMode, текущий профиль, конфигурацию, NVRAM `PowerMode`; обычные режимы снимают FanBoost. Gaming/Office вызывают configurableTGP target95, Turbo115 с DynamicBoost; эти числа — литералы OEM вызова, не доказанный измеренный итог TGP.

`SetUserProfile` (`2295–2457`) вызывает `SetFanMode(mode)`, обновляет трей, выбирает RAM fan table и commit через `FanTable.SetFanTable`. В зависимости от поддержки аппаратуры далее:

- обычные Intel режимы обнуляют overrides783/784/785, Custom записывает свою PL-тройку;
- задаёт CPU voltage/TCC и fan switch speed;
- задаёт GPU offsets/target temperature/DynamicBoost/Whisper и связанные политики;
- может менять memory overclock и liquid cooling для поддерживаемых конфигураций.

Это **не** эквивалент наших кнопок0.1.129 Office/Balanced/Turbo: они CPU-only и намеренно сохраняют FANs, native751 и GPU. Слепой перенос `UserSet_Mode*` нарушит существующее разделение и добавит незаказанные побочные действия.

## Биты, индикатор и значения751

OEM `SetFanMode` (`2537–2610`):

|Профиль|751 без FanBoost|CustomerModeLight727.6|Custom726.7|
|---|---:|---:|---:|
|Office0|0xA0|0|0|
|Gaming1|0x00|0|0|
|Turbo2|0x10|0|0|
|Custom3|0x00 либо0x10 при OverClockingEnabled|1|1|

FanBoost —751.6, добавляется отдельно. Поэтому751=0 не различает Gaming и Custom. `GetFanMode` в OEM использует только751.7/.4 и другой return numbering; его нельзя использовать как полноценный decoder четырёх OperatingMode.

`CustomerModeLightOn/Off` — прямой RMW727.mask0x40 (`MyFanTableCtrl.cs:162–197`), соседние биты сохраняются. Название этой функции доказывает назначение OEM-индикатора Custom; **реальный белый цвет и приоритеты LED решает прошивка**, RGB-таблица светодиода здесь не найдена. Отдельно custom726.7 и commit7C6.2 (`MyFanTableCtrl.cs:139–159`) влияют на режим/исполнение RAM. Нельзя считать эти четыре поля взаимозаменяемыми и переключать только свет ради исправления поведения.

`Set_APExistToEC` — RMW741.mask1 (`MyEcCtrl.cs:304–311`). Native App устанавливает при init/resume и снимает при Exit. Наш `putTables` устанавливает741.0 при явном Manual/online; Default сохраняет APP presence. **Нет оснований утверждать, что741.0 автоматически означает белый Custom**, или переносить Wujie auto-blanking. Подтверждённый consumer-флаг727.6 гораздо ближе к жалобе, но без сохранённых727.6/светового результата полной причинности нет.

**Явная неподтверждённая гипотеза:** наблюдение владельца «без CC три режима, с CC четыре» может означать, что firmware при APP-present передаёт переключение хосту событием176, а без APP-present исполняет собственный трёхрежимный цикл. Тогда установка741.0 нашим Manual вместе с отсутствием GM6-подписки и исполняющего handler могла оставлять нажатия без обработки. Это логически совместимо с найденными путями, но **consumer741.0 в firmware не найден**, точные условия генерации176 не установлены, причинность не доказана. Гипотеза не является основанием устанавливать/снимать741.0. Для проверки нужны сохранённые741.0, событие176,727.6 и цвет до/после каждого физического нажатия с временной привязкой, при отдельно зафиксированных режимах приложения.

## Что потребуется для корректного повторения штатного поведения

1. Сначала расширить **существующий** OEM event adapter с точным GM6 profile/capability admission, затем общий handler для176. Одной подписки недостаточно. Вывод OSD из общего сервиса сохранить; текущая generic-фраза «настройка изменена» не подтверждает применение.
2. Нужна отдельная явная модель **штатного системного профиля**, а CPU PL preset, FANs Default/Manual/online/Max и LED-индикация остаются отдельными состояниями. Источник текущего состояния нельзя определять по ваттам, яркостиLED или751 в одиночку.
3. Полный OEM whole profile сознательно меняет FANs, CPU и GPU; это выходит за границы существующего CPU-only API. Это **ограничение исходной архитектуры, а не запрет пользователя на штатный системный профиль**. Для будущей реализации область физической кнопки следует выразить явно: отдельный native whole profile с прекращением нашего online-владения либо CPU-only цикл без обещания штатных цветов/тепловой политики. Не расширять текущие CPU-only кнопки скрытыми FANs/GPU/NVRAM-записями. В настоящем исследовании действует прямой запрет пользователя **пока ничего не менять в EC**; он соблюдён.
4. Если выбран native whole profile, построить транзакционный exact-device writer: маски mode/CustomerLight/Custom, понятный переход от RAM/FanBoost/online, readback и корректный отказ/rollback своих полей, защита от OEM второго владельца. Проверить необходимость751.5,741.0 и commit по прошивке/контролируемому опыту. Не копировать OEM полнобайтовую запись751, которая теряет соседние биты.
5. GPU/NVRAM/voltage/TCC побочные действия не переносить автоматически. Заводские fan tables брать из подтверждённого exact-device источника. Не имитировать профиль одним индикаторным битом.
6. Для последнего участка нужен сохранённый эксперимент физической кнопки: отдельно Default/native без других команд, фиксировать событие176,751,726.7,727.6,741.0,7C6.2,PL и цвета до/после каждого нажатия при OEM и MagicControl. Это предложение для будущего разрешённого опыта; сейчас ничего не запускалось. RAM-дампы позволяют сверить состояния, но не восстановить отсутствующий firmware producer и без-CC state machine.

## Ограничения

- Нет EC executable firmware: автономная обработка кнопки/LED цвета/741.0 consumer не восстановлены.
- Новые логи не включают isolated speedometer presses,727.6/741.0 или LED-фотографии с временной привязкой. Нулевой captured-event count не доказывает, что владелец не нажимал кнопку: приложение не было подписано.
- OEM ветки вычислены статически, реальные аппаратные последствия не проверялись.
- Задержка200мс сериализации кнопки не связана с10с UI refresh BatteryProtection2. Не связывать кнопку питания/индикатор зарядки с profile LED.
