### Intel файл — полезный BIOS-регион16МиБ

`pass1.partial.bin` содержит16 777 216байт,
SHA256 `e6f32976b391d66a20649b71b5cfb0bd44d5c42a521f30e46ef5c71dd09a68ff`.
В нём18 структурно допустимых FV headers с корректной header checksum; Reset
Vector совпадает со старым полным GM6 SPI. Файл не состоит из00/FF и не выглядит
оборванным на случайной длине: AFU закончил своё окно16МиБ.

В ранее присланных полных32МиБ `backup.fd`/`new.fd` проверен Intel Flash Descriptor:

| Регион | Смещения в полном SPI | Размер |
|---|---|---:|
|Descriptor|00000000–00000FFF|4096байт|
|GbE|00001000–00002FFF|8192байт|
|ME|00003000–003DCFFF|4 038 656байт|
|BIOS|01000000–01FFFFFF|16 777 216байт|

Новый AFU файл соответствует именно этому BIOS-региону:

- с BIOS частью патченого `new.fd` совпали16 561 035байт (98.71146%),
  4019 из4096 блоков по4КиБ;
- все отличающиеся блоки находятся до0x60000, в первых384КиБ;
- от0x60000 до конца весь остальной BIOS-регион побайтно совпадает с `new.fd`;
- с BIOS частью исходного `backup.fd` совпадение75.95093%,3080 блоков;
- встроенный EC update payload131072байта SHA5059e6cb... найден целиком
  по BIOS-offset0x51BB1C. Это обновляющий payload, не новый live EC/e-flash dump.

Это даёт сильную файловую привязку к ранее сохранённому патченому GM6 BIOS.
Уточнение после прямого сравнения с непатченым backup.fd приведено ниже:
первые384КиБ — два NVAR-хранилища, а не единый блок ROM-ID.

В начале AFU файла нет Intel Flash Descriptor, а ME/GbE в нём отсутствуют.
**Полный32МиБ SPI этим Intel запуском не получен.** Отдельный live EC flash и
его постоянный ROM-ID также не получены. Два прохода Intel не сравнивались —
второй отсутствует.

### Точная причина ошибки приложения

В `AmiBiosDumpWindows.cpp::validate` сначала проверяется `file_size==SMBIOS size`.
На Intel это16 против32МиБ. Затем есть отдельная проверка Descriptor/ME для Intel.
Первый guard бросает исключение, collector записывает manifest failed и не
начинает pass2. `win32_last_error=0` при этой ошибке соответствует программному
отказу проверки, а не Win32-коду аппаратного сбоя.

Слово `.partial` означает здесь «не прошёл проверку полного SPI». Полезный
BIOS-регион сохранён и не потерян. В manifest отсутствует его SHA, поскольку
поле sha256 заполняется после полной валидации; вычисленный выше хэш сохранён
в `bios-comparison.json`.

Правильная доработка: разделить типы результата «BIOS-регион» и «полный SPI»,
проверить второй проход допустимого региона и показывать его как проверенный
регион16МиБ с full_spi=false. Для полного Intel SPI нужен отдельно подтверждённый
путь чтения Descriptor/ME/GbE. Просто снять проверку размера и назвать16МиБ
полным32МиБ образом нельзя. В README AMI `/O` описан как save current ROM image;
сам этот режим не является универсальным обещанием всех регионов Intel SPI.

События driver_before показывают оставшуюся остановленную GENERICDRV службу
от ручного инструмента; driver_after — services пустой. Активного конфликта
драйвера не записано. Команд программирования flash/EC в логе нет, запрошен `/O`.

## 4. Пульсация и недоступный выбор цветов

В23:30:45.623 выбран Pulse. Весь свежий лог содержит переключения эффектов,
но не нажатия цветовых кнопок: UI их отключил.

В0.1.187 есть три блокировки GM6 Pulse:

1. `updateButtons` разрешает палитру только вне Pulse/Multi.
2. `paletteIndex` возвращает-1 для GM6 Pulse.
3. `writeColor` бросает «Палитра пресетов пульсации GM6 требует визуального подтверждения».

Таким образом, это подтверждённое программное ограничение интерфейса, не отказ
попытки записи выбранного цвета. Native OEM SingleZone использует BreathingIndex
1–4 в7C5.low3 и сохраняет upper bits. Запись этих четырёх пресетов подтверждена
родным кодом. Совпадение их физических цветов с Wujie White/Red/Green/Blue не
подтверждено; нельзя автоматически переносить чужую цветовую легенду.

У HID зон другой механизм: breathing принимает RGB. Их выбор цвета должен
сохранять breathing effect, а не переводить конфигурацию в Mono.

Нажатия Off140 в свежем187 нет. Исправление выключения эффектов184 этим
архивом физически не испытано. Итоговые keyboard.apply теперь содержат полный7C5:
Pulse1,Multi0,Cycle0 и соответствующий767.7; данные читаются без ошибок.

## 8. Приоритеты

1. BIOS collector: сохранить полезный BIOS-region как отдельный тип результата,
   выполнить и проверить два чтения региона,продолжить отдельное исследование
   полного Intel SPI. Не снимать защиту полноты и не подставлять размер16 вместо32.
2. Убрать подтверждённую UI блокировку четырёх native Pulse пресетов GM6,
   сохранив точную модельную легенду; на HID не сбрасывать breathing при RGB выборе.
3. Отдельно проверить физический Off после Pulse/Multi и remaining power-input
   stages; в этом свежем187 их не выполняли.
4. Продолжить поиск причины NVIDIA P0/18–19Вт. Сохранение старого числа при
   ошибке — исправление отображения, не энергетический ремонт драйвера.

## 9. Прямое сравнение с непатченым backup.fd и ROM-ID

Первые0x60000байт BIOS-региона исходного backup.fd и патченого new.fd
**побайтно одинаковы**, SHA256
ccf106d9ddb6702f8ad32197674c6d5c08a23c261aab0a6a2e2e465ca338837e.
Это два FV по0x30000 с raw FFS/NVAR-хранилищем
CEF5B9A3-476D-497F-9FDC-E98143E0422C. Изменение всего prefix свежего дампа
составляет216181байт относительно любого из двух старых файлов. Оно не
объясняется простой заменой одного ROM-ID-байта. После prefix свежий файл
**полностью совпадает с патченым**, а относительно непатченого там3818583
отличающихся байта. Пересборка/сжатие BIOS при патче объясняет отличие размеров
изменённых областей от10байтов изменения внутри распакованного Setup PE.

Выполнен UEFIExtract NE alpha75 только над сохранёнными384КиБ excerpts.
Отсутствие Volume Top File в этом обрезанном excerpt ожидаемо. Оба FV headers
и FFS checksums корректны. Stock имеет F0 store0/E0 store1, fresh — наоборот.
Для сравнения выбраны F0-хранилища; это файловая интерпретация, не live
GetVariable query. Разобраны цепочки Next; нет неразрешённых цепочек у
выбранных действующих корней. Stock:105 переменных, fresh:110;83 тела
идентичны,17 изменились,5 есть только в stock,10 только в fresh.
Имена/размеры/хэши сохранены в nvram-comparison.json, без публикации payload.

UniWillVariable180байт отличается только поoffset5D и61:01→00.
В сохранённой OEM NVRAM_STRUCT эти поля названы **ApExistFlag** и **ApUseFlag**;
структурные offsets и SHA исходника повторно сверены. Это статическая схема
из декомпила, не запрос действующего BIOS. Battery
storage30/31/32 остаётсяFF/FF/FF в обоих файлах. **Это не EC RAM770**;
связь двух изменившихся полей с ROM-ID не установлена. Setup/CpuSetup/SaSetup/
PchSetup присутствуют, BootOrder/Boot0000 и PK/KEK/db побайтно сохранены.
Обнаруженные изменения dbx, counters, MemoryConfig и иных runtime-переменных
сами по себе не доказывают повреждения. В новом выбранном store отсутствуют
три старые VsmLocalKey-переменные и две policy-переменные; причина и последствия
для функций Windows из этих файлов не устанавливаются. Утверждение «вообще
ничего не изменилось/не потерялось» было бы слишком сильным. Признаков потери
кода BIOS нет: весь участок после384КиБ точно равен патченому эталону.

В ранних сохранённых GM6 EC-снимках было7C3=07/770=FF (в частности архив3,
0.1.98,20.10.2026); сопровождающие свежий BIOS-дамп логи показывают07/04.
Сам SPI backup/new содержит встроенный EC update payload с невалидным нулевым
шаблоном ROM-ID, а не текущее постоянное хранилище отдельного EC. Из этих
host BIOS файлов нельзя объявить7/FF либо7/04 сохранённым EC ROM-ID.
