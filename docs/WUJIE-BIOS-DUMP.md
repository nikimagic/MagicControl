# Снятие BIOS ROM на Wujie X5SP4NAG

## Общий Insyde reader,01.11.2026

INFO/CLI используют прежний единый ресурсный BIOS entry. H2OFFT6.76 выбирается
по фактическому Insyde BIOS vendor или корректной ACPI UEFI/H2O таблице, на
AMD/Intel, включая Unknown. Выбранная GUI модель, название платы и BIOS1.09
не являются допуском. Проверенный FPT на Intel сохраняет приоритет; если LPC
не входит в его таблицу, подтверждённый Insyde может выбрать H2OFFT до запуска
какой-либо утилиты. После ошибки уже запущенного ридера другой не пробуется.

Candidate detection только выбирает возможный backend. Нативный H2OFFT обязан
принять IHISI; отказ/ошибка сохраняется вместе с raw vendor logs. EXE/SYS/CAT,
INI и фиксированная команда `<new output> -g` прежние. Никаких новых switches,
base/size overrides, firmware inputs, hooks, flash/unlock/reset команд нет.

Общий file-only validator ищет HFDM, проверяет header checksum, известный
формат84/0 без неизвестных extensions, ROM base, границы/перекрытия регионов,
самоописание карты, SHA256 немодифицируемых регионов и FV header checksums.
Размер подтверждается SMBIOS либо размером top-of-32bit ROM window из самой
карты; длина файла сама размер не назначает. AMD дополнительно требует EFS и
корневую PSP/2PSP цепочку с верными Fletcher32, без смещений Honor. Ошибка,
неизвестный формат или несколько карт дают сохранённый partial/отказ.

Два независимых чтения должны совпасть. `passN.insyde-map.json` содержит карту,
declared/derived size source, PSP roots и region hashes. Manifest schema5
различает `completeness_scope=rom_map/full_spi/declared_rom_size` и
`rom_map_verified`; Insyde без полного Intel Descriptor остаётся
`physical_spi_complete=null`, даже при успешной проверке ROM. Intel Descriptor,
если присутствует, проходит прежнюю строгую SPI проверку. Неизвестные host-read
права не представляются как true для карты Insyde/AFU.

Исходный Honor16MiB и его прежние corruption checks проходят общий поиск
HFDM/PSP; синтетические Intel/AMD8/32MiB проверяют другие смещения, усечение,
ошибки checksum/extent и защищённых hashes. Это файловые проверки; новые
устройства на железе ещё не проверены. Linux собирает общий validator, но
Windows H2OFFT/SYS в Linux не исполняются, Linux BIOS reader не добавлен.

## Содержимое AMD AFU32 проверено по сохранённому дампу,01.11.2026

Снимок29.10, SHA3e4a7745..., содержит согласованную EFS→PSP→A/B→BIOS карту:
6 каталогов/174 записи,4 image-slot header,9 FV с правильными header checksum,
две полностью распаковывающиеся BIOS-копии. Проверены реальные flash-смещения
с учётом relative addressing и сжатия, а не только размер33 554 432байта.
Включены PSP NV DATA/RPMC, APCB/APOB NV и обе AMI NVAR области19C0000/19E0000.
Их type6D ссылки в обеих BL2 совпадают с фактическими хранилищами; в каждой
SPIROMSIZE=32МиБ. По сравнению с24.10 все изменения только в объявленных NV.

Это **структурно согласованный ROM32**, не независимая аттестация всего
физического SPI: JEDEC/аппаратного сравнения нет; неописанные/резервные области
отдельно не подтверждены. Текущий production AFU validator этим исследованием
не менялся; physical_spi_complete остаётсяunknown. Нельзя объявлять отдельные
EC flash, OTP/RPMC counters или внешние EEPROM включёнными в такой образ.
Подробная карта, decompile AFU size-from-blocks и воспроизводимый file-only
анализ: [REPORT](../research/wujie-afu-completeness-20261101/REPORT.md).

## Подключён FPT19 для двух Ultra-моделей, версия0.1.191

К существующему автовыбору добавлена отдельная ветка: фактические
`eluktronics-hydroc16g2` или `mechrevo-yaoshi-series-x6ar55xy`, CPU vendor
GenuineIntel и ProcessorNameString Ultra9 275HX → IntelFpt19.0.5.1948.
Профиль определяется по реальным manufacturer/baseBoard/product через общий
реестр, без EC. Подпись CPU нормализуется только по ASCII имени; другие Ultra,
другая модель или просмотр меню не получают этот допуск. Нужен единственный
настоящий present LPC class0601 из таблицы19:7F00–7F7F/7700–777F, затем
успешный vendor -I. Отказ не запускает другой FPT или AFU автоматически.

Original bytes из Colorful iGameCenter2.0.0.82: FPTW64_8102.exe19.0.5.1948,
SHA88491119..., встроенный RT_RCDATA118 SYS2508.0.23.0 SHAacd5d366....
Отдельная protected embedded group IntelFpt19 с собственными source/hash pins,
подписи FPT Intel и SYS Microsoft WHCP проверяются offline до запуска.
Папка licenses/Intel-FPT19 содержит NOTICE/PROVENANCE. Оригинальные16.1/AFU
и их ресурсы/команды/правила сохранены.

Новая особенность19: региональная ветка FUN140003790 может при ошибке чтения
заполнить пропущенные данные нулями и сохранить файл с успешным возвратом.
Collector проверяет raw stdout/stderr на exact skip/read-failed/truncation
сообщения до признания формы. Такие файлы остаются partial; одинаковый размер,
Descriptor с разрешениями и одинаковый SHA двух файлов не отменяют ошибку.
Общие проверки образа и доступа всех регионов не ослаблены.

Guard также проверяет SystemTemp/WNPDriver.sys — точный fallback FUN140018370.
Существующая служба/SYS, ошибки SCM, подписи или несовместимая идентичность
останавливают работу; collector не удаляет чужие драйверы и не меняет политики.
Linux reader не подключён. На железе помощник не выполнял даже -I.
[Точная цепочка и результаты файловых проверок](../research/fpt19-integration-20261025/REPORT.md).

## Автоматический выбор reader, версия0.1.190

Одна кнопка INFO «Снять дамп BIOS», один общий сборщик Windows:

- Фактический `AuthenticAMD` + AMI → прежний AFU5.17.00.0153 `/O`.
  Размер1–64МиБ сверяется с SMBIOS, два чтения должны полностью совпасть.
  Это `declared_rom_image`; отдельная физическая топология SPI этим не доказана.
- Фактический `GenuineIntel` → присутствующий PCI LPC/eSPI class0601 из
  SetupAPI. Единственный ID должен попасть в проверенные диапазоны таблицы
  FPT16.1.27.2181:7A00–7AFF,5180–51FF,5480–54FF. Все31пары диапазонов
  совпадают с прежним16.1.25.1871; список допущенных устройств не расширен.
  Затем собственный FPT `-I`
  должен завершиться успешно; только после этого два фиксированных `-d`.
  Подпись AMI для Intel не требуется: FPT работает с Intel SPI, а не брендом UEFI.
- Неизвестный CPU/неподходящий Intel/не-AMI AMD → сохранённый отказ до чтения.
  AFU на неподходящий Intel автоматически не подставляется.

Для GM6IR0C сохранён LPC8086:7A0C, ME16.1.30.2361, эталон32МиБ с Descriptor,
BIOS16МиБ,ME,GbE,DevExp2. Это статический допуск, не аппаратный запуск FPT.
HYDROC/YAOSHI с Ultra9 275HX не получают этот16.1 по сходству названий.
Остальные Intel13/14HX — кандидаты до фактической PnP-проверки на экземпляре.
[Список моделей/границы доказательств](../research/fpt-integration-20261025/REPORT.md).

Intel полнота: свежий Flash Descriptor, плотности1–2 компонентов, размер образа
равен сумме ёмкостей, все16 записей регионов разобраны; обязательны Descriptor,
BIOS и ME, GbE проверяется если включён. Регионы не выходят за файл, не
перекрываются и покрывают всю flash без неопределённых промежутков. BIOS
проверяется по FV/header checksum/reset jump, ME по partition header.
Для каждого включённого региона сохраняется SHA256 и FLMSTR1 host-read.
При отсутствии read permission любого включённого региона полнота отклоняется:
разобранный FPT умеет оставить FF для region9. Разрешения расширенных регионов
12–15 пока не допущены. GbE bank0 checksum записывается как наблюдение.
Две одинаковые длины/хэша без этих проверок недостаточны. Файлы не дополняются
FF/нулями и не исправляются. Только полный прошедший Intel capture получает
`physical_spi_complete=true`. Это не доказательство чтения отдельной EC flash.

Исходный FPT и подписанный embedded driver reference встроены в общий protected
runtime, с SHA pins; сеть не нужна. Подписи проверяются offline до запуска.
Существующая WNPDriver служба (даже остановленная), остаточный SYS или ошибка
проверки SCM запрещают запуск FPT: наш код чужой драйвер не останавливает/удаляет.
Только `-I`/`-d`, без unlock/reset/flash BAT. Runtime notice хранится в portable.
Полные stdout/stderr каждого процесса идут прямо в отдельные файлы без прежнего
pipe backpressure. При отмене текущая vendor-операция заканчивается; следующая
не начинается. Принудительного завершения vendor-процесса по timeout нет.

Ни приложение, ни AFU/FPT/их драйверы помощником на железе не запускались.
Linux reader остаётся недоступен; Windows EXE/SYS в нём не запускаются.
Ниже сохранена история исследования и прежнего контракта0.1.189.

## Intel AFU: отдельно проверенный UEFI-регион, версия0.1.189

Свежий GM6 из Users_logs/logs_GM6IR0C(15) успешно выполнил AFU /O(exit0),
но получил16МиБ BIOS-региона при SMBIOS32МиБ. Прямое файловое сравнение
с полными backup.fd/new.fd подтвердило тип области. До0.1.188 включительно
проверка размера останавливала сбор после первого прохода и оставляла partial.

Теперь Intel без Descriptor проходит отдельную строгую проверку UEFI-региона:
размер — степень2, не больше ожидаемого, делит размер SMBIOS; FV начинается
на0, есть минимум2 FV с корректными заголовками/checksum и reset jump в хвосте.
Проверяются два прохода, размеры, тип и SHA256. Это валидация формы/повторяемости,
а не доказательство физической ёмкости или доступности всех SPI-регионов.
Неизвестный/обрезанный/неравный результат остаётся partial с ошибкой.

Два равных результата сохраняются как bios-region.bin/bios-region-verify.bin.
Manifest schema3: state=region_verified,capture_kind=uefi_region,
region_only=true,capture_saved=true,capture_complete=false,two_passes_equal=true.
Сообщение явно отличает размер сохранённого региона от SMBIOS и говорит,
что полный SPI не получен. База региона без Descriptor не угадывается.
Для целого Intel SPI прежние проверки Descriptor/BIOS/ME/GbE и размера сохранены.
Поведение успешного AMD capture ожидаемого размера не меняется.

Оба pass SHA256 и фактические размеры сохраняются до проверки формы, также
при ошибке инструмента или несовпадении. Прогресс показывает реальные байты
двух чтений, не процент от неподтверждённого размера возвращаемой области.
Новых AFU switches, FPT backend, EC-записей, flash/unlock-команд нет.
Это исправление ещё не запускалось на Intel помощником; два свежих прохода
должен снять владелец. Первый сохранённый16МиБ файл уже проверен офлайн.

Сравнение с непатченым и разбор переменных:
[GM6 logs15](../research/gm6ir0c-logs15-20261024/REPORT.md).

## Встроенный AFU reader, версия 0.1.185

Кнопка BIOS в Windows доступна для всех фактических моделей, включая Unknown.
При нажатии проверяются реальные BIOSVendor, версия, плата, CPU vendor и размер
из SMBIOS. До подтверждения AMI внешний инструмент не запускается. Отказ тоже
сохраняется в логах. Preview и --no-ec не разрешают аппаратное чтение.
Linux не получает неподтверждённый Windows AFU backend.

Официальный AFU 5.17.00.0153 скачивается только по явному запросу дампа.
Архив с AMI CDN проверяется по SHA256; загрузка и распаковка используют общие
update-адаптеры. Файлы подготовки хранятся в settings/tools. Проверенные EXE/SYS
публикуются через общий защищённый ACL/pinning cache ProgramData. Оригинальные
бинарники AMI не добавляются в Git или release. Используется ровно режим /O.

Результат находится в logs_<плата>/bios-dumps/bios-<UTC>-<suffix>/:

- precheck.json, tool.json, независимый events.jsonl и атомарный manifest.json;
- полные pass1/2.stdout.log и stderr.log, PID, код завершения, время и хэши;
- pass1/2.partial.bin при ошибке, неполноте, отмене или несовпадении;
- bios.bin и bios-verify.bin после двух равных проходов ожидаемого размера.

Для Intel дополнительно обязательны Flash Descriptor, допустимые границы
Descriptor/BIOS/ME и непустые данные ME. Выгрузка одного BIOS-региона не считается
полным SPI. Размер SMBIOS не подменяет измерение физической ёмкости чипа.
Отдельные поля manifest указывают, что live EC flash и EC RAM не считывались;
встроенный образ EC для обновления внутри BIOS возможен.

Отмена заканчивает текущее чтение AFU и не начинает следующий проход. При
тайм-ауте процесс поставщика не убивается произвольно; сохраняются PID и partial.
Временный thread execution request удерживает автоматический сон; ручной сон
определяется по часам. Настройки защиты, BIOS/EC, FANs и лимиты не меняются.
CLI mctl --dump-bios вызывает ту же логику до открытия EC и startup restore.

Новые обычные EC-дампы и серии БП создаются в logs_<плата>/ec-dumps.
Старые dumps и bios-rom2 папки не перемещаются и не перезаписываются.
Нативный путь 0.1.185 проверен на Wujie: два одинаковых прохода по 33554432 байта,
SHA256 2870a75a8c2518199cd9c572c3cd466d9f971b41bb047edbd3dda85ec6d2aaad.
Проверка на Intel пока требует самого Intel-ноутбука.

## Разбор пользовательского запуска0.1.180,24.10.2026

В рабочей portable найден bios-rom2-20261024-134936-0: первый проход прочитал
16777216байтов, второй4098560байтов; второй целиком совпал с префиксом первого.
Завершение поdeadline совпало с записью SYSTEM SLEEP приложения17:29:41МСК.
Поэтому этот запуск не доказывает самостоятельный дефект тайм-аута/чтения.
Причина сна именно от крышки отдельно не установлена. Полного32МиБ дампа нет.

Первый проход статически распакован: найден AmdPspRomArmor3Smm с чтением

## История реализации

В0.1.179 пользователь запустил сборщик: он остановился на identity-read
FED50454, до чтения ROM; оба partial-файла остались пустыми. В0.1.180 исправлен
разбор4-байтного ACPI integer и добавлен журнал сырых ответов. Исправление
позднее пользователь запустил на ноутбуке (результат выше); помощник
приложение/сборщик не запускал.
Доступен в Windows на вкладке INFO отдельной кнопкой «Снять дамп BIOS».
Во время сбора эта же кнопка отменяет его. Смена вкладки не прерывает чтение;
выход из приложения или смена модели отменяет worker. Драйвер не устанавливается,
OEM-службы не останавливаются автоматически. Активный GCUService/AiStoneService
вызывает отказ до чтения ROM.

## Поддерживаемая конфигурация

- MECHREVO / WUJIE Series-X5SP4NAG, BIOS N.1.20MRO15.
- AMD family1Ah/model24h, сохранённый reviewed DSDT с точным SHA256.
- Родной UWACPIDriver с одним из двух просмотренных SHA256 и правильной
  привязкой ACPI/INOU0000. Неизвестный драйвер не подставляется автоматически.
- EC identity82/72/26 проверяется фиксированным чтением без ECRR fallback.
- Чужой preview, другая модель, Linux и --no-ec BIOS-чтение не включают.

## Что сохраняется

У этого Wujie сохранённый SMBIOS сообщает BIOS ROM **32МиБ**. Пока native ACPI
reader умеет читать только окно **16МиБ** FF000000..FFFFFFFF. Это частичный
доступ: кнопка не обещает полный SPI backup или прошивку EC.

В `logs_<фактическая плата>/bios-dumps/bios-rom2-<дата>-<суффикс>/`:

- `admission.json`: плата, BIOS, hash DSDT, сведения/проверенный hash драйвера,
  идентификаторы EC и размер ROM, объявленный текущим SMBIOS.
- `bios-rom2-16MiB.bin` и `bios-rom2-verify.bin`: только если оба полных прохода
  совпали побайтно и образ не состоит целиком из00/FF.
- `manifest.json`: версия MagicControl, UTC, диапазон, число сохранённых байт,
  SHA256 успешного окна, результат, отмена/ошибка, full_spi_confirmed=false.
- `acpi-responses.jsonl`: сырые запросы/ответы, длина внешнего ответа, статус
  IOCTL/Win32, адрес, время, версия, длительность и причина принятия/отказа.
  Сохраняется также при отказе первого identity-read, до admission.json.
  Первые16ответов, все identity-read, начало каждого ROM-прохода и любой отказ;
  дополнительные аппаратные запросы ради журналирования не выполняются.
  При включённом AllLogs те же записи попадают в основной лог как
  channel=bios_acpi, вложенный объект response. Отдельный JSONL сохраняется
  независимо от AllLogs; это bounded выборка, не миллионы строк на все DWORD.
- При сбое или несовпадении остаются `pass1.partial.bin`, `pass2.partial.bin`.
  Ошибки не заполняются нулями/FF, существующие папки не перезаписываются.

Прогресс относится к двум проходам. Скорость native ACPI неизвестна до первого
разрешённого запуска; чтение по DWORD может быть долгим. Предел прохода worker —
6часов, ожидание очередного ответа —60секунд, доступна отмена. Частичный результат
не считается полным BIOS. Окно не атомарно: изменения NVRAM между проходами могут
дать честное несовпадение.

Никаких write/erase/unlock/изменения ROM-ID, SPI clock/page или напряжений
в этом сборщике нет. Права открытия handle нужны протоколу существующего OEM
IOCTL; отправляется только фиксированный запрос чтения MMRD.

## Формат ACPI integer и проверка ответа

Windows ACPI_METHOD_ARGUMENT_V1_INTEGER содержит ULONG4байта. OEM SYS копирует
DataLength из ACPI-ответа, но внешне сообщает16байт — размер буфера запроса.
Поэтому внешний bytes_returned не является длиной integer. При4-байтном
ответе три последующих canary-DWORD должны остаться от входного буфера;
нулевая верхняя половина больше не обязательна. Также принимается8-байтный
zero-extended DWORD с неизменным хвостом. Размер payload определяется по форме
буфера и помечен inferred: OEM не возвращает наружу ACPI DataLength/Type.

Если весь METHOD_BUFFERED пакет остался неизменным, нельзя отличить ошибку AML
от корректного DWORD, равного запрошенному адресу. Такой ответ отклоняется как
ambiguous_unchanged_reply и сохраняется в raw-лог; дополнительных проб нет.
Неожиданный внешний размер/изменённый хвост/ошибка IOCTL также остаются отказом.
Полный output_buffer_hex включает нулевую инициализацию пользовательского
буфера; returned_output_hex ограничен числом реально заявленных байт.

Описание Microsoft:
https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/acpiioct/ns-acpiioct-_acpi_method_argument_v1

Кнопка «Снять дамп EC» сохраняет прежний диагностический сценарий EC/телеметрии,
включая доступные ранее пробы вентиляторов; это отдельный механизм.
