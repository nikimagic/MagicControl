## Общий BatteryLog и оценки EC, 21.10.2026

Актуальный контракт для всех моделей и обеих ОС: app-settings.ini содержит
BatteryLog=1 (подробный журнал и диагностическая карточка SETs) или BatteryLog=0
(подробный журнал выключен, диагностическая карточка скрыта). Если ключ отсутствует,
сохраняется прежнее включённое поведение. Настройка читается при запуске;
после ручного изменения конфига перезапустить программу. AllLogs независим:
BatteryLog=1 работает и при AllLogs=0, а BatteryLog=0 не отключает общий журнал.

logs_<реальная плата>/battery.jsonl — отдельный файл с SOC, параметрами, флагами
драйвера/ОС, available native power context и разрешёнными EC-кандидатами.
Он дописывается между запусками, использует общую bounded rotation:8MiB
и3 предыдущих сегмента. UTC, session id, elapsed_ms и общий sequence совпадают
с зеркальными строками общего журнала. Никакого второго аппаратного опроса
ради второго файла нет. Общий журнал сохраняет SOC/flow/flags/действия/события,
без полных таблиц battery_candidates и battery_power. Снимок дампа копирует
оба активных журнала с retained parts под одной блокировкой, не обрезая живые.

Windows: GetSystemPowerStatus (включая BatteryFlag/ACLineStatus/SystemStatusFlag),
политика питания и доступный raw EC context записываются на изменениях и каждом
наблюдаемом проценте независимо от 60-отсчётной серии CPU/GPU. При скрытом FANs
BatteryLog поддерживает обычный1Hz polling; блокировки команд/дампа по-прежнему
уважаются. Battery Class состояния/capabilities/technology/alert1/alert2/critical
bias и ёмкости фиксируются общим BatteryJournal. Linux пишет доступные sysfs
status/health/capacity_level/charge_type/charge_behaviour/пороги/alarm и внешние
online inputs, а скрытие вкладки не обрывает battery polling. Нет обещания
захвата переходов между опросами или при сне/выключенной программе.

Основная карточка ограничения зарядки SETs постоянно содержит три строки:
до разряда, до100% и до настроенного порога; источникEC, пометкаоценка.
Они используют общий ecBatteryTimes и те же формулы, что диагностическая
карточка, без OS fallback. Стиль контролов/шрифтов и механика scrollbar прежние.
При BatteryLog=0 недоступен только большой диагностический блок, не оценки.
Поддержка EC определяется отдельным модельным reader, не общим журналом:
где нет подтверждённого EC reader, данные не придумываются и виден прочерк.
Порог97 и прочие аппаратные команды этим изменением не менялись.

По новым логам490.3 остаётся1 и при discharge490=0E. Кандидат переименован

Базовые поля остаются общим двойным согласованным набором. Дополнительные
кандидаты читаются отдельно, не более двух пар чтений; ошибка/нестабильность
одного кандидата не обнуляет/не отменяет SOC/ток/температуру основного набора.
Нет глобального atomic snapshot: совместно читаются не все поля одновременно.
Logging и форматирование выполняются ПОСЛЕ освобождения общего EC transaction.
При выключенном AllLogs FANs не делает дополнительный candidate poll;
видимая SETs может читать свою карточку через прежний read-only API.

Новый channel battery_candidates: начальный полный SNAPSHOT, полный набор при
каждом наблюдаемом целом SOC и каждые10с; CHANGED содержит все наблюдаемые
изменения с previous/current/xor/set/cleared. Несколько изменений пакетируются
в одну запись. Unknown/paused/unstable не считаются нулём или снятием флагов.
В снимках есть design/full/remaining EC,mAh,percent/W/V/mA/C. Дельты публикуются
с частотой штатного опроса, не захватывают переходы между опросами. Подписи
driver_critical относятся к raw Battery Class flag, не Windows policy action.

Отдельное явное поручение владельца: заменить прежний нижний80 на97 для всех
Wujie верхних кнопок100/95/85/10 и их штатного replay. Новый constant —
kRequestedBatteryLowerPercent. Маска7D0.low7 сохраняетbit7; forward readback,
final confirmation и owned rollback используют тот же97, без clamp до95.
OEM reference Down допускает1..95;97 — отдельный эксперимент, не установленная
возможность firmware. Остальные модели сохраняют собственные текущие пары.

Пользователь предполагает, что7D0 задаёт порог медленной зарядки. Это пока
гипотеза: точный EC consumer не найден. В UI поле называется нейтрально
«Порог0x7D0(назначение?)»; logs пишут lower_role=unverified, не доказанный restart.
Старые упоминания80/restart ниже — история до запроса21.10. Значение97 будет
запрашиваться пользователем при следующем штатном запуске/выборе лимита;
помощник не применял его и не менял верхний10 на100. Проверка замедления
выше80 невозможна, пока выбранный верхний предел останавливает раньше.

## Проверочная сборка GM6IR0C, 20.10.2026

По явному поручению владельца добавлен отдельный экспериментальный процентный
путь Windows для точной GM6IR0C/Project25/RAM1.5. Три прежние кнопки задают
upper/restart100/80,95/80,85/80. Кодек из точного BatteryProtection2: low7
7B9 (100 кодируется0), low7 7D0 (80); старший бит каждого байта сохраняется.
Это проверка исполнения владельцем, а не подтверждённая отсечка тока.
Остальные исторические указания о недоступности процентов GM6 ниже описывают
состояние ДО этого явного эксперимента; для HYDROC их уточняет следующий отдельный проверочный путь.

NativeBatteryController использует общий EC transaction, точный SMBIOS,
ProjectID/capability и проверки OEM владельца. Сначала пишет restart80, затем
upper; читает всю пару и неизменный контекст7A6/7C3/770. Эти три контекстных
байта, WMI, UEFI, FANs, PL не записываются. При ошибке возвращаются только
попытанные собственные low7, если ОБА компонента пары ещё ours/original;
откат upper→restart сохраняет свежие bit7. Чужое значение/владелец/контекст
останавливают откат с явным unknown. Записи не выполняются при обычном чтении.
Raw0/0 не считается100%; подсветка кнопки означает прочитанную пару с restart80,
а статус сообщает: «Порог записан; остановка зарядки не проверена.»

Проверочная команда не сохраняет INI и не ставится в startup/resume replay.
В пределах этого процесса она отменяет/подавляет старый native-profile restore;
явная native-команда снимает подавление. После перезапуска обычный старый
сохранённый BatteryProtection может восстановиться: для опыта не перезапускать
программу между выбором порога и наблюдением зарядки. Исходные raw, результат,
изменение контекста и rollback пишутся в battery journal; hardware не проверялся.

Телеметрия GM6 читается отдельно read-only, только для одной достоверно
перечисленной физической батареи. Exact OEM/DSDT: cycles word4A6, design word402,
full word404. Две одинаковые пары чтений исключают разорванное слово; FFFF,
нулевые/неправдоподобные ёмкости не подменяются значениями. Windows health
сохраняется в powerStatus диагностики, UI использует доступное EC full/design.
DSDT при ISDB=1 и cycles<50 подставляет design вместо full в _BIF: Windows100%
при EC5200/4300 не означает отсутствие износа. Это оценка ёмкости, не химический
анализ батареи. Зарядка Вт/AC берутся из Windows. 7CC/7CD/7CE=0 не доказывает
отсутствие AC и не превращается в USB-C65Вт. Не подтверждённый рейтинг49F и
PMAX/PBSS/PSRC/DTTF сохраняются только raw в диагностике.

## Штатные профили GM6IR0C и HYDROC-16 G2 (19.10.2026)

Уточнение владельца20.10.2026 отменяет подстановку названий
Производительность / Баланс / Здоровье в карточку SETs. Эталон Wujie — единые
заголовок «Батарея · верхний предел зарядки», кнопки100%/95%/85%, геометрия,
скролл и ряд питания/циклов/здоровья. GM6/HYDROC не имеют подтверждённого
percentage API: эти кнопки отключены и не имеют applied highlight. Обработчик
процентной команды дополнительно отклоняет native-only backend, не вызывает
NativeBatteryController::set(mode) по индексу процентной кнопки. Строка порта
Wujie сохраняет прежний EC-статус. Доступный ранее внутренний Native API и
его отдельные сохранённые BatteryProtection-настройки не переименованы в проценты.
Общий API `NativeBatteryController::set(BatteryProtectionMode)` принимает
только0/1/2 и пишет только `0x7A6 & 0x30` значениями00/10/20. Использует точную
identity соответствующей платы, проверку возможностей/занятости OEM и общий
межпроцессный transaction gate. HYDROC дополнительно требует ProjectID26,
RAM1.5 capability, точный ACPI\INOU0000/UWACPIDriver и проверенный SHA256 SYS
11.2.18.347. Батарейный транспорт разрешает только запись7A6.4–5; универсальный
EC writer не включён. Дамп RAM использует отдельный read-only backend;
отдельный factory-only FAN adapter не расширяет батарейный allowlist.
Readback подтверждает выбранные биты; не обещает конкретный процент остановки.
При ошибке сохранения/подтверждения общий API пытается откатить только свои биты,
если они ещё принадлежат операции. Результат отката включается и в exception:
already original/no-op, verified restore либо rollback unknown/ownership lost;
последние два исхода не скрываются только в журнале и не обещают restoration.

Только успешное явное действие сохраняет `BatteryProtection=0/1/2` в

обычный опрос/открытие карточки не восстанавливает его. При занятом OEM restore
сообщает ошибку и не перезаписывает его настройки. На выходе сброса нет.
FANs, PL, `7B9/7D0`, WMI и UEFI этот API не меняет. Linux использует тот же
общий процентный набор подписей и не вызывает Native API из этих кнопок.

## Поля

| Поле | Смысл и правила |
|---|---|
| EC `0x7B9`, маска `0x7F` | Текущий процент. 0 означает 100%; старший бит сохранять |
| EC `0x7B9`, бит 7 | Признак достижения порога в эталоне; вручную не выставлять |
| WMI `0x87F` | Хранимый процент через `AcpiTest_MULong.GetSetULong` |
| EC `0x7C3` | Платформа выполнения ограничения; на проверенной конфигурации 7 → 4 |
| EC `0x770` | ROM ID; для перехода 7 → 4 требуется `0xFF`; только чтение |
| EC `0x742`, бит 2 (`0x04`) | Признак включения в эталоне; только чтение |
| EC `0x7A6`, биты 4–5 | Отдельный профиль защиты по напряжению; текущий battery API не пишет |
| EC `0x7D0` | Нижний порог возобновления: маска `0x7F`, фиксированно 80%; бит 7 сохраняется |

**WMI `0x87F` не заменять записью того же адреса обычным EC IOCTL.**
При WMI-записи сохранять соседний байт слова и биты вне маски. Штатная маска
порога `0x7F`, в том числе при откате. Текущий status bit7 и соседний байт
сохраняются; полный старый0xFF snapshot не проигрывается обратно.

## Применение

**Подтверждённый побочный эффект 16.10.2026:** при Office от батареи платформа 4
даёт SMU Fast/Slow/STAPM 45/40/40 вместо 30/25/25 при платформе 7. Результат
повторён 4→7→4→7→4; флаги и таблицы FANs сохранились. От USB-C 65 Вт различий
между 4/7 для Office/Balanced/Turbo не обнаружено. `0x7C3` нельзя считать
исключительно батарейным. Исходное значение 4 после теста восстановлено;
текущая согласованная политика: 100/95/85%=4, Авто=7. Данные:
`research/test_util/analysis/battery-platform-smu-20261016/REPORT.md`.

Дополнение: все три штатных режима на батарее при 7C3=4 дают Fast/Slow/STAPM
45/40/40; при 7C3=7: Office 30/25/25, Balanced 40/35/35, Turbo 60/54/54.
Manual 25/20/15 сохранил задание при обеих платформах и источниках.
Полная сводка: `research/test_util/analysis/battery-platform-smu-20261016/ALL-MODES.md`.

На 100 Вт эффект также подтверждён: платформа 4 даёт Fast/Slow/STAPM
Office 35/30/30, Balanced и Turbo 55/50/50; платформа 7 — Office 30/25/25,
Balanced 50/45/45, Turbo 70/65/65. Вывод «AC не зависит от платформы» верен
только для проверенного блока 65 Вт. Полный отчёт:
`research/test_util/analysis/charger-rating-smu-20261016/REPORT.md`.

1. Принимать 100%, 95%, 85% и отдельный Авто (100%, automatic=true). Проверять доступ к записи и identity платы.
2. Читать исходные процент, платформу, ROM ID, флаг включения и WMI-порог.
3. Неизвестную платформу или невалидную сохранённую запись отклонять до записей.
4. До первого перехода 7 → 4 атомарно сохранять исходную платформу в
   `battery-enforcement-platform.txt`. Формат: `82/72/26 7 4`.
5. Записать изменившийся процент в `0x7B9`. Для 100% использовать ноль.
   Записать нижний порог 80 в `0x7D0 & 0x7F`, сохраняя старший бит.
6. Сохранить через WMI и проверить чтением. При отсутствующем флаге включения
   повторить WMI-сохранение выбранного ограничения, даже если число совпадает.
7. Для 100%/95%/85% выбрать платформу 4; только для Авто — 7. Проверить исходную платформу 4/7 и ROM ID=FF до записей. Другие платформы отклонить.
8. Подтвердить верхний процент, нижний порог 80%, платформу, ROM ID и включение тремя чтениями.
   Максимальное ожидание 10 секунд; пауза 25 мс при совпадении, 250 мс иначе.

От батареи отсутствующий флаг допускается как ожидание подключения зарядки:
`pending_on_battery=true`. Интерфейс не должен выдавать этот статус за включение
или физическую остановку. Флаг включения и достижение порога — разные признаки.

## Отключение и ошибки

По запросу пользователя код записывает нижний порог **80%** с любым верхним
пределом: 85%, 95%, 100%. Назначение: начать заряд ниже 80%, продолжать до
выбранного верхнего предела. Это гистерезис, а не остановка заряда на 80%.
Отдельного контрола на карточке нет. Физический цикл старта ещё не проверен.
Пользователь сообщает, что заряд начнётся уже при 84%; поэтому не считать
гистерезис работающим только по readback 7D0=80.

Матрица с физическим потоком батареи 16.10.2026: около отображаемых 85% от
100 Вт во всех Office/Balanced/Turbo/Manual при платформе 4 заряд=0 Вт,
при 7 заряд≈35 Вт. 742:26→22, 7B9:D5→55, пороги 85/80 неизменны.
Источник — native Battery Class IOCTL. Без кабеля при обоих значениях разряд.
Данные: `research/test_util/analysis/platform-charge85-matrix-20261016/REPORT.md`.

По последнему запросу пользователя 17.10.2026: **100%, 95% и 85% выбирают 4**.
Добавлена отдельная четвёртая кнопка **Авто**, она выбирает **7**, верхний процент
при этом 100% (ноль в 7B9 и WMI). Нижний порог 80 остаётся записанным; его
исполнение при платформе 7 не подтверждено. В Авто требуется снятие 742.2;
у 100%/платформа4 флаг может быть как установлен, так и сброшен.
`applyBatteryChargeLimit(ec, percent, automatic=false)` задаёт 4; только явный
`automatic=true` задаёт 7 и допустим с percent=100. Проверки и откат общие.
`ChargeAuto=0/1` хранится отдельно от `ChargeLimit` в device-settings.ini.
ChargeLimit хранит последний явный пресет даже при ChargeAuto=1. При восстановлении
для Авто API получает percent=100, иначе сохранённый ChargeLimit. Старый файл без ChargeAuto
трактует сохранённые 100% как новую кнопку 100%/4, а не как Авто.
Авто — переключатель: при включении actual=100%/7, подсвечены Авто И 100%,
остальные процентные кнопки погашены. Сохранённый ChargeLimit не меняется.
Повторное нажатие Авто выключает его и применяет/подсвечивает последний явный
пресет (платформа4). Явное нажатие 100/95/85 также выключает Авто и сохраняет
новый процент. UI/трей определяют Auto по actual upper100 + platform7; одно
число100 без платформы недостаточно. Сохранение — только после успешного API.
FANs при выборе не переприменять; не писать APU overrides из battery API.

Наблюдение пользователя: при Авто/7 на батарее ниже 70% возникает потолок 15 Вт,
при 72% доступно больше. Это ещё не установленный точный порог или доказанная
зависимость только от процента (возможны напряжение/ток); не считать имя Авто
разрешением динамически менять платформу программой.

При ошибке попытаться вернуть изменённые платформу, WMI-порог и текущий порог.
Каждое поле возвращается только если попытка записи относилась к этой операции:
current==original — no-op; current==attempted — возврат собственной маски;
третье значение или неизвестное чтение — отказ от записи чужого поля.
Живые upper/lower и platform сравниваются под короткими EC transactions;
WMI read/compare/masked write/readback используют тот же общий gate на попытку,
не удерживая его на всё10-секундное ожидание активации. Online FANs не останавливаются.
ROM/platform context проверяется перед каждым возвращаемым полем.
Ошибки отката объединяются в журнале и exception с явным неизвестным actual state.
Созданный platform pin удаляется лишь после успешного возврата всех собственных
полей и проверки его содержимого; при ошибке/неопределённости остаётся для разбора.
Не сбрасывать другие настройки EC и не отправлять повторную WMI activation,
если хранимое значение уже исходное.

## Запуск, сон, гибернация

Выбор в `SettingsPage.cpp` и восстановление в `ConfigurationRestoreWindows.cpp`
используют один battery API. **Совпадения числа в `0x7B9` недостаточно:**
проверять также сохранение WMI и включение. Проверять сохранённый выбор при
запуске и после сна/гибернации. Открытие вкладки и обычное обновление UI только
читают состояние и не активируют ограничение заново.

## Не затрагивать FANs

Механизм батареи не выбирает режим вентиляторов, не приобретает их владение,
не останавливает OEM-сервис и не переприменяет кривые. Не добавлять сюда вызовы
`FanController`, `restoreSavedProfiles`, Default/Max/Manual или расчёт PWM.

Аппаратные записи батареи: **EC `0x7B9`, EC `0x7D0`, WMI `0x87F`, при необходимости EC `0x7C3`**.
Не писать флаги FANs `0x726`, `0x727`, `0x741`, `0x751`, `0x7C5`, `0x7C6`,
вентиляторные таблицы и PWM. EC/WMI-вызовы сериализовать общим механизмом доступа,
но не удерживать общий mutex на всё ожидание флага: online-контроллер продолжает работу.

## Журнал и проверка результата

Канал `battery`: `LIMIT begin`, `LIMIT confirmed`, `LIMIT failed`, ошибки отката.
Поля: `percent`, `platform`, `gate`, `enabled`, `stored`, `pending_on_battery`,
`reached`. `fan writes=0` описывает именно путь батареи; независимый online-контроллер
может продолжать писать PWM. Power diagnostics читает также `0x742`, `0x7C3`,
`0x770`, `0x7A6`.

Физическую остановку проверять по времени, выбранному пределу, проценту батареи,
внешнему питанию и мощности зарядки. Цвет надписи, число порога или один флаг
не заменяют проверку прекращения существенного положительного потока в батарею.

Красное «Потребление» — EC `0x44C`; физический смысл и масштаб ещё не установлены
окончательно. Не подменять им мощность батареи и не считать доказанным расходом
только ноутбука без зарядки.

По запросу пользователя подвал показывает расчёт: при `Charging` из EC `0x44C`
вычитается положительная мощность зарядки из того же снимка батареи. Без зарядки
отображается EC без вычитания. Разряд не прибавляется. Отрицательная разность
на переходах ограничивается нулём; неизвестная мощность при зарядке даёт прочерк.
В журнале `system_power_watts` остаётся исходным EC, а `system_consumption_watts`
содержит вычисленное показание подвала. Это расчёт, не новый аппаратный датчик;
не использовать его для управления питанием, зарядкой или вентиляторами.

Не запускать аппаратные тесты и не менять EC ради чтения инструкции.
Не добавлять/запускать тесты без запроса пользователя. При правках обновлять
этот документ, отделяя реализацию от подтверждённого поведения на устройстве.

## Текущее размещение управления — APU в SETs (17.10.2026)

В шапке карточки APU находится пара Выкл./Вкл. От батареи подпись Limiter EC
синим; от сети Turbo EC красным. На KEYs этого переключателя нет.
В трее он находится в подменю мощности. Смена питания меняет название/цвет,
не пишет EC автоматически. Оба интерфейса используют setBatteryAutomatic:
Вкл. — platform7/upper100, Выкл. — platform4/последний явный процент.
ChargeAuto хранит состояние переключателя, ChargeLimit — последний явный пресет.
При включении подсвечены Вкл. и батарейный100%; при выключении возвращается
сохранённый100/95/85%. Доступен и в Default FANs: это отдельная политика EC,
в отличие от недоступных в Default ручных ватт-лимитов APU.
Названия не означают новый SMU setter. Кривые и флаги FANs не переприменять.

## Удалённый эксперимент приоритета питания (17.10.2026)

По запросу пользователя блок «Приоритет питания / Батарея / Сеть» удалён из SETs,
включая неиспользуемый обработчик записи 7CC.7. Поддержка команды на этой плате
не была подтверждена. В батарейной карточке остаётся строка порта зарядки на
полную ширину; лишняя высота убрана. Чтение Type-C для определения порта/рейтинга
сохранено. Переключатель платформы4/7 на APU — отдельная функция и не удалён.

На месте удалённого «Приоритета питания» SETs показывает текущую Зарядку/Разряд
в ваттах справа от порта, зелёным/красным как FANs. Формат общий batteryCard,
источник тот же Windows Battery Class IOCTL (MonitoringReader::readBatteryOnly).
Обновляется фоновым опросом SETs раз в3 секунды, без записей EC/повторного полного
опроса CPU/GPU/дисков. От сети без заряда — нейтральное «От сети 0,0 Вт»;
нет числовых данных — прочерк. Цифры — мощность батареи, не общее потребление.

В той же строке добавлены «Циклов» и «Здоровье». Циклы — тот же EC счётчик,
что на FANs, с резервом Battery Class. readBatteryOnly читает только батарею:
Battery IOCTL + проверенные EC battery metadata, не весь мониторинг.
Здоровье = FullChargedCapacity / DesignedCapacity * 100 из BATTERY_INFORMATION;
это оценка по данным контроллера, не текущий процент заряда. Оба значения должны
быть известны и ненулевые; иначе прочерк. Не обрезать показание выше100%.
Данные сохраняются при единичном пропуске чтения; подтверждённое отсутствие
батареи очищает их. Увеличение карточки/изменение скролла не требуется.

Последнее уточнение SETs: значение разряда скрыто; зарядка, циклы и здоровье
остаются. FANs и сбор телеметрии разряда не изменены.

## Диагностика температуры,18.10.2026

Общий BatteryTemperature IOCTL декодируется как0.1K; raw0/FFFFFFFF и значения
вне-40…100°C отвергаются. Лог power sample сохраняет raw, источник и Win32 status
даже при отсутствии температуры. Сохранение прошлого значения явно отмечается
в status и сохраняет его источник. EC fallback температуры остаётся только у
подтверждённого X5SP4NAG; на GM6IR0C нельзя переносить эти регистры.
В пользовательском логе0.1.50 GM6IR0C температура null во всех41samples,
а точной ошибки прежний формат не содержал. Это не доказательство отсутствия
датчика. Пока подтверждённого альтернативного источника GM6IR0C нет.

## GM6 круглый разъём, уточнение владельца20.10.2026

Владелец подтвердил физическое подключение GM6 к круглому DC. Exact GM6
MyEcCtrl отдельно подтверждает7CC&1 и7CC&36, но присланный raw7CC=0 при
WindowsAC=true не позволяет называть DC активным по данным EC.
Общий getter читает и этот raw; положительные native flags имеют приоритет.
При подтверждённом свежем WindowsAC и неизвестных EC flags общая строка
пишет «Разъём питания: DC (круглый разъём)»: это известный тип разъёма данной
конфигурации, не «EC подтвердил порт». Отсутствие питания/stale не показывают
этот fallback. Номер Type-C и рейтинг7CD/7CE для GM6 не перенесены с HYDROC.
Физическую нумерацию/ваттность круглого адаптера программа не угадывает.

## Сбор трёх состояний БП по кнопке дампа,20.10.2026

Фактические GM6/HYDROC обеих ОС получают выбор «Обычный дамп» / «Проверка БП»
в существующем диалоге. Геометрия карточек/скроллбар не меняются. Сценарий
PowerInputDump общий, GUI только показывает шаги/подтверждения на4языках.
Порядок: 1)без внешнего питания;2)положительная зарядка через круглый БП;
3)полный заряд100% с почти нулевой мощностью батареи. Такой порядок не требует
повторного discharge после полного заряда. Питание USB-C просим отключить;
физический разъём подтверждается инструкцией владельцу, не угадывается изAC.

Перед каждой попыткой read-only изолированный provider с deadline10с проверяет
одну физическую батарею/свежие OS-данные. Этап1: online=false независимо от
исследуемых charging bits. Этап2: online=true,flow=charging,watts>0.1.
Этап3: online=true,percent>=99.5,abs(watts)<=0.05 независимо от flow flags.
Ошибочные/unknown/stale/несколько батарей не подставляются под нужное состояние.
Затем обычный DiagnosticDumpMode::ReadOnly собирает полный EC/firmware и
минимум60сек телеметрии. Не вызываются Default/Max/factory или setter батареи;
нагрузка для разрядки не запускается. Независимые фоновые контроллеры приложения
работают как прежде, scenario_hardware_writes=false не означает остановку всегоEC.

В fast JSONL добавлен полный raw battery object+flow для каждого наблюдения;
trailing whitespace удаляется, JSONL остаётся однострочным. Валидатор требует
>=3matching samples/span>=60000мс и ни одного несовпадения, а не одного правильного
кадра. Это проверка маркеров ОС, не доказательство физическогоDC/MUX или cutoff.
Raw EC snapshot не атомарный; состоянием он охвачен до и после чтения, но
не объявляется непрерывным осциллографическим измерением во время каждогоECбайта.

Папка logs_<board>/dumps/power-input-<time>-N содержит session JSON, README,
preflight-N.json и подпапки01-unplugged/02-charging-on-dc/03-full-on-dc с обычными
дампами/неверными попытками. power-input-validation.json объясняет принятие;
power-input-registers.json содержит только raw/valid исходных EC-байтов,
включая43C/432/434/49F/7CC/7CD/7CE/7B9/7D0 и BMS4A2/4A4/4A6/4AB.
ДляHYDROC4xx — same-offset кандидаты без собственногоAML, не декодированные
температура/ток. Полнота состояний ОС иEC записана раздельно; недоступныйLinux
EC не становится доступным из-за мастера. Передавать всю папку серии.

«Отложить» сохраняет прогресс в памяти UI и пакет на диске. Следующее нажатие
дампа с выбором проверкиБП продолжает этот этап в том же процессе/профиле.
После выхода или смены preview-профиля создаётся новая серия, прежние файлы
не удаляются. Никаких автоматически восстановленных черездругойкомпьютер
процентов/флагов. Cancellation stop-aware; между подсказками нетEC/device mutex.
Windows abandon-job сбрасывает указательsession, чтобы новая серия не делила
mutableprogress с ещё завершающимсяworker. GTK GDK displays снимаются наUI
для каждого принятого этапа; backgroundне вызываетGDK.
