## 1. P1 — отсутствует согласованное восстановление Manual после сна

Места:

- [Обработчик питания](C:/Users/admin/Documents/mechrevo_dsh/MagicControl/src/gui/windows/MainWindow.cpp:408)
- [Защита от активации оставленной RAM-таблицы](C:/Users/admin/Documents/mechrevo_dsh/MagicControl/src/platform/windows/FanControlWindows.cpp:275)
- [Остановка при внешнем изменении](C:/Users/admin/Documents/mechrevo_dsh/MagicControl/src/platform/windows/FanControlWindows.cpp:512)
- [Сброс состояния контроллера](C:/Users/admin/Documents/mechrevo_dsh/MagicControl/src/platform/windows/FanControlWindows.cpp:548)

GUI обрабатывает пробуждение только запросом `restoreApplicationPresence()`. Отдельных состояний suspend/resume, сохранённого намерения пользователя и восстановления кривых нет. Если при переходе питания EC сбросил `0x741.0`, но сохранил `0x7C6.2`, восстановление presence правильно откладывается: включать оставленную RAM-таблицу без её владельца нельзя. Однако владелец затем воспринимает ситуацию как постороннее изменение, прекращает пересчёт и освобождает владение.

**Воспроизведение:** применить связанную Manual-кривую, сбросить в имитаторе только `0x741.0`, отправить запрос восстановления после пробуждения. Получено:

```text
owned=0 error=1 needsRestore=0 controlled=0,0 app=00 ram=04
```

RAM-режим остаётся отмеченным включённым, программного пересчёта уже нет, обязательного восстановления интерфейс не требует. Нового автоматического восстановления не происходит. Это подтверждает дефект обработки потери управления; фактическое поведение вентиляторов конкретной прошивки после сна этим тестом не устанавливается.

В эталоне `Form1.FanPower.cs` и `EcFanCurveController.cs` есть приостановка работы, эпоха питания, сохранение применённого намерения и согласованное восстановление.

**Исправление:** перенести этот жизненный цикл. Восстанавливать только собственное подтверждённое управление, после проверки платы, свежих температур и состояния EC. Сохранить защиту от чужой оставленной таблицы.

## 2. P2 — изменение профиля Office → Turbo не замечается активным Manual

Место: [маски контроля владения](C:/Users/admin/Documents/mechrevo_dsh/MagicControl/src/platform/windows/FanControlWindows.cpp:30).

Для `0x751` проверяется только Fan Boost `0x40`; поле профиля `0x90` игнорируется. Поэтому внешняя смена `0xA0 → 0x10` не считается изменением режима: Manual продолжает работать, сохранив прежнюю сессию. Выбранный Office при этом уже не действует. Пассивное обновление SETs может показать новый профиль, но контроллер не обрабатывает потерю выбранного режима.

**Воспроизведение:** после подтверждённого Manual заменить в имитаторе `0x751=0xA0` на `0x10`. После следующего цикла:

```text
owned=1 error=0 controlled=1,1 mode=10
```

В эталонном `MatchesFanSetting(0x751)` проверяются допустимость программного управления и совпадение профиля.

**Исправление:** включить поле профиля в контроль. Различать намеренный выбор пользователя, переключение OEM и переход питания. Обрабатывать изменение явно; бесконечно перезаписывать чужой профиль нельзя.

## 3. P2 — запись поля регистра проверяется как запись всего байта

Место: [локальный помощник записи](C:/Users/admin/Documents/mechrevo_dsh/MagicControl/src/platform/windows/FanControlWindows.cpp:214).

Помощник принимает маску и собирает байт через read-modify-write, но затем вызывает `writeVerified(address, wanted)`. Этот метод сравнивает весь байт и до трёх раз повторно записывает прежнее значение. Изменение другого бита прошивкой вызывает ложную ошибку и повторную запись посторонних битов.

**Воспроизведение:** при установке `0x726.7` имитатор прошивки устанавливает другой бит, `0x726.1`. Требуемый бит применён, но контроллер сообщает:

```text
EC 0x726 did not confirm the write: requested 0x80, read back 0x82
owned=0 error=1 needsRestore=0 shared=82 ram=00
```

Кроме ложного отказа, обработчик ошибки видит уже изменённое собственное поле при старом `expected` и может классифицировать свою незавершённую операцию как внешнее вмешательство. Тогда нормализация режима пропускается.

**Исправление:** для неполной маски использовать `updateBitsVerified`, проверять принадлежащие операции биты и обновлять ожидаемое состояние по результату. Полную проверку байта оставить для целиком принадлежащих приложению ячеек таблиц.

## 4. P2 — кнопка подсветки сбрасывает Manual вентиляторов

Место: [SettingsPage::writeNative](C:/Users/admin/Documents/mechrevo_dsh/MagicControl/src/gui/windows/SettingsPage.cpp:687).

Кнопка «Штатный режим» размещена в карточке подсветки, но сначала вызывает `controller->nativeAndWait()`, возвращая оба вентилятора в Default, и лишь затем устанавливает цвет и яркость. Это скрытый побочный эффект действия с подсветкой.

**Воспроизведение:** включить Manual на имитаторе, нажать настоящую кнопку `150` в скрытом тестовом SETs. Получено:

```text
owned=0 error=0 controlled=0,0 ram=00
message=Штатный режим CPU/GPU подтверждён EC.
```

**Исправление:** действие в карточке подсветки должно управлять подсветкой. Если требуется общий сброс, вынести его в отдельное действие с явным описанием затрагиваемых настроек.

## 5. P2 — в Linux используется уже уничтоженная подпись кнопки

Отдельный GTK-тест с weak pointer подтвердил уничтожение после отсоединения:

```text

```

**Исправление:** удерживать ссылку на время переноса либо создать новую подпись. После передачи новому контейнеру освободить временную ссылку.

## 6. P2 — отсутствует запрос разрешения для Wi-Fi/Bluetooth

Место: [setRadio](C:/Users/admin/Documents/mechrevo_dsh/MagicControl/src/platform/windows/WindowsDevices.cpp:146).

Код перечисляет устройства и сразу вызывает `SetStateAsync`. `Radio.RequestAccessAsync()` отсутствует во всём пути. Чтение состояния может работать, а изменение — отклоняться Windows, особенно при первом использовании или изменении политики доступа. Эталонный `Set3WindowsDevices.cs` запрашивает доступ перед изменением.

Контракт подтверждён [документацией Microsoft](https://learn.microsoft.com/en-us/uwp/api/windows.devices.radios.radio.requestaccessasync?view=winrt-26100): чтение разрешения не требует; изменение требует. Запрос может вызвать диалог согласия, поэтому его нужно выполнять из подходящего пользовательского контекста и сохранять результат на сессию.

**Исправление:** запрос доступа при явном действии пользователя, обработка Allowed/отказа, затем изменение и проверка результата. Физическое отключение радиоустройств при ревизии не выполнялось.

## 7. P2 — команда CLI mode обходит общую логику выбора профиля

Место: [commandMode](C:/Users/admin/Documents/mechrevo_dsh/MagicControl/src/cli/main.cpp:436).

`mode ... --yes` вызывает общую побайтовую запись `commandWrite` для `0x751`. GUI использует `selectEcPerformance` и согласование с владельцем вентиляторов. В CLI не сбрасываются пользовательские переопределения `0x783–0x785`, не выполняется согласование с активными Manual/Max и не приобретается их mutex владения.

**Следствие:** при ненулевых переопределениях CLI сообщает выбранный Office, но сохраняет другие лимиты. Во время работы GUI команда может изменить режим его активного контроллера. Mutex транзакций предотвращает перемешивание отдельных операций, но не даёт право менять чужую сессию управления.

**Исправление:** проводить команду выбора профиля через общий сценарий и владение. При активном GUI передавать ему запрос либо явно отказывать. Низкоуровневый `reg ... --yes` может оставаться отдельной диагностической командой; его намеренная запись байта сама по себе здесь не считается дефектом.

- В просмотренных путях закрытия фоновые потоки GUI присоединяются; BIOS-задача удерживает отдельный объект результата. Нового подтверждённого дефекта времени жизни там не найдено.

| Отдельный GTK-тест | Подтверждено уничтожение заимствованной подписи |

Первый запуск тестов профилей в стандартной временной папке завершился ошибкой доступа; повторная проверка подтвердила `create_directory: Access is denied` для `%TEMP%/magiccontrol-fan-presets-*`. С `MAGICCONTROL_TEST_TMP` внутри рабочей папки прошли все проверки. Производственный механизм сохранения профилей по этому сбою дефектным не объявляется.

Проверочные исходники и вывод находятся в `build/review-harness/`; это временные материалы ревизии, не поставляемая утилита. В сборке есть предупреждение C4458 о затенении `message` в `OsdModel.h`; оно не объясняет обнаруженные функциональные дефекты.

## Границы проверки и порядок исправления

Реальный сон/пробуждение, нагрузка при ≥85 °C, включение Wi-Fi/Bluetooth и независимый Manual одного вентилятора аппаратно заново не испытывались. Влияние пустой RAM-таблицы второго канала при независимом управлении требует отдельной проверки точной прошивки; данных для объявления этого подтверждённой ошибкой нет. Значения EC-лимитов не доказывают фактически применённые лимиты SMU и не запрещают Windows повышать частоту внутри разрешённой мощности.

Рекомендуемый порядок: **согласованные suspend/resume → проверка профиля и записи по маскам → отделение сброса подсветки от вентиляторов → исправление GTK → разрешения радиоустройств → общий путь CLI**. Для каждого исправления добавить регрессионную проверку соответствующего сценария; затем отдельно проверить сон и переходы AC/DC на ноутбуке.
