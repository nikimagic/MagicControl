# Версии и обновление MagicControl

## Проверенная очистка старых staging-папок, 06.11.2026

`Tools/Package-Releases.py --prune-verified-staging preview` проверяет старые
распакованные релизы; `--prune-verified-staging apply` удаляет только прошедшие
ту же проверку папки. ZIP/TAR, `SHA256SUMS.txt`, текущая версия и шаблоны
`0.1.0`, если они существуют, остаются на месте. Перед удалением проверяются SHA архива, состав и байты
всех файлов, отсутствие ссылок, личных настроек, журналов и дампов. Изменившаяся
или непроверенная папка пропускается. Отчёт — `build/release-staging-cleanup.csv`.

## Запуск после замены файлов, 02.11.2026

На восстановлении Downloads 0.1.452 → 0.1.460 все файлы прошли SHA-проверку,
но helper остался на строке `Start-Process` запуска нового EXE. Это подтверждено
живым стеком `Runspace.Debugger.GetCallStack()`; наличие процесса SmartScreen
само по себе не доказывает причину ожидания. Ручной запуск 0.1.460 из того же
каталога подтверждён launch-handoff и новой сессией журнала.

Общий adapter запускает проверенный EXE через `ProcessStartInfo` с
`UseShellExecute=false`, как существующий native launch в ядре. Helper уже
наследует административный токен MagicControl. Один этот запуск используется
после установки и rollback; дополнительный shell/новый UAC не требуется.
Проверки Windows, подписи и Zone.Identifier не меняются. В update-result.txt
отдельно публикуются стадии проверки, запуска и очистки; успех — после очистки.

## File.Replace в Windows PowerShell, 02.11.2026

Общий Windows script adapter передаёт `[NullString]::Value` третьим аргументом
File.Replace. В Windows PowerShell5.1 обычный `$null` превращался в пустую
строку backup path и вызывал «Путь имеет недопустимую форму» при первой замене.
Тем же helper пользовался rollback, поэтому повторная попытка возврата также
завершалась ошибкой; старая версия могла снова запуститься с сообщением о
неполном восстановлении. Подтверждено на файловой пробе с обычными txt-файлами:
старый вызов падает, исправленный атомарно заменяет и возвращает содержимое.
Проверки пакета/масок preserve, backup, SHA и штатного выхода сохранены.

Исправление встроено в обновляемый EXE; уже установленный старый EXE продолжает
запускать свой старый script adapter. Для первой установки исправленной сборки
требуется ручное восстановление либо запуск исправленного adapter по проверенному
плану; один новый ZIP сам по себе встроенный старый скрипт не исправляет.

## Единая корневая папка архивов, 02.11.2026

Оба архива сохраняют версию и ОС в имени файла, но внутри содержат единственную
корневую папку `MagicControl/`, включая пустую `magiccontrol-update/`. Общий
упаковщик проверяет состав, байты файлов, корень и пустоту каталога. Апдейтер
новой сборки принимает `MagicControl` и старый `MagicControl-...`, сохраняя
проверки версии, платформы, SHA и единственного корня для GitHub и local ZIP.
Уже установленные версии до этого изменения принимают только длинный корень;
первый переход на новый формат требует ручного обновления из архива.

Ниже — история изменений конкретных версий. Текущие архитектурные контракты
INFO/KEYs: [PROJECT-MAP](PROJECT-MAP.md), [KEYS-PERSISTENCE](KEYS-PERSISTENCE.md)
и AGENTS.md. В INFO/KEYs после0.1.400 нет GUI workers/очередей и Copilot hook fallback;
исторические записи про software fallback или старые пути не являются
разрешением вернуть их в действующий код.

## Видимые служебные папки,02.11.2026

Новые служебные каталоги — `magiccontrol-update`, `magiccontrol-install`
(старый install-каталог, в текущем коде не создаётся) и `locks`, без ведущей
точки на Windows и Linux. Package-Releases включает ПУСТОЙ каталог
`magiccontrol-update/` в каждый Windows ZIP и Linux tar.gz явной записью;
проверяет наличие и отсутствие содержимого. Заглушек .keep/README внутри нет.
При обычном запуске папка обновлений заранее не создаётся.

Все новые staging/local ZIP/GitHub update пути используют видимый каталог.
Старый `.magiccontrol-update` читается только для совместимости с ранее
положенным архивом или незавершённой установкой; новые stage туда не пишутся.
Cleanup receipts для двух имён разделены. Успешная установка очищает только
проверенный каталог транзакции; при ошибке backup сохраняется.

Новые logger/inventory/publish/update leases используют `locks/`. Если старая
`.locks/` уже существует, берётся также legacy lease того же имени — для
совместимости с ещё работающими старыми процессами. Старая папка не создаётся.
Занятые lock-файлы не удаляются и не переименовываются во время работы.

## Очистка после успешного обновления,01.11.2026

Windows GitHub/local ZIP использует один одноразовый PowerShell script adapter.
Ядро проверяет пакет и формирует install-plan.json только из неперсистентных
файлов manifest. Script встроен в EXE, копируется в stage и полностью читается
в память перед вызовом, поэтому может удалить свой файл. Копия большого
MagicControl.Update.exe больше не создаётся. Старый --apply-update entry для
ручных/SSH adapters направляется в тот же план/script, без второго Win writer.

Script ждёт штатного выхода приложения, повторно сверяет пакет/план/версию,
сохраняет backup, атомарно заменяет файлы, проверяет установленные SHA и запускает
новый MagicControl. После успешного запуска очищает cache и завершает работу.
До окончания скрипта success-result не публикуется; исключён одновременный
legacy-cleanup новой программы. Ошибка до запуска выполняет rollback и оставляет
backup. Ошибка cleanup после запуска не откатывает уже работающую новую версию.

Linux сохраняет существующий typed --apply-update/helper; новый normal startup
до GUI/hardware завершает cleanup. Такой startup также поддерживает первый
Windows переход со старого EXE-helper без стадии очистки. Проверяются success,
версия, совпадение финального installed/package manifest и SHA256 payload;
settings/INI/CSV/логи не сравниваются с чистыми шаблонами.

Новая программа ждёт завершения helper без kill. Общая файловая lease находится
в стабильном `locks/update-transaction.lock`, вне очищаемого каталога. После
подтверждения установки удаляется ВСЁ содержимое `magiccontrol-update`:
архивы, исходный локальный ZIP/TAR, распаковки, старые backup, временные EXE,
скрипты и отчёты, ранее оставленные в этом служебном каталоге. Сам каталог
остаётся пустым. После успеха он не предназначен для хранения личных файлов.

Для продолжения прерванной очистки до первого удаления атомарно сохраняется
малый receipt в `locks/update-cleanup.json` с версией/хэшем installed manifest.
После очистки receipt удаляется; стабильные lock-файлы не удаляются. Ошибка
установки/частичный payload не допускают cleanup и сохраняют rollback. Сбой
самой очистки не откатывает новую версию; сохраняет pending receipt и сообщение
в update-result.txt, повтор возможен при следующем обычном запуске.

Рекурсия проверяет абсолютную разрешённую границу папки до удаления. Symlink/
Windows reparse point удаляется как ссылка, без обхода его содержимого. Личные
settings, logs/dumps и другие файлы вне `magiccontrol-update` не очищаются.
Основной EXE не удаляет себя; временный Windows helper удаляется после его выхода.
Проверки ниже, где сказано сохранять backup/исходный ZIP после успеха, описывают
прежние версии. При неуспехе резервные копии по-прежнему сохраняются.

## SETs/FANs: общий runtime и владельцы моделей,0.1.402

Четыре основные страницы передают typed resource intent и отображают данные;
очереди, worker/results, подтверждение/сохранение и restoration принадлежат

## Нативный Copilot через общий firmware adapter,0.1.249

После повторной неудачи0.1.248 при активном F23 hook разобран OEM. Общий adapter
предпочитает распознанный OemWMIfun keyboard ABI, затем source-verified EC ABI
(728.2+APP-present741.0) через действующий транспорт Wujie/L16/HYDROC.
OEM EXE не запускается; произвольные EC-карты не копируются. Нативный setter
проверяет readback, sync — только fresh mismatch под общей operation admission.
FAN/APU/таблицы/лимиты не переписываются. Software fallback сохраняется для
shortcuts/неподдержанных native интерфейсов; физическая клавиша требует прогона.

## Copilot и все11полей в файле KEYs,0.1.248

OSD/Copilot перенесены в keys-settings.ini Version3 с резервной копией старого
app INI. App-файл/шаблон больше не записывает эти флаги. Windows/Linux читают
их через отдельную схему KEYs, языковые/логовые настройки не перезаписывают их.
Windows hook перенесён с UI на отдельный message-loop поток, поддерживает F23
и обычный Win+C, с подтверждением состояния и переустановкой на On/resume.
Счётчики только подавленных Copilot событий заменяют угадывание физического
результата по configuration_saved; обычный ввод не записывается. Реальная
физическая проверка нового фильтра ещё нужна. См. KEYS-PERSISTENCE.md.

## KEYs/INFO для всех устройств,27.10.2026

Общие KEYs lifecycle и schema вынесены в core/KeysLifecycle; настройки собраны
в settings/keys-settings.ini с однократным импортом прежних явных полей.
Windows startup/resume работает без model/EC admission, Linux использует тот
же worker через logind. Fn Honor и microphone сохраняются после readback.
Системные кнопки доступны в Unknown/каталоге; аппаратные EC/HWMI маршруты

Bluetooth lifecycle сохраняет состояние Windows. KEYs не зависит от восстановления
FAN/APU; отдельных model KEYs replay workers больше нет. См. KEYS-PERSISTENCE.md.

## KEYs и Bluetooth,27.10.2026

Lifecycle restore больше не применяет старый Bluetooth из INI: сохраняет текущее
состояние Windows. Явные кнопки KEYs продолжают работать с readback и сохранением.
GM6 читает системные KEYs из того же модельного INI, куда пишет интерфейс.
Wujie не подтверждает неизвестное состояние устройства как успешное restore.
Linux OSD перечитывает общие preferences перед изменением одного поля, сохраняя
свежий выбор языка. Полная матрица и границы ревизии: docs/KEYS-PERSISTENCE.md.

## Закрытие модального окна без переактивации приложения,27.10.2026

Общий Windows modal loop теперь связывает диалог с контекстом своего owner.
closeModalDialog включает только owner, отключённый этим loop, ДО DestroyWindow.
Прежний обратный порядок мог активировать другое окно, а затем заново всё
главное окно при EnableWindow/SetActiveWindow после уничтожения диалога.
Одинаковый helper используется обновлениями, лицензией и modal information;
modeless operation без modal context не включает чужой owner.

Закрыть/X/Escape и отложенное закрытие после cancellation/ready используют
одну последовательность. Отмена updater-worker, join и результат установки
не изменены. Уже disabled owner не включается; уничтоженный owner пропускается.
Восстановление focus ограничено живым enabled descendant прежнего owner,
повторная SetActiveWindow при уже активном owner не посылается.
Audit ui.modal_close фиксирует owner_enabled_before_destroy.
Перерисовка всего дерева, WM_SETREDRAW замораживание, layout/scroll изменения
для маскировки дефекта не добавляются. Linux modal lifecycle не меняется.

## Inventory и две постоянные истории, версия0.1.199

bios-inventory.json теперь сохраняется в logs_<actual board> вместе с логами.
Старый root файл импортируется только при отсутствии нового; исходник остаётся.
GUI обеих ОС и CLI inventory сохраняют снимок по общему пути.
Постоянные rom_id и platform_id используют общий append-only JSONL writer:
дата/время UTC/local, версия/session, origin startup/automatic/user/observation,

До конструирования controllers/restore читаются7C3 и все16байт770–77F.

порядок/маски/ownership write/rollback. Старые schema1rom_id строки сохраняются.
Returned не выдаётся за подтверждённое применение, наблюдение — за внешнего
известного writer. Геометрия/скролл/модели и BIOS/VBIOS читалки прежние.

## Файловые тесты BIOS/VBIOS и reset-вектор GM6, версия0.1.197

Добавлена отдельная изолированная suite для AFU, FPT16, FPT19 и NVIDIA:
синтетические буферы, зафиксированные SHA наших WUJIE/GM6 файлов и прежняя

## Два вида NVIDIA dump, версия0.1.196

Одна INFO кнопка и mctl dump-vbios обеих ОС сохраняют обычный VBIOS и entire
основной EEPROM по два чтения. Ёмкость определяется по распознанному --check
descriptor (K * width *128байт), а не по файлу. Entire требует стабильные ID,
ёмкость<=16МиБ, точные размеры/SHA двух файлов и положительный raw compare.
Unknown/oversize/ошибки не включают full. Обычный VBIOS сохраняется отдельно;
при одном успехе выдаётся partial, CLI JSON содержит оба статуса, exit4.

Общий typed allowlist list/check/save/entire-save/compare используется обоими
native runner. Команд записи firmware/EC, отключения GPU или override нет.
Model policy/геометрия/скролл/пять кнопок INFO и runtime payload прежние.
Проверка каталога14NVIDIA/7семейств и parser выполнена offline без platform
библиотек; vendor/hardware/product не запускались. [Контракт](VBIOS-DUMP.md).

## VBIOS reader lifetime при SSH/отмене, версия0.1.195

Linux запускает NVFlash в отдельной сессии без управляющего TTY, чтобы
терминальный Ctrl+C/разрыв SSH не посылали сигнал самому reader. Child обеих
ОС удерживает межпроцессную lease до выхода даже при гибели frontend; pending
waiter также удерживает scheduling gate. Windows AFU/FPT по-прежнему наследуют
ровно3 стандартных handle, NVFlash — ещё capture semaphore. Команды/данные
чтения, runtime pins, UI/геометрия/скролл прежние. Реальный reader не запускался.

## VBIOS в INFO и mctl обеих ОС, версия0.1.194

Общий collector выбирает фактическую NVIDIA по PCI, выполняет два фиксированных
NVFlash save, сохраняет raw/ошибки/версии и проверяет SHA256/PCI ROM. Кнопка
только на фактической GPU, чужой preview не включает reader. GPU tabs зависят
от каталога dGPU/обнаружения, Unknown больше не включает пустые вкладки.
Геометрия карточек/шапки/скролла и порядок пяти действий0.1.193 сохранены.

Windows NvFlash группа offline RCDATA с SHA pins и signed SYS references;
Linux отдельный pinned ELF в tools/NvFlash и protected root-owned cache.
Обе GUI и mctl используют одно ядро; прежние AFU/FPT команды не меняются.
Сборка/portable обновляются общим Build-All. Ни vendor tools, ни GUI/CLI,
ни драйверы на железе помощником не запускались. Публичный релиз не выполнялся.
Контракт, пределы и точные версии: [VBIOS-DUMP.md](VBIOS-DUMP.md).

## Постоянная история ROM-ID,24.10.2026

Каждый обычный GUI-запуск Windows/Linux, включая запуск с активацией уже
работающего окна, дописывает UTF-8 JSON-lines в `logs_<фактическая плата>/rom_id`
(без расширения). Сначала `startup_begin`, затем `startup_read`: реальное RAM
значение0x770 либо явные unsupported/disabled/unavailable и причина. Helpers
обновления/диагностики не являются пользовательским запуском и историю не открывают.
Windows читает только на уже допущенных точных Uniwill-моделях, read-only backend,
после своих проверок платы/драйвера; до создания контроллеров и startup restore.
Honor/Unknown/остальные catalogue-only и Linux не получают придуманного EC пути.

История независима от AllLogs/BatteryLog. Файл никогда не ротируется, не
перезаписывается и не удаляется приложением; записи защищены OS file lock,
дописываются в конец и сбрасываются на диск. Смена трёх пар обычных журналов его
не затрагивает. Обновлятор также сохраняет любой целевой `rom_id`, даже если
такое имя ошибочно попадёт в manifest пакета. Настройки/ownership по этой истории
не восстанавливаются.
В каждой строке — UTC, местная дата/время с UTC-смещением, версия приложения,
сессия, реальная плата/профиль, источник, прежнее/запрошенное/прочитанное значения
(hex и decimal), результат/ошибка. Чтение при старте не доказывает, что значение
не менялось между запусками; состояние до добавления истории неизвестно.

Наш общий ROM-ID policy writer дописывает попытку ДО записи, затем результат
существующего контрольного чтения; откаты имеют отдельные события. Ошибка IO
без readback остаётся unconfirmed. Существующие стабильные чтения Wujie/native
battery дописывают только первое/изменившееся значение, без нового таймера и
аппаратного опроса. `observed_change` не приписывает изменение внешней программе.
История фиксирует наблюдаемые значения, а не все незамеченные переходы прошивки.
Сбой файлового журнала сообщается диагностикой и не отменяет аппаратный cleanup.

## Единая portable-папка settings,22.10.2026

По окончательному решению владельца все известные пользовательские настройки
всех моделей хранятся в `settings/` рядом с EXE: INI, CSV кривых, PL drafts,

каталог0.1.161, затем старые корневые файлы. При первом переходе в новую папку
эти файлы имеют приоритет над чистыми шаблонами. Marker settings/.portable-settings-v1

settings/, не переносят туда пользовательские логи или runtime. Обновлятор

ROM-ID ownership receipt — отдельный служебный документ с прежней SMBIOS UUID

Совместимость с валидными старыми portable receipts сохранена.

## GM6IR0C: восстановление выбранного конфига

По прямому поручению владельца выбранный конфиг GM6 сохраняется после успешных
команд/readback и восстанавливается на startup/resume/system_sleep_clock.
Native Office/Gaming/Turbo/Custom/Economy, отдельный Auto reset overrides,
последующий FAN overlay, обе кривые/каналы/linked и отдельный Custom draft
записывает общий Gm6Controller. Restore использует те же setters и DeviceOperation,
с WMI APP admission, epoch/owner/identity guards, readback и прежними rollback.
Custom/Economy с ненулевыми PL по-прежнему требуют AC: до подключения ожидают;
новая явная команда отменяет ожидание. Неуверенный результат записи не повторяется.
Cycle6 сохраняет отдельное намерение запуска и начинает работу только после
подтверждённого восстановления подсветки. Переключатели Windows-устройств используют
прежний WindowsDevices, radio permission готовится на GUI STA.

Первый переход не может восстановить выбор, который старая версия вообще не
записала. Такие режимы нужно один раз явно выбрать в новой сборке. Отсутствующий
файл не заменяется догадками по EC или логам. Перезагрузка Windows применяет
конфиг при запуске MagicControl; службу/задачу автозапуска эта правка не создаёт.
Штатный обновлятор сохраняет settings/. При ручном переносе новой версии
копируется settings/ либо используется передача запуска между активными копиями.

## Windows: передача запуска между локальными версиями,0.1.149

каталоги имеют защищённую ACL Administrators/SYSTEM, reparse points отвергаются.
Ресурс и файл сверяются по размеру/SHA256; файлы и каталоги закреплены handles
до завершения процесса, запись/подмена загруженных файлов запрещена. Это обычная
загрузка неизменённой DLL через LoadLibraryEx, не memory-mapping собственного PE.
Установка/запуск службы не выполняются при извлечении. INFO извлекает embedded
setup только после нажатия и сохраняет проверки подписи/хэша и штатный мастер.

Диагностика проверяет встроенные ресурсы без извлечения/аппаратных обращений,
записывает хэш и размер, расположение защищённого кэша. Notices/COPYING доступны
также в licenses/PawnIO. Упаковщик использует тот же stager; сам выпуск не создаётся
без отдельного запроса. Linux не содержит Windows зависимости и обновляет общую
версию обычным общим билдом. Правила подписи/драйверные guards не менялись.


## Рабочая portable-копия и релизные архивы

Правило пользователя от18.10.2026: каждая успешная Release-сборка обязательно
обновляет соответствующую папку `MagicControl/windows` или `MagicControl/linux`
внутри проекта. Stager вызывается явно, если выбранный build-target его не
запускает. После замены сверяются версия и SHA-256 бинарника; настройки и логи
сохраняются. Временный staging не заменяет обновление рабочей portable-копии.
При занятом EXE дождаться штатного выхода через трей и закончить копирование.

Правило пользователя от20.10.2026: после каждого успешного общего билда
обязательны обновление обеих рабочих portable, проверка версий/SHA-256 и
локальный Git-коммит с подробным описанием. Повторного разрешения на коммит
не запрашивать; законченные билды не копить незакоммиченными.
Заголовок: фактическая версия0.1.N и суть изменения. Тело: что/почему изменено,
модели/компоненты, UI/поведение, поставка portable Windows/Linux, реальные
проверки и ограничения. В финале работы указывать версию и хэш коммита.
Личные INI/CSV, логи/дампы и посторонние изменения не добавлять в этот коммит.
Исходники, ресурсы, документация и проверенные portable одного общего билда
фиксируются вместе, после готовности обеих ОС. Неполный/неудачный билд сначала
довести до завершения. Полный рабочий контракт закреплён в `AGENTS.md`.

`GitHub_Releases`, релизные ZIP/TAR.GZ, manifest/build-info и `SHA256SUMS.txt`
создаются/обновляются только по отдельному явному запросу пользователя.
Обычная сборка, исправление интерфейса и коммит такого запроса не подразумевают.
Команды упаковки ниже применять только после такого запроса; публикация также
требует явного поручения пользователя.

## Версия 0.1.N

Версия принадлежит общему билду продукта, а Windows и Linux — два его варианта.
Запуск: `Tools/Build-All.cmd` или `powershell -File Tools/Build-All.ps1`.
Обычный `Tools/build.cmd Release` также запускает общий билд. Ярлыки сборки
обеих ОС ведут на этот же запуск. Одна новая общая сборка — один новый номер.

`Build-All.ps1` под блокировкой выбирает0.1.N, записывает `build/product-version.txt`
и состояние `build/product-build.json`, последовательно собирает GUI и CLI обеих ОС,
обновляет рабочие portable и сверяет версии/SHA-256 (включая Windows VERSIONINFO).
Успех фиксируется только после обеих ОС. Native `cmake --build` лишь читает
выбранную версию через прежний файл `cmake/IncrementBuildVersion.cmake`; сам этот
скрипт больше не увеличивает счётчик. Без выбранной версии native build отклоняется.

Незавершённый билд при следующем запуске продолжается с прежним номером,
`-Resume` явно требует продолжения. Уже подтверждённая ОС пропускается только
при совпадении исходных входов, версий и хэшей build/portable. Если исправлены
исходники, номер незавершённого билда сохраняется, но обе ОС пересобираются.
`-NewVersion` явно начинает новый номер вместо продолжения. После завершённого
билда следующий обычный запуск создаёт новый номер. Пропуски после аварий допустимы.
Готовые публикации не перезаписывать этим механизмом. Тесты и GitHub-упаковка
в общий запуск не включены.

Общий счётчик Windows/Linux: `build/version-counter.txt`, с блокировкой файла.
Очистка `build/windows` или `build/linux` его не удаляет. Полный каталог `build`
со счётчиком нужно сохранять; при переносе исходников перенести счётчик вместе с ними.
Счётчик локальный, не отправляется в публичный репозиторий. Перед сборкой на новом
компьютере установить значение не ниже последнего выпущенного билда.

Для экспериментальных сборок разрешён отдельный staging-каталог, например
`build/honor-portable/{windows,linux}`. Упаковщик принимает
`--portable-root build/honor-portable`; он всё равно сверяет бинарник и версию
с успешной native-сборкой, а настройки берёт только из чистых шаблонов.
Это позволяет готовить архив без замены занятого рабочего EXE пользователя.

Сгенерированные `generated/MagicControl/Version.h` и `Version.h.version` принадлежат
конкретному build-каталогу. Версия встроена в подвал, окно обновлений и Windows
VERSIONINFO EXE. Windows и Linux одного общего билда имеют одинаковый N.
При успешном portable staging копируется `build-version.txt`.
В релизных именах архивов и package-manifest.json использовать фактическую версию
каждого бинарника; не брать неизменный PROJECT_VERSION=0.1.0 из configure-лога.

Официальный репозиторий: https://github.com/nikimagic/MagicControl.

- `MagicControl-<версия>-windows-x64-portable.zip`
- `MagicControl-<версия>-linux-x64-portable.tar.gz`
- `SHA256SUMS.txt` — SHA256, два пробела, точное имя архива; отдельная строка на архив.
- Внутри архива один каталог пакета и `package-manifest.json`: product=MagicControl,

## Инструкция упаковщику

Порядок обязателен для человека и автоматического помощника. Один вход упаковки —
`Tools/Package-Releases.py`; отдельные ZIP/TAR-скрипты для новых моделей не создавать.

### 1. Определить поручение и готовность сборки

- Запрос «в папку гитрелиз» означает подготовить файлы в `GitHub_Releases`.
  Публикация, push, создание тега и релиза требуют отдельного поручения.
- Использовать существующую успешную общую Release-сборку. Сверить
  `build/product-build.json`: `status=complete`, одинаковую версию0.1.N
  и `platforms.windows/linux.status=verified`.
- Сверить `build/product-version.txt`, обе `Version.h.version`, оба portable
  `build-version.txt`, Windows VERSIONINFO и SHA256 GUI с build/portable/session.
  При изменении исходников приложения после сборки сначала собрать обе ОС через
  `Tools/Build-All.ps1`; не менять номер, sidecar или статус билда вручную.
- Рабочие portable обновляются общими stager-скриптами. Занятый EXE заменять после
  штатного выхода через трей. Упаковка из готовой portable не требует её запуска.
- Записать исходный git revision и фактическое состояние исходников. Не ставить
  `includes_uncommitted_source_changes=true/false` константой. Чистый коммит
  приложения отмечать как точную ревизию, изменённые исходники — как base revision.
  Изменение release-архивов, логов или упаковочных метаданных само по себе не
  означает незакоммиченное изменение кода приложения.

### 2. Подготовить только разрешённый состав

- Настройки брать из чистых `packaging/app-settings.ini` и
  `packaging/fan-curves.csv`; не копировать рабочую папку целиком и не подставлять
  личные INI/CSV пользователя. Удалённые распакованные шаблоны `0.1.0` для
  упаковки не нужны.
  Явное исключение владельца19.10.2026: готовый **целый** fan-curves.csv из его
  Wujie включён в packaging/fan-curves.csv и используется всеми моделями/ОС.
  Упаковщик копирует его побайтово, без построения кривой из чисел. Старые архивы
  и отдельные model-specific headers не используются как источник этой кривой.
  Stager создаёт файл в новой portable; существующие настройки не заменяет.
  Тем же поручением владелец разрешил включить готовый app-settings.ini:
  общий packaging/app-settings.ini содержит языкRU, включённые OSD/embedded font/
  AllLogs и разрешённую Copilot. Оба файла копируются целиком для обеих ОС.
- Включать GUI, обязательные runtime, шрифты, инструкции и лицензии.
  Уточнение владельца25.10.2026: mctl остаётся только в его рабочей portable,
  в релиз не входит. Linux включает pinned tools/NvFlash/nvflash.
  Внутри архива должна быть одна папка `MagicControl`.
- Исключать mctl/mctl.exe, исходники MagicControl, PDB, SSH-ключи, build/research,
  отчёты BIOS, дампы, logs и logs_*/Backups, update/install staging, device-settings.ini
  и battery-enforcement-platform.txt. По уточнению владельца21.10.2026 проверенные
  OEM-пакеты из src/platform/windows/runtime/Uniwill входят только в ресурсы EXE.
  Общие cmake/UniwillRuntime.cmake и EmbeddedRuntime.cmake проверяют их исходные
  байты/хэши. Папки drivers и PawnIO рядом с EXE не включать; драйверы из рабочей
  portable целиком не копировать. Ресурсы EXE должны совпадать с исходниками.
- Windows: использовать обязательный список `cmake/PawnIORuntime.cmake`, а не
  собственный сокращённый список файлов. Нужны в том числе RyzenSMU.bin,
  IntelMSR.bin, SmbusI801.bin, LpcIO.bin, библиотеки и все соответствующие notices.
  Проверять закреплённые хэши модулей; отсутствие зависимости останавливает упаковку.
- Копировать разрешённые тексты лицензий и уведомлений по явному перечню
  `Tools/ReleasePackageAssets.py` из `packaging`; остальные уведомления зависимостей
  добавляются stager-скриптами. Отсутствие обязательного текста останавливает упаковку.
- ADL/ADLX/IGCL/NVML DLL из установленных GPU-драйверов не распространять.
  PawnIO setup входит только во встроенные ресурсы EXE; отдельный установщик
  рядом с программой не добавлять. Его запуск — явное действие пользователя INFO.
- Для Linux сохранить libgtk4-layer-shell, его лицензию, executable биты
  GUI/start.sh/NVFlash. Strip только копии нашего GUI, ABI в linux-abi.txt.
  Рабочие бинарники и pinned vendor ELF не strip-ить.

### 3. Запустить общий упаковщик

Из корня проекта, с Python3 и доступным WSL Ubuntu-26.04:

```powershell
python Tools/Package-Releases.py
```

Если `python` указывает на Windows Store alias, использовать полный путь к
доступному Python3. `--platform windows` или `--platform linux` применять только

Для отдельного staging допустим `--portable-root <каталог>` с подкаталогами обеих ОС.

Скрипт создаёт новые ZIP/TAR.GZ и распакованные пакеты, затем сверяет SHA256SUMS
с реально находящимися в `GitHub_Releases` архивами. Существующий каталог или архив

`--reconcile-checksums preview` и `--reconcile-checksums apply`: второй вариант
сохраняет прежний список и имена отсутствующих архивов в

сверку. После ошибки сначала
выяснить причину; частичный результат не объявлять готовым. Не удалять старые
выпуски автоматически и не повышать версию только ради обхода ошибки упаковки.

### 4. Проверить результат и передать пользователю

- Проверить версию/platform/product, source revision и source_binary_sha256
  в build-info.json; для Linux это хэш исходного GUI до strip.
- package-manifest.json описывает каждый поставляемый файл, кроме самого манифеста,
  с точным относительным path, размером bytes и SHA256. Он включает build-info.json.
  Сопоставить список и байты файлов архива с каталогом и манифестом.
- Проверить обязательные модули/лицензии и отсутствие запрещённых runtime-файлов.
  Проверки состава/целостности выполняются без запуска GUI, установки драйвера,
  аппаратных проб или запуска тестов приложения.
- Проверить SHA256 готовых ZIP/TAR.GZ по SHA256SUMS.txt; исторические строки об
  отсутствующих архивах сохраняются в аудите, а не как действующие файлы.
- Обновить верхний GitHub_Releases/README.txt: фактическая версия, дата, имена
  архивов и краткие изменения. Не обещать аппаратные возможности, которые
  подтверждены только наличием API или успешной компиляцией.
- В ответе дать версию и ссылки на подготовленные архивы/папку. Завершение
  подготовки означает наличие файлов и проверенную целостность пакетов.
  Фактическую публикацию на GitHub подтверждать только после отдельного поручения
  и успешного размещения assets, а не по наличию локальных архивов.

## Применение

Скачивание идёт в `magiccontrol-update/<уникальная-папка>` рядом с EXE.
Проверяются HTTPS, лимит размера, SHA256 архива (и GitHub asset digest, если указан),
безопасность путей/типов архива, версия и SHA256 всех файлов манифеста.
Ссылки, выход за каталог и архивные бомбы отклоняются до установки.

После «Обновить» и успешной подготовки запускается помощник, затем приложение
завершается обычным путём. Помощник не получает доступ к EC: его режим обрабатывается
до GUI, single-instance и аппаратной инициализации. Он ждёт выхода родителя до120 сек,
никогда не убивает работающий MagicControl, копирует резервную копию и атомарно
заменяет каждый файл. При ошибке выполняет откат и запускает прежний EXE.
После успеха запускает новую программу. Результат сохраняется в update-result.txt
и показывается при следующем открытии окна обновлений. Backup остаётся в папке стадии.

INI, CSV, журналы и battery-enforcement-platform.txt не заменяются. Каталоги логов
и резервных копий пользователя не очищаются. Протоколы FANs/APU/зарядки не меняются;
сохранение/восстановление аппаратного состояния остаётся задачей обычного запуска/выхода.

Windows использует системные curl.exe, PowerShell/.NET ZIP и BCrypt SHA256.
Linux: `/usr/bin/curl`, `/usr/bin/tar`, GLib SHA256; для обновлений нужны curl и tar.
Папка portable должна быть доступна для записи. Текущий EXE должен иметь штатное имя.

## Проверка реализации

Обе ОС собираются отдельно. Сборка не подтверждает фактическую замену и перезапуск
в рабочем окружении. Тесты, принудительное понижение версии и аппаратные пробы
без отдельного запроса пользователя не запускаются.

## Явная установка зависимости PawnIO (BIOS-вкладка)

Кнопка «Установить драйвер PawnIO» заменяет проверку BIOS. Общий bounded HTTPS
transport Download.cpp используется и обновлениями, и установщиком зависимости.
Windows скачивает https://github.com/namazso/PawnIO.Setup/releases/download/2.2.0/PawnIO_setup.exe
(официальная ссылка Download Now с https://pawnio.eu/).
Файл2.2.0:3410960байт, SHA256
1f519a22e47187f70a1379a48ca604981c4fcf694f4e65b734aaa74a9fba3032.
Метаданные GitHub asset и Valid Authenticode namazso проверены18.10.2026;
будущие версии требуют отдельного обновления этих закреплённых данных.
Установщик не добавляется в portable/архивы. Скачивается в уникальный каталог
.magiccontrol-install рядом с программой; подпись и хэш проверяются до запуска.
Непосредственно при запуске файл повторно проверяется под read lock, подпись —
через ранее заполненный Windows trust cache, без сетевого ожидания UI.
Мастер запускается интерактивно через ShellExecuteEx/runas, без silent-параметров.
Закрытие страницы/смена профиля отменяют незавершённую подготовку, не устанавливают
драйвер автоматически. На старте программы запросов/установки нет. Linux-кнопка
отключена, поскольку это драйвер Windows. Реальную установку без запроса не проверять.

Перед скачиванием кнопка проверяет регистрацию kernel-driver службы PawnIO
через SCM (CONNECT/QUERY_CONFIG). Остановленная служба считается установленной;
проверка не запускает драйвер и не открывает аппаратный интерфейс.
Если драйвер установлен, показывается тёмное окно «Драйвер PawnIO уже установлен»
с общей кнопкой ОК, без скачивания/переустановки. Ошибка чтения службы не считается
отсутствием драйвера. Перед запуском мастера SCM проверяется повторно.
Окно информации использует PageMechanics/ControlTheme, а модальный цикл общий
с существующими окнами обновлений/лицензии (runModalDialog).

При обычном запуске Windows GUI та же pawnIoDriverStatus проверяет регистрацию
и QueryServiceStatusEx: installed/running, state и оба exit code записываются
в startup log. Проверка выполняется до инициализации аппаратных контроллеров.
Если статус RUNNING — лишнего окна нет. Отсутствующий драйвер, незапущенная
служба и неизвестный статус различаются в сообщении общего тёмного диалога,
показываемом после создания главного окна. --no-ec сохраняет запись статуса
в лог, но не показывает предупреждение о неиспользуемом аппаратном доступе.
Установка/StartService при запуске не вызываются. Режим помощника обновления
по-прежнему обрабатывается до GUI и этой проверки.

Intel/NVIDIA monitoring: Windows runtime теперь также обязательно включает
IntelMSR.bin0.2.11 и IntelMSR-NOTICE.txt через общий PawnIORuntime.cmake.
CMake и Intel-читатель сверяют SHA256 официального неизменённого модуля.
THIRD-PARTY-NOTICES/SOURCE_OFFER дополнены, соответствующий исходник сохранён
в существующем локальном наборе PawnIO.Modules0.2.11. Упаковка без модуля не проходит.


После ревизии19.10.2026 общий билд сохраняет application_inputs (пути/SHA256
компилируемых источников, ресурсов и build-скрипта) по cmake/ApplicationInputs.json,
а также source_revision/source_dirty в product-build.json. Package-Releases.py
проверяет полный набор/хэши до создания папок и использует зафиксированное
происхождение. Старый успешный бинарник рядом с новым HEAD не является новой
сборкой. Изменения самого упаковщика/README не маскируют изменения кода приложения.
Если после сборки закоммичен именно её исходный снимок, упаковщик может указать
новый точный HEAD: полный набор application_inputs должен совпадать по SHA256,
каждый вход должен быть tracked, а исходники — чистыми относительно HEAD.
Иначе сохраняются исходные source_revision/source_dirty успешного билда.

## Локальные пакеты обновления,23.10.2026

По кнопке «Проверить» обновлятор рассматривает архивы непосредственно в
magiccontrol-update/ рядом с исполняемым файлом и опубликованные GitHub Releases.
Выбирается самая новая версия выше установленной; при равенстве источников
остаётся локальный пакет. Вложенные staging/backup-каталоги не сканируются.
Windows: MagicControl-<version>-windows-x64-portable.zip; Linux:
MagicControl-<version>-linux-x64-portable.tar.gz. Архивы другой ОС, ссылки,
пустые файлы и пакеты свыше128 МиБ не предлагаются. Достаточно самого архива,
соседний SHA256SUMS.txt для локального источника не обязателен.

Локальный пакет отмечен в окне обновления. При недоступности GitHub он остаётся
доступен с явной подписью о сбое сетевой проверки; без локального кандидата ошибка
GitHub сохраняется. Фоновой установки/сканирования при запуске нет: пользователь
нажимает «Проверить», затем «Обновить». Понижение/повтор текущей версии запрещены.

При проверке запоминается SHA256 выбранного локального архива; при установке он
копируется в новую уникальную staging-папку и сверяется с этим снимком, чтобы
замена ZIP между проверкой и установкой не прошла незаметно. Это проверка
неизменности выбранного пользователем файла, не удостоверение происхождения
от GitHub. Затем действуют прежние проверки распаковки, ОС/версии манифеста,
размеров и SHA256 каждого файла, штатный выход и rollback. Весь settings/
сохраняется. Исходный локальный архив не удаляется. Проверки GitHub SHA256 и
списка контрольных сумм для сетевого источника остались обязательными.
