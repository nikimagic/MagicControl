не являются общей шкалой совместимости или признаком исправления ошибки.

## Где ошибка

IOCTL `0x9C40A4CC` вызывает ACPI-метод `WIOP` через общий трёхаргументный
упаковщик по **RVA `0x1DC0`**. Аргументы пользователя — три DWORD little-endian.
Функция копирования по RVA `0x351C` имеет смысл
`copy(destination, input + offset, count)`.

| Место вызова copy, RVA | Смещение входного DWORD | Адрес назначения на стеке |
|---|---|---|
| `0x1F45` | `+0` — первый аргумент | `rsp + 0xB4` |
| `0x1F6A` | `+4` — второй аргумент | `rsp + 0xBC` |
| `0x1FB4` | `+8` — третий аргумент | **`rsp + 0xBC` снова** |

При подготовке третьего аргумента инструкция **RVA `0x1F6F`** повторно
использует `lea rax,[rsp+0xB8]`, хотя требуется следующий ACPI-элемент.
Второй DWORD затирается третьим; третий элемент не заполняется корректно.
Поэтому нельзя считать, что ACPI получит переданные пользователем
`Arg0 / Arg1 / Arg2`. Успех DeviceIoControl не подтверждает их правильность.
Фактическое значение незаполненного третьего элемента этим анализом не установлено.

Источники машинного кода: сохранённая дизассемблированная копия
`research/wujie-full-bios-20261024/driver-width-review/6e360ee4a0c4.asm`,
RVA `0x1DC0..0x2020` и `0x351C..0x3558`; привязки IOCTL/методов —
`COMPARISON.json` в той же папке. Это RVA, не смещения в сыром SYS.

## Почему прежняя I2EC-проба недостоверна

DSDT именно Wujie определяет:

- `WIOP(port,index,value)`: записать index в port, value — в port+1;
- `RIOP(port,index)`: записать index в port, прочитать port+1.

Для адреса EC `0x0454` прежняя проба передавала `WIOP(0x681,0x04,0x54)`.
Драйвер затирает второй аргумент значением `0x54`, то есть ожидаемая установка
старшей части адреса в `0x04` не обеспечивается. Последующий
`RIOP(0x682,0x54)` этого не исправляет: он задаёт только младшую часть адреса.
При обычном выполнении WIOP/RIOP таким образом мог бы получиться `0x5454`
вместо `0x0454`; конкретный ход ошибочно сформированного WIOP аппаратно не трассировался.

Следовательно, результат повторной пробы **`00` вместо `52` не доказывает**,
что I2EC выключен, отсутствует или что батарейная служебная память недоступна.
Первоначальные результаты сохранены, их нельзя выдавать за корректный тест
I2EC-адреса `0x0454`. Сам дефект ещё не доказывает, что после обхода I2EC заработает.

## Ограниченная альтернатива для исследовательской тестилки

Двухаргументный упаковщик **RVA `0x1A98`** в этом SYS копирует первый DWORD
в `rsp+0xAC` (`0x1C1D`), второй — в `rsp+0xB4` (`0x1C42`): назначения различаются.
Для чтения того же адреса без WIOP достаточно двух вызовов IOCTL `0x9C40A4C8`:

```text
RIOP(0x681, 0x04)  # записать high-селектор; чтение low-селектора игнорировать
RIOP(0x682, 0x54)  # записать low-селектор; прочитать data-порт 0x683
```

Это реальные записи в два **адресных I/O-селектора**, а не чистый read-only I/O.
Записи в data-порт `0x683`, EC RAM, регистры SMBus или устройство `0x50`
не требуются. Назначение портов всё равно должно подтвердиться на точном
устройстве: проверка аргументов драйвера не доказывает включённый I2EC decode.

Подготовлена `research/wujie-age-live-20261031/i2ec-two-argument-probe.ps1`:
exact SMBIOS, точный хэш SYS, mutex, обычная EC identity 82/72/26,
остановка на первом несовпадении, сохранение входов/ответов каждого IOCTL.
PowerShell и C# проверены без открытия устройства. На момент этой записи
до первого запуска аппаратная доступность оставалась неподтверждённой.

**Аппаратная проверка 31.10.2026, 11:30:09 МСК — успешна.** После повторного
разрешения владельца проба получила через два RIOP:

| Адрес XRAM | Получено | Проверка |
|---|---|---|
| `0x0454` | `0x52` | Совпало с обычным ECRR и ожидаемой identity |
| `0x0456` | `0x48` | Совпало с обычным ECRR и ожидаемой identity |
| `0x0740` | `0x1A` | Совпало с обычным ECRR и ожидаемой identity |
| `0x200D` | `0xCB` | Низшие биты `11`, I2EC read/write по карте ITE |
| `0x2012` | `0x21` | Бит разрешения выделенного I2EC-порта установлен |
| `0x2014 / 0x2015` | `0x06 / 0x80` | Базовый порт `0x0680` |

Итого 14 записей адресных селекторов, **0 записей data-порта, 0 записей EC RAM,
0 SMBus-команд**. Служебный возраст и данные батареи не менялись. Сохранён
`research/wujie-age-live-20261031/i2ec-two-argument-probe.json` с входами,
ответами и временем всех 17 IOCTL; сырой снимок хранится вне Git.
Это подтверждает путь I2EC на данной машине. Это ещё не чтение устройства
SMBus `0x50`, не проверка его восстановления и не успешный сброс возраста.

## Граница влияния

Дополнительная проверка31.10.2026,12:16 МСК: по отдельному прямому запросу
владельца RIOP использован для записи I2EC data-порта683 в тесте сброса
истории9C9/9CA. Двухаргументный вызов RIOP(683,value) записывает value в683,
затем читает684 (полученоFF, результат отброшен). Ноль обоих целевых байтов
и новая цель EC17800мВ подтверждены чтением. Таким образом, RIOP нельзя
считать исключительно читающим методом: он всегда сначала ПИШЕТ в Arg0.
Предыдущая гарантия «только адресные селекторы» относится к конкретной
identity-пробе с Arg0=681/682, а не ко всем возможным вызовам RIOP.
Это исследовательская запись с exact-board/hash/address guards; в production
такой путь не добавлен. Подробности и исходное9082 для отката — в
research/wujie-age-live-20261031/REPORT.md.

В production `src` нет вызовов WIOP/RIOP или этих двух IOCTL; они появились
в исследовательской тестилке. Штатные ECRR/ECRW и управление вентиляторами
этим выводом не объявляются неисправными. Дефект не является основанием
патчить подписанный SYS, менять комплект драйвера или ослаблять защиту Windows.
Любые другие методы, использующие тот же трёхаргументный helper, требуют
отдельной проверки до применения.
