# EcBitTest — пошаговый тест 0x741

## ROM-ID в RAM: отдельное поручение владельца22.10.2026

`EcBitTest.exe --battery-romid-ram --apply --output PATH`.
Только X5SP4NAG82/72/26, исходные ROM-ID FF и платформа7. Верхний предел
не меняется: нужен ненулевой одинаковый live/WMI ниже текущегоSOC и начальный
зарядный ток>=100мА.10с baseline →770FF→04 →10с наблюдения →возвратFF →10с
наблюдения. Свежий read-modify-write с маскойFB сохраняет общий bit2.
СнимкиRAM до/во время/после, durable recovery и общий transport те же.
Контролируются ROM771–77F, FAN config/tables, APU, upper/lower/health/priority;
при постороннем изменении опыт прерывается, чужие поля не перезаписываются.
CPU>=85C или батарея вне0..45C также прерывают опыт.

ПроцедураSet_ROMID и запись77E/77F не вызываются; WMI только читается.
Нельзя обещать отсутствие firmware-side persistence без исследования точного
образа. В production и других режимах770 по-прежнему недоступен на запись.
`--read-only` только фиксирует baseline; `--restore DIR` этого отдельного режима
разрешает восстановление только770/FB/FB/0 из его battery-restore.txt.
После опыта первоначальная настройка остаётся, успешная остановка сROM04
ещё не означает постоянное решение с исходным ROM-ID FF.

## Батарейный режим,22.10.2026

По прямому запросу владельца добавлен отдельный режим в ту же утилиту и транспорт:
`EcBitTest.exe --battery-flags --apply --output PATH`.
`--read-only` вместо`--apply` сохраняет только исходный снимок.
Нужны точнаяWujie82/72/26,ROMFF,подтверждённоеDSDTокно,закрытыеMagicControl/OEM,
сетьAC,готовностьбатареи,SOC11..98и температура0..45°C.

Устанавливает толькоlive upper10/platform7,безWMI/NVM/INI. Сначала10с baseline;
тест продолжается только при зарядном токе>=100мА. Затем по10с однократно:
742.2,7B9.7,7A6[5:4]=01,7A6[5:4]=10,742.2+7B9.7. Профили пропускаются,
если78E.3 не объявлен. Между шагами10с исходного состояния. Самосброс флага
фиксируется и НЕ преодолевается повторными записями. Первые два флага —
намеренный диагностический тест firmware-owned статусов,не production setter.

Один sample/с: ток434/435,напряжение438/439,состояние432/433,SOC,gate/flags.
Полные4КБ снимки EC RAM сохраняютсядо/после;это НЕ исполняемая прошивка.
Все записи masked RMW;исходные маски сохранены до записи. После каждогошага
восстановление,вконце liveupper/platformвозвращаютсяк исходным. ROM/алармы/
температурные защиты/FAN/APU/WMI не записываются. СменаAC/identity/context
или ошибка прерывает прогон и запускает восстановление.

`--battery-flags --restore RUN_DIR --output NEW_DIR` восстанавливает оставшиеся
owned маски из battery-restore.txt,не перезаписывая посторонние значения.
Ctrl+C обрабатывается с cleanup;жёсткое завершение процесса/питанияне гарантирует
cleanup. Нулевой ток на одном кадре не доказывает устойчивую остановку;
результат оценивается по серии,состояниюзаряда и удержанию записанной маски.

Запуск: `windows/StartEcBitTest.cmd` — шаги с Enter при закреплённом `.0=1`;
`windows/StartEcBitTestAuto.cmd` — такой же автоматический прогон по 40 секунд.
`windows/EcBitTest.exe` без аргументов сохраняет исходный интерактивный тест `.0`…`.7`.
Исполняемый файл запрашивает права администратора через свой manifest.
Закрыть MagicControl и OEM Control Center; EC должен быть в штатном режиме
без RAM/Manual. Утилита проверяет модель X5SP4NAG, идентификаторы 82/72/26
и объявленное DSDT окно EC 0xFED50000/4096. Службы она не останавливает.

## Ручной контекст и автоматический прогон

```powershell
.\windows\EcBitTest.exe --manual-context --auto --step-seconds 40
```

Сначала сохраняется штатный снимок, затем `.0` выставляется в 1. После
контрольного участка только с `.0=1` проверяются `.1`…`.7`, по одному.
Каждый проверяемый бит восстанавливается перед следующим, а `.0` остаётся 1.
В конце, при ошибке или остановке восстанавливается и исходное значение `.0`.
Если прошивка сбросила `.0`, прогон прекращается; бесконечной повторной записи нет.
RAM/Manual вентиляторов тест не включает. Другие адреса EC не записываются.

`--bit N` выбирает один бит; `--start-bit N` начинает последовательность с N.
Например, `--manual-context --bit 2` проверяет `.2` при `.0=1` с управлением Enter.
Проверять `.0` одновременно с его закреплением нельзя.
`--step-seconds 5…90` задаёт длительность наблюдения, по умолчанию в автопрогоне
40 секунд, в интерактивном режиме 90. Это **не уставка таймера EC**:
время в аппаратный регистр не записывается. Таймер может быть константой в коде
прошивки, а не доступным для записи числом в RAM.

Автопрогон не требует нажатий Enter и завершает процесс самостоятельно.
`q`, Esc или Ctrl+C останавливают его с восстановлением. Синтетические
нажатия клавиатуры не отправляются. Раз в секунду снимается вся RAM EC;
снимки последовательные, не атомарные. Датчики и счётчики могут меняться
непосредственно в процессе чтения. Журнал не доказывает физическое свечение
клавиш; для этого необходимо отдельное наблюдение.

## Один шаг

1. Утилита показывает номер бита `.0`…`.7`, маску и известное назначение.
2. Enter снимает исходные 4096 байт, инвертирует ровно этот бит и снимает
   состояние после записи. Другие биты берутся из свежего чтения.
3. Наблюдать внешнее поведение. В журнал раз в секунду записываются
   управляющие регистры, CPU EC temperature, питание и общий Windows idle.
   Дополнительные полные снимки снимаются примерно через 10 и 35 секунд.
4. Ввести наблюдение и Enter — сохранить заметку, восстановить исходное
   значение проверяемого бита и снять результат восстановления.
5. Следующий бит можно применить только после восстановления предыдущего.

`s` перед применением пропускает бит. `d` во время наблюдения делает
дополнительный снимок. `q`, Esc и Ctrl+C прекращают тест с попыткой
восстановления. Через 90 секунд шага без завершения происходит восстановление
и переход к ожиданию перед следующим битом; сам он не записывается.
Продолжение с нужного бита: `EcBitTest.exe --start-bit 1`.
Команды вводятся в это консольное окно, поэтому сами нажатия
могут будить клавиатуру; время Windows idle записывается для сопоставления.
Неудавшуюся запись утилита не повторяет постоянно: firmware-owned бит
может вернуться сам, и это часть результата.

## Файлы

Каждый запуск создаёт каталог `logs/ec-bit-test/<UTC>-<PID>`:

- `events.jsonl` — команды, фактическое чтение, наблюдения и восстановление;
- `baseline.bin` — исходный снимок 4096 байт;
- `manual-context-after.bin` — состояние после установки `.0=1`;
- `final-restored.bin` — состояние после возврата `.0`;
- `bit-N-before.bin`, `bit-N-after.bin`, `bit-N-restored.bin` — снимки шага;
- `series.bin` — последовательные кадры по 4096 байт без заголовков;
  индекс кадра, время начала/конца и фаза указаны в событиях `sample`;
- `*.bytes.csv` — все байты снимка;
- `*.diff.csv` — отличия от снимка перед данным шагом;
- `restore.txt` — сохраняется до записи и удаляется после подтверждённого
  восстановления. Каждая строка: адрес, номер бита, исходный 0/1.
  В контексте `.0=1` первая строка хранит исходный `.0`, вторая — активный
  проверяемый бит. Восстановление идёт в обратном порядке. Файл записывается
  с FlushFileBuffers и заменяется до аппаратной записи.

Это снимки RAM EC, не образ BIOS или EC flash. Различия включают живые
датчики и счётчики; одного изменения байта недостаточно для вывода о его
назначении. `all_bits_tested` в журнале сообщает, прошли ли все восемь битов.

При аварийном прекращении питания/процесса автоматическое восстановление
невозможно гарантировать. Если остался `restore.txt`, восстановление только
принадлежащих тесту битов запускается из повышенной консоли:

```powershell
.\windows\EcBitTest.exe --restore 'полный путь к каталогу запуска'
```

`--read-only` делает исходный снимок и заканчивает без аппаратных записей.
`EcBitTestSelfCheck.exe` проверяет маски и восстановление на всех комбинациях
байтов; к оборудованию не обращается.
