# SensorProbe — переносимый сборщик аппаратной телеметрии

Папку `util` можно целиком скопировать на другой компьютер. Во время запуска
MagicControl, исходный репозиторий, Python и .NET не нужны. Все пути к своим файлам
определяются относительно EXE. Используются уже установленные драйверы и системные
интерфейсы. Утилита не устанавливает драйверы и не применяет настройки оборудования.

Набор устройств не фиксирован: CPU Intel/AMD, GPU Intel/AMD/NVIDIA, несколько
видеокарт, модулей памяти, дисков и батарей обнаруживаются по доступным интерфейсам.
У каждого источника сохраняются собственные идентификаторы. Доступность конкретных
каналов зависит от оборудования, ОС, установленных драйверов и прав процесса.

## Запуск

- **Windows x64:** двойной щелчок по `windows/StartSensorProbe.cmd`;
  подтвердить штатный UAC. В корне также работает `run-windows.cmd`. Или запустить
  `windows\SensorProbe.exe` из консоли администратора.
- **Linux:** ярлык `linux/SensorProbe.desktop` в файловом менеджере или
  `sh linux/StartSensorProbe.sh`. В корне также работает `sh run-linux.sh`.
  Для защищённых DMI/EC-интерфейсов —
  `sudo sh run-linux.sh`. Без root сохраняются доступные пользователю данные и ошибки прав.

Ярлыки определяют расположение своей папки без путей к исходному репозиторию.
Запускатели в `windows/` и `linux/` оставляют терминал открытым после завершения.
Для `.desktop` нужен Bash и Linux-рабочий стол с поддержкой этого формата; файловый
менеджер может потребовать разрешить запуск ярлыка. Консольный `.sh` доступен отдельно.

По умолчанию — **10 кадров**. План начала кадров относительно старта серии:
**0, 5, …, 45 секунд**. Первый кадр начинается сразу после технической инвентаризации; последний —
примерно через 45 секунд. Если источник занял больше интервала, кадры не накладываются:
сохраняются фактическая задержка старта и превышение интервала. Инвентаризация выполняется один раз.

Каждый запуск атомарно создаёт **новую уникальную папку**:

```text
util/
  windows/SensorProbe.exe
  windows/PawnIO/                  DLL, подписанные модули, лицензия
  linux/SensorProbe
  logs/ИМЯ_КОМПЬЮТЕРА_ДАТА_ВРЕМЯ_МИЛЛИСЕКУНДЫZ/
    technical.json
    dump.jsonl
```

При совпадении имени к папке добавляется уникальный суффикс. Старые результаты
не перезаписываются. Время внутри файлов — **UTC**, дополнительно в журнале есть
монотонное время от начала сбора. Два файла связаны общим `run_id`.

В рабочем репозитории запускатели сохраняют новые результаты в
`out/test_util/logs/` от корня проекта. При копировании `util` отдельно
сохраняется автономный путь `util/logs/`. При прямом запуске EXE или
Linux-бинарника можно выбрать другое место аргументом `--output`.

Актуальные пути ниже. Первый столбец описывает материалы, а не пути для открытия:

| Материалы | Текущий путь от корня проекта |
|---|---|
| Исходники утилит | `tests/util/` |
| Журналы SensorProbe | `out/test_util/logs/` |
| Сохранённые прогоны discovery | `out/test_util/discovery/runs/` |
| Скрипты анализа и отслеживаемые отчёты | `research/test_util/analysis/` |
| Сохранённые входные данные анализа | `out/test_util/analysis/` |

Имена файлов и содержимое журналов не изменялись. Локальные пофайловые SHA-256
до и после переноса сохранены в
`research/workspace-audit-20261106/inventory/test-util-move-before.csv` и
`test-util-move-after.csv`; карта переноса analysis —
`test-util-analysis-before.csv` и `test-util-analysis-after.csv` в том же каталоге;
карта переименования утилиты — `test-util-rename-before.csv` и
`test-util-rename-after.csv`; финальная карта — `analysis-final-move-before.csv`
и `analysis-final-move-after.csv`.
Новые результаты скриптов анализа записываются в создаваемый при запуске
каталог `out/test_util/generated/`,
отдельно от сохранённых исходных данных. `out/` хранится локально; в Git могут
входить `research/INDEX.md` и исходники/описания в `research/test_util/`.

## Содержимое файлов

**technical.json** — ОС, ядро, тип виртуализации, права, CPU/CPUID, плата, BIOS/EC,
SMBIOS/DMI, PCI-устройства и драйверы, все обнаруженные модули памяти и накопители,
доступность источников, каталоги сенсорных интерфейсов и параметры запуска.
В Windows также сохраняются сырой SMBIOS и доступные ACPI для дальнейшего
изучения описания оборудования. Содержимое таблиц лицензирования Windows не собирается.

**dump.jsonl** — по одному JSON-объекту на строку. События:

- `run_start`, `run_end` — границы и результат запуска;
- `sample_start`, `sample_end` — номер кадра, расписание, фактическая задержка и длительность;
- `source_start`, `source_end`, `source_unavailable`, `source_partial` — источник, время и ошибки;
- `sensor` — источник, ID устройства/канала, название, `raw`, `value`, `unit`,
  `comment`, `status`, `error`;
- `ec_dump` — весь доступный диапазон, время начала/окончания, число прочитанных
  байтов, каждый адрес с собственным временем, сырым значением, ошибкой и известным назначением.

`null` означает отсутствие значения; действительный ноль сохраняется как `0`.
Первое измерение разностных счётчиков помечается `warmup`. Для неизвестных форматов
сохраняются сырые данные; единицы и назначение не угадываются. Номера устройств
разных API не считаются автоматически одинаковыми физическими устройствами.
Журнал сбрасывается на диск после каждого источника и кадра. У незавершённого
запуска может отсутствовать `run_end`; уже записанные строки остаются пригодными для анализа.

## Источники Windows

- **AMD ADL:** все 256 PMLog-слотов каждого обнаруженного присутствующего AMD-адаптера,
  включая флаги поддержки и неизвестные каналы.
- **AMD ADLX:** поддерживаемые температуры, hotspot, частоты GPU/VRAM, обороты,
  напряжение, мощность, загрузка, VRAM, температура памяти GPU и NPU при наличии расширения API.
  Сохраняются время провайдера, SystemRAM и SmartShift. Текущая привязка SDK
  допускает ADLX 1.5+ первой основной версии; другой ABI явно отмечается,
  а ADL и системные источники продолжают работу.
- **Intel IGCL:** все обнаруженные Intel GPU, датчики температур, домены частот,
  вентиляторы и пакет телеметрии установленного драйвера.
- **NVIDIA NVML:** все обнаруженные NVIDIA GPU, температуры, частоты, нагрузка,
  вентиляторы, мощность, память, состояние производительности и PCIe.
  Дополнительно запрашиваются все опубликованные в включённом NVML SDK field IDs
  с областью `scope_id=0`: тип, значение, статус, время провайдера и комментарий.
- **PawnIO:** подписанные `AMDFamily17`, `IntelMSR`, `SmbusPIIX4`, `SmbusI801`.
  Только разрешённые чтения MSR, известный AMD-регистр температуры и стандартные
  SPD-адреса `0x50–0x57`. Физические ядра перечисляются с учётом групп процессоров;
  привязка потока после чтения восстанавливается. Температуры DTS/RAPL Intel,
  энергия/частоты AMD и DDR5 SPD Hub сохраняются по доступности. Для DDR4, где SPD
  сообщает наличие TSOD, дополнительно читается стандартный JC42-датчик и его ID;
  такие значения помечены `candidate` до сопоставления с эталонным мониторингом.
  Модельные форматы
  без проверенного декодера остаются сырыми. Модули не устанавливают драйвер PawnIO.
- **Windows WMI:** обнаруженные классы счётчиков CPU/GPU/NPU/памяти/дисков/thermal/power,
  батарея, ACPI thermal zones, доступные SMART-провайдеры. При наличии работающего
  WMI-провайдера LibreHardwareMonitor/OpenHardwareMonitor сохраняются и его каналы.
- **Battery Class IOCTL:** все перечисленные батареи, напряжение, заряд/разряд,
  ёмкость, состояние, идентификаторы и температура, если батарейный драйвер её отдаёт.
- **Storage IOCTL:** все перечисленные физические диски и все возвращённые каналы
  температуры; для NVMe — полный SMART health log и отдельные температурные каналы.
- **AMD XRT:** полный доступный отчёт установленного `xrt-smi`, с ограничением времени дочернего процесса.
- **EC:** у проверенного X5SP4NAG — окно `0x000–0xFFF` через установленный UWACPIDriver.
  Прямое чтение MMRB применяется только после проверки текущего DSDT и идентичности
  платы; оно сохраняет `0xFF` без fallback. Известные показания дополнительно читаются через ECRR.
  Для диагностики USB-C/зарядки отдельными полями сохраняются `0x49F` (ADPT),
  `0x74C` (PDIN), `0x7CC` (статусы портов и приоритет питания), `0x7CD` и `0x7CE`.
  Событие `typec/negotiated_power` показывает результат OEM-логики
  `max(0x7CD, 0x7CE)`; единица измерения этого OEM-кандидата требует проверки внешним
  PD-анализатором или сравнением с подтверждённым профилем зарядного устройства.

На другом Windows-компьютере EC помечается недоступным, пока нет проверенного
интерфейса и карты его окна. Размер адреса в пакете драйвера не доказывает наличие
регистров по всем этим адресам. Утилита не сканирует произвольную физическую память.

## Источники Linux

- Все обнаруженные `hwmon`: AMD `k10temp`/`amdgpu`, Intel `coretemp`, NPU, SPD,
  NVMe, платы/Super I/O и другие драйверы, публикующие этот ABI.
- Thermal zones, все cpufreq policy, `/proc/stat` по каждому логическому CPU,
  память, нагрузка, I/O, PSI, power_supply, powercap/RAPL.
- DRM/accelerator sysfs, частоты/занятость/память; сырой пакет AMD `gpu_metrics`.
- NVIDIA NVML, если установлен; `smartctl` и нативный AMD `xrt-smi`, если доступны.
- Уже существующие EC debugfs-интерфейсы `ec_sys`: стандартное окно **256 байт**.
  Для расширенного OEM-окна нужен отдельный поддерживаемый интерфейс ядра.

В WSL собираются сведения **гостевой Linux-системы**. Физические датчики хоста
не подменяются Windows-данными; отсутствие hwmon/EC/NPU явно видно в журнале.
Бинарник Linux x86_64 требует glibc **2.38 или новее**; сборка получена на Ubuntu 26.04.
libstdc++/libgcc включены статически. Для старого дистрибутива можно собрать утилиту
из этой же переносимой папки на целевой системе.

## Параметры

```text
--count 10 --interval 5
--output КАТАЛОГ                  новая уникальная папка внутри этого каталога
--inventory-only                  только паспорт + журнал границ запуска
--no-ec --no-pawnio --no-amd --no-nvidia
--help
```

Чтения разных источников последовательны. EC-дамп также последовательный,
**не атомарный**: показания могут измениться между первым и последним адресом.
Низкоуровневое чтение датчика может включать выбор индексного регистра или обмен
по SMBus; пользовательские настройки вентиляторов, питания, напряжений и частот не меняются.
Чтение некоторых аппаратных флагов может подтверждать/сбрасывать их — сырые значения сохранены.

## Сборка

Из основного репозитория, существующие каталоги `build/windows` и `build/linux`:

```text
cmake --build build/windows --config Release --target sensor-probe --parallel -- /p:TrackFileAccess=false
cmake --build build/linux --target sensor-probe --parallel
```

Папка также собирается самостоятельно, без остального MagicControl:

```text
cmake -S . -B build/windows -A x64
cmake --build build/windows --config Release --parallel

cmake -S . -B build/linux -DCMAKE_BUILD_TYPE=Release
cmake --build build/linux --parallel
```

Сборка копирует исполняемый файл в `windows/` или `linux/`, PawnIO — в отдельную
подпапку Windows. Windows использует статический CRT. Внешние GPU DLL берутся
из установленных системных драйверов, не из случайных каталогов и не из сети.
Исходные подписанные модули для переносимой сборки находятся в `runtime/PawnIO`.

Официальные заголовки AMD ADL/ADLX и лицензии находятся в `vendor/AMD`.
ADLX закреплён на SDK 1.5.0.124; описания структур, интерфейсов и их идентификаторов
берутся из SDK. `vendor/AMD/sources.json` содержит исходные пути, commit и SHA-256
включённых файлов. Версия SDK сохраняется отдельно от версии установленного драйвера.
