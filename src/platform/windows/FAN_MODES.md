# Режимы вентиляторов MagicControl

## GM6: наблюдение ошибки I2EC, 06.11.2026

После команды Default пользователя 0.1.488 подтвердила режим EC, но
`native_default_fans=null`: фактические RPM/PWM показываются, таблицы нет.
Тот же I2EC admission используется для FAN-селекторов и истории батареи;
батарейный путь сообщил отказ identity/configuration. Точная FAN-причина в
том журнале скрыта catch-блоком, поэтому их связь остаётся вероятной, а не
доказанной. Первый отказ FAN теперь записывается один раз с текстом причины,
без вывода каждой попытки опроса; после восстановления фиксируется событие.
Возможность чтения или выбора кривой и аппаратные команды не расширены.

## GM6IR0C: отображение Default EC 1.12, 06.11.2026

На штатном GM6 экран ранее не получал `nativeDefaultFans`: контроллер отдавал
RPM/PWM и режим, но не публиковал firmware-кривые в общий ResourceState.
Теперь существующий GM6 FAN collector через `EcAccess` и тот же transaction
получает типизированный I2EC-снимок 08E6/08E7/08B8/08EB и подтверждает
Project25, EC1.12, SKU18, состояние FAN и выбор таблицы до/после чтения.
Допуск I2EC и его version/BIOS/driver guards принадлежат backend; чтение
использует запись двух адресных I/O-селекторов, без записи данных EC, mailbox
или команд вентиляторов.
Неверный/FF/меняющийся выбор остаётся unavailable, без чужого fallback.

Для подтверждённой группы5D48/5D60 ядро показывает извлечённые из образа
EC1.12 `5659c821...` Up/Duty таблицы Gaming/Office/Turbo; все12 указателей и
384 байта rising/duty сравнены с образом. Источник на графике помечен как
«Образ EC 1.12 · базовая кривая»: это восходящая база из сохранённого образа,
не доказательство побайтного совпадения live EC flash или фактического PWM.
CPU использует управляющий EC 043E/базовый запрос0461, GPU — 044F/0469;
фактический PWM75B/75C показывается отдельно. Запрос обозначен как базовый:
дополнительные thermal/forced ветви и гистерезис могут изменить конечный PWM.
При подтверждённом forced08EB запрос скрывается. Доступность 913E и итоговое
выполнение на ноутбуке владельца не проверены.

Снимок селектора кэшируется на3с с исходной меткой, при изменении mode/49F
обновляется сразу; подтверждённые Manual или Max немедленно снимают Default.
Текущий PWM по-прежнему поступает из обычного FAN-полла. Выбор штатного
графика на GM6 использует подтверждённый EC/ResourceState, а не сохранённый
локальный Manual-черновик; сами черновики и аппаратные команды не меняются.
Fake-EC тесты обеих ОС покрывают все профили/unknown, оба selector и три режима,
датчики, неизвестные значения и отсутствие записи. Реальный GM6 не тестировался.

## Lenovo KWCN: штатный флаг Max и общий дамп,02.11.2026

Реальный0.1.441 лог(4) подтверждает только RAM-readback при Max, за которым
обороты1700/1700 не изменились, запись оборвалась и владелец сообщил о выключении.
В0.1.442 общий writer был приостановлен; владелец отклонил этот общий запрет.
Теперь Maximum для GUI/CLI, restore и дампа идёт через один executeFanResource
и Controller::setMaximum: LENOVO_OTHER_METHOD.SetFeatureValue(04020000,1),
проверка FNST. Как Wujie751.6, это штатный флаг, не setFixed(100)/setCurves.
Max не записывает RAM-кривые, их флаги/индирекцию/ступени, lease или preset.
Даже переданные с восстановлением profiles не становятся Manual-командой.
Default/Manual снимают FNST через тот же проверенный setter. Возврат к уже
применённой неизменённой Manual-кривой снимает только флаг. Форматы настроек
и старые кривые сохраняются; старый kind2 RAM receipt сам Max не подтверждает.

Collector снова выполняет классический Default → EC → Max30с → Default →
возврат прежнего режима. Max — тот же ресурсный вход; более новая команда/сон
отменяет старый cleanup/replay. ReadOnly по-прежнему не меняет вентиляторы.
Raw EC/valid публикуются с flush/atomic replace до производных данных и Max.
Подтверждение FNST не равно измерению максимальных RPM. Штатные условия EC,
включая Custom gate, не обходятся переключением мощности. Новых аппаратных
запусков не было; физическая работа исправления пока не проверена.
Подробности: [LENOVO-KWCN](../../../docs/LENOVO-KWCN.md).

## Honor: read-only Balanced/Performance,01.11.2026

HLYL BIOS1.09 показывает документированные EC RPM-таблицы двух штатных режимов
через NativeDefaultFan -> Monitoring -> accepted ResourceState. Один прежний
typed FAN poll; GUI не читает EC. TUBO выбирает набор,8 OEM inputs/stages
определяют управляющий датчик по максимальной ступени; обе кривые используют
его температуру и собственные RPM. Запрос534/53A и факт03CC/03CE читаются
раздельно; PWM не пересчитывается в RPM. Все8 входов/пороги/источники доступны
в resource JSON, неопознанным каналам не назначаются GPU/VRM/DIMM имена.

Таблицы — read-only firmware reference, не Manual storage/receipt. Служебные
126/128 не превращаются в пользовательские точки. Контекст проверяется до/после,
ошибки не публикуют ноль. Подтверждённый Manual сразу снимает factory-view;
краткий пропуск использует общий display cache без обновления времени.
Fixed PWM Manual/Max, native Default, watchdog/rollback и старые устройства
сохраняют свои hardware paths. HPBSD исходники/кривые этой правкой не меняются.


## Общий FAN request/entry,01.11.2026

GUI/CLI/внешнее восстановление и прежний FAN шаг Custom используют
FanWriteRequest/executeFanResource. Старые публичные family writers/workers и
applyEc wrappers удалены; очередь модели содержит тот же request. Реальные
controllers сохраняют свои identity/ownership/tables/thermal guards/rollback.
Внутренний replay/diagnostic cleanup остаётся у их прежнего владельца.

CLI Wujie Manual теперь повторяет GUI autonomous EC Manual; Online — прежний
host mode. Online отправляет одну profiles operation, как GUI, без потери
первого канала двумя coalesced requests. Точки не пересчитываются. Fixed input
в CLI соответствует общим5–100%, а Min — native minimum из fresh state, не
локальный clamp36/38. Принятый target не объявляется фактическим PWM/RPM.

Caller DeviceOperation передаётся в existing enqueue до обработки, включая
Max/Manual; worker не делает tryBegin против собственного lease. Async GUI EC
получает pending, не ложный confirmed. CLI waits/checks находятся в общем entry.
Native OwnershipLost запрещает успех даже при auto-looking readback; ошибки
команды и последующего чтения сохраняются. При неудачном чтении не публикуется
выдуманное нулевое состояние. Curves/draft сохраняют исходные points/markers.

Явный Wujie Default по-прежнему сбрасывает APP consumers. Restore/Compound
Default — узкий возврат FAN без сброса Copilot/APP; recovery перед restore
остаётся в том же entry. CPU/PL/battery writers не добавлены. Linux без writer
возвращает честную недоступность. Карта/Memory EC tests/source comparisons:
research/fans-single-path-20261101. Новых аппаратных запусков нет.

## Штатные графики Wujie,30.10.2026

NativeDefaultFan core/protocol reader пассивно подтверждает82/72/26,
штатныеFAN-флаги, выбранныйheader62C0 и secondary62C4. Он не применяет
режимы/таблицы и не отправляет factory mailbox. Данные входят в существующий
FAN monitoring snapshot, затем в ResourceState; GUI читает только принятый
resource view. Источник кривой — точный декодированныйEC-образ, evidence
Documented, а текущие параметры выбора/запросы/PWM читаются изEC.

На графике базовая холодная/растущая кривая не обещает фактическийPWM при
задержках/дополнительных ограничениях. Контурный маркер — запрос, заполненный —
факт. Первичный запрос670 наблюдается непосредственно, вторичный выводится
через разобранную штатную transfer-функцию из общего запроса и первичногоPWM
и помечается≈расчёт. При forced-ветке запрос неизвестен, а не выдуман из факта.

У выбранногонабора отдельныеGPU-input records нулевые; ОБА графика используют
управляющуюCPU температуруEC:43E в Turbo+49F.1, иначе9178. Это не ADLX GPU T
и не обязательное совпадение с PawnIO. Контекст читается до/после; сравниваются
только относящиеся к FAN/selector биты общих регистров. Подтверждённые Manual,
Boost, чужаяidentity/table отключают Default-view немедленно. Пауза/ошибка или
разорванный снимок — отдельный исход Unavailable, не подтверждение смены режима.
Общий MonitoringDisplayCache держит последнее чтение максимум10с, не меняя его
время; retained и чтение старше2,5с обозначаются «последнее чтение» в легенде.
Это покрывает реальные интервалы2–3с без обнуления карточки. Windows собирает
generic telemetry до native EC, чтобы медленный provider не состарил новый кадр.

Manual-профили/редакторы/гистерезис/пределы/кодирование не менялись; Default
points отдельного readonlyтипа не проходят через Manual storage. График
переиспользован, включая координаты/DPI; дробные0,5% сохраняются. Карта не
включена для других моделей. Это наблюдение не меняет семантику кнопокDefault.

## Wujie: явный Default сбрасывает потребителей APP,30.10.2026

По прямому указанию владельца явная кнопка Default (GUI и CLI) выполняет
одну операцию core resetApplicationControl: возвращает FAN gates прошивке,
снимает Copilot через существующий setter, свежо проверяет отсутствие
потребителей и последним снимает741.0. Copilot Off сохраняется в отдельном
keys-settings.ini; очередь KeysLifecycle читает файл после общей admission.
Нулевой FAN-переход не пропускает этот сброс: повторный Default тоже работает.

Никаких записей CPU751.maskB0, PL783/784/785, RAM-кривых или Custom-слотов.
Соседние биты741/728/726/727/751/7C6 сохраняются. При отказе/ошибке сохранения
восстанавливаются только принадлежащие операции маски; после смены power epoch
записи прекращаются. Отдельного Copilot writer, hook или GUI-механизма нет.

Внутренний Default при recovery/диагностике сохраняет узкую четырёхбитную
семантику и не сбрасывает настройки KEYs. Выход приложения не меняет железо.
Startup/resume больше не захватывает APP без потребителя; retained RAM tables
по-прежнему активирует только их проверенный FAN owner. Карта ограничена
точным Wujie82/72/26; GM/Honor/HPBSD hardware paths не изменены.

Этот раздел заменяет ниже сохранение APP именно для ЯВНОЙ кнопки Default.
Max, Manual, кривые, защитные ступени и остальные аппаратные команды прежние.

## Wujie: команда при восстановлении, 29.10.2026

Принятая команда уже владеет DeviceOperation, в том числе переданной из
ConfigurationRestore. Worker присваивает её operation и revision ДО проверки
восстановления: повторный tryBegin против собственной блокировки запрещён.
Временная недоступность identity возвращает ту же команду в очередь вместе с
promise и operation; это не завершение и не разрешение записи. Проверка платы,
10-секундный допуск и PowerInterrupted сохраняются. По завершении Performance
снимается также wake-пауза опроса. Состав аппаратных команд, RAM-кривые,
температурный алгоритм и настройки не меняются.

Регрессия из лога0.1.387: fans.execute завершался за114мкс как pending,
promise разрушался, а applying оставался у потерянной revision9. Следующие
restore не проходили admission. Программная проверка воспроизводит queued
Performance на фоне clock-sleep, включая временную ошибку чтения identity,
завершение future, освобождение admission и последующий выбор профиля.

## Wujie: проверка владельца после сна, 28.10.2026

Совпадение FAN-флагов после сна не подтверждает содержимое активной RAM-таблицы.
Перед продолжением управления прежний контроллер читает и сравнивает таблицу;
чужое изменение завершает владение без записи поверх него. Кривые, их точки,
алгоритм управления и аппаратные команды не менялись. Сценарий проверен на
подставном EC в памяти, а не физическим переводом ноутбука в сон.

## Физический цикл GM6 на батарее,27.10.2026

Office→Gaming→Turbo→Office при отсутствии подтверждённого AC. Недоступный
Custom пропускается с причиной в общем OSD/журнале, а не повторяет отказ
Turbo→Custom при каждом нажатии. При AC прежний цикл включает Custom.
Сохранённые Custom PL/кривые и слоты не очищаются и не заменяются.
Явный Custom/Minimal и их AC guards не ослаблены, AMD цикл не меняется.
Переход Office использует прежний checked native apply, masks и rollback;
новых EC/прошивочных команд не добавлено. На железе помощник его не запускал.

## Единые поля Manual, 27.10.2026

Окончательное правило владельца: температура 20–100 °C, PWM / nominal RPM
5–100% для всех моделей Windows/Linux. Общие константы FanControlLimits.h
используются при создании полей, обновлении, колесе и подтверждении ввода.
Заводская телеметрия, служебные 255 и обязательные защитные ступени не
являются пользовательским вводом и сохраняют реальные значения.

HPBSD Manual показывает 7 CPU и 2 System обычные точки: все 18 полей
доступны. Последняя MAX-ступень показана отдельно текстом и на графике.
Пользовательские точки 20–100 °C сохраняются без ограничения 80/85 °C.
При кодировании EC отдельная MAX-ступень действует не позже исходных
94 °C CPU / 83 °C System; поздние точки проецируются в доступные обычные
ступени перед ней, а в полях остаются запрошенные значения. График показывает
фактическую проекцию EC. MAX-базы 51/40, верх 100, override и аппаратный
CPU >93 °C не изменяются. Все обычные строки перед переносом границ
временно получают MAX. Receipt v4 содержит 34 поля; v2/v3 восстанавливаются
по исходным 16/30 полям с заводскими добавленными границами. Старые draft v1
нормализуются только в памяти, при явном сохранении пишется v2.

Общий Wujie validator принимает логические точки до 100 °C, включая 85 °C
с пользовательским PWM. В autonomous EC table отдельно остаётся защитная
85 °C / 100%; точки выше неё хранятся в настройках, но не отменяют защиту.
Host-online thermal guard 85 °C не изменяется. Нижний диапазон старых файлов
3–19 °C сохраняется только для совместимого чтения, не для новых GUI-полей.

Min HPBSD по-прежнему выбирает заводские 36/38%; это пресет, не минимум
редактора. Ввод 5% допускается, но номинальная цель не гарантирует физические
обороты или PWM. Для Max наблюдалось около 5026/3529 RPM при номинальных
5100/4000; график RPM и фактический PWM показывают разные величины.

Этот раздел заменяет прежние ограничения редактирования ниже. Старые
рецепты, receipt и read-only заводские таблицы декодируются без подмены.

## HPBSD: родные кривые в прежнем редакторе,27.10.2026

Default показывает прочитанные8CPU/3System bands и slopes, Manual использует
прежние поля температуры/процента и прежний renderer графика. Температура —
верхняя граница ступени («До°C»), процент — nominal RPM (5100/4000max), неPWM.
Пользователь изменяет6normal CPU boundaries и1System boundary,7/2normal bases;
нижние границы выводятся из предыдущей верхней. Минимум2°C между ступенями,
монотонные ненулевые цели. CPU slopes вычисляются какfloor(100*delta/span),
max255; System selector является ступенчатым. График Default использует actual
slopes прошивки, не пользовательский черновик и не чужую16-точечную таблицу.

Неприкосновенны CPU final normal boundary93, critical(51,100,93,0), System
normal upper83 иcritical(40,100,83), overrides088A/B иSystem slopes. При переносе
температур planner сначала обнуляет normal slopes и поднимает normal bases до
MAX, затем меняет границы иставит целевые bases/slopes. Всеprefixes/recovery
журналируются; legacy16-field receiptv2 расширяется canonical boundaries,
новыйv3 хранит30fields итипcurve. Чужие политики не перезаписываются.

Кривая автономно исполняется EC; горячие94+/83+ stages остаютсяMAX даже при
аварии приложения. Прежний80/70host fallback сохраняется только дляfixed
targets/Min, не отменяет валидную автономную кривую до её верхних точек.
Fresh-temperature/ownership/telemetry guards иDefault recovery сохранены;
некорректный черновик не сбрасывает уже действующую owned curve. Допуск нового
apply приCPU<94C/System<83C. Файлsettings/hpbsd-fan-curves.txt хранит model-bound
draft, безавтоматического replay пристарте. Default возвращаетполнуюfactorypolicy.

PWM читается отдельно: C0CPRS1803/C1CPRS1804, period1841=127 поsame-profile
firmware feedback limits иlive clock signature.100*raw/127, invalidcount=>unknown;
PWM never written. Targets, physicalRPM иPWM не подменяют другдруга.
Матрица4598interruptedrestore prefixes иживой12секундный опыт: curved policy
подтверждена, targetcodes24/22, RPM~2460/~2140, PWM~35.4/~47.2%; Default
восстановилвсеисходныеполя. Нагрузочныеhot-stage переходы отдельно не проверялись.

Honor сохраняет прежнюю fixed-only ветку, остальные ноутбуки — прежние
редакторы/протоколы. НовыхUIкарточек, геометрии, шрифтов, скролла нет.
Прежнее описание fixed targets ниже сохраняется дляMin/Max иCLI fixed requests;
ограничение old Manual однимполем заменено родным editor adapter толькоHPBSD.

## HPBSD native targets,26.10.2026

Отдельный HpbsdFanController обслуживает GUI/mctl, без EcAccess/Uniwill.
Общий NativeFixedFans задаёт только typed интерфейс и формат состояния;
Hlyl — прежние методы/guards/watchdog, HPBSD — собственные ITE5571/RAM tables.
Default восстанавливает подтверждённые BIOS1.06 B1/B2 bases/slopes. Manual
задаёт проценты от nominal target5100/4000RPM, а не PWM. Min — минимальные
ненулевые заводские цели1800/1500RPM; Max —5100/4000nominal targets.
Целевые коды не гарантируют измеренные обороты: live Max~5074/~3535RPM.

Меняются только normal CPU bases/slopes и две normal system base rows.
CPU critical row94+C, system high-temperature row83+C, пороги, override088A/B,
PWM/SFR, платформа,ROM-ID,APU и battery не записываются. В частности,FF manual
handoff дляsystem НЕ используется: firmware thermal stages остаются активны.
Таблицы, overrides и immutable поля проверяются до команды и по readback.

Receipt hpbsd-fan-ownership.txt сохраняется до первой записи, включая точные
prefix apply/Default. Чужие/неизвестные таблицы не переписываются. После сбоя
Default доступен только для exact reachable состояния собственного receipt.
Getter никогда не выполняет recovery writes. В процессе один owner semaphore;
при обычном выходе возвращается наш Default. Watchdog возвращает Default при
потере контроля/телеметрии или CPU80C/system70C для Manual/Min; Max доступен
при нагреве. Аппаратные hot rows сохраняются даже при аварии процесса.
После firmware reset наблюдается Default, старые targets автоматически не
переигрываются. Черновик Manual сохраняется отдельно hpbsd-fan-targets.txt.

Дамп HPBSD всегда ReadOnly: полное RAM window0000–0FFF и observed tables,
без Default/Max-пробы и без изменения активного режима. Это не live EC flash.
Аппаратно проверены Max→Default→Manual65/65→Min→Default с исходными таблицами
в конце; температура/поведение после сна и thermal guard под нагрузкой отдельно
не испытывались. Старые Wujie/GM/Honor exit/restore policy не меняется.

## Неприкосновенные правила

1. Default и Max переключаются флагами. Таблицы перед этим НЕ очищать.
2. При выходе НЕ переключать Default, НЕ обнулять таблицы, НЕ снимать флаги
   вентиляторов и APP presence. Оставлять последнее применённое состояние EC.
3. Manual и Manual online записывают новую таблицу поверх прежней. Отдельного
   этапа очистки нулями или 255 нет. Служебные значения внутри новой таблицы
   являются частью её формата, а не отдельной очисткой.
4. SETs не управляет вентиляторами. Office/Balanced/Turbo меняют только профиль
   APU и его переопределения мощности. Сохранять Fan Boost в общем байте 0x751.
5. RPM/PWM — телеметрия, а не признак потери владения. Не восстанавливать режим
   по оборотам, отсутствующему чтению или несовпадению фактического PWM с кривой.
6. Переключение вкладок, сворачивание, разворачивание и трей не запускают
   восстановление. Запуск, подтверждённый сон и гибернация — запускают проверку.
7. Подсвечивать нажатую кнопку сразу. Подтверждения EC не ждать. При ошибке
   вернуть подсветку фактического режима и показать ошибку.

## Названия и смысл кнопок

Порядок на обеих карточках: Default, Manual, Max, отступ, Manual online.
Manual online отображается в две строки. Min online удалена из интерфейса;
старый пресет Min в формате конфигурации не равнозначен новой кнопке.

| Кнопка | Внутреннее имя | Кто рассчитывает PWM | Таблицы |
|---|---|---|---|
| Default | Native | Штатная прошивка EC | Существующее содержимое сохраняется и отключается флагами |
| Manual | EcManual / ecManual | Прошивка EC по записанной автономной таблице | Собственная общая ecManualCurve |
| Max | Maximum | Fan Boost прошивки | Не менять |
| Manual online | Curve / SavedProfiles | Работающее ядро MagicControl | Отдельные сохранённые Manual-кривые CPU/GPU |

CPU=GPU / CPU≠GPU доступна ТОЛЬКО в Manual online, включая случай, когда
online управляется один канал. В Default, Manual и Max кнопка отключена и
не подсвечивается. Запрет есть и в ядре.

Manual всегда использует общую CPU-кривую для обоих вентиляторов. Две кнопки
Manual на CPU/GPU запускают один общий автономный режим, а не два разных.
CPU=GPU не обещает равенства реальных PWM или RPM.

Уточнение ревизии20.10.2026: каждый явный Manual проверяет живые48байт
CPU-таблицы перед подтверждением no-op; Down[0] не сравнивается и не пишется.
При активации таблица свежо читается после открытия RAM-доступа. Кеш прошлого
Max/online или снимок до активации не заменяет это чтение. GPU-таблица по-прежнему
не читается и не пишется. Подтверждение таблицы/флагов означает readback,
а не измеренное физическое исполнение прошивкой.

Завершение старого фонового чтения не должно закрывать applying нового запроса
или заменять его статус. После фонового сбоя требование cleanup перепроверяется
перед исполнением уже принятой команды; неподтверждённый возврат требует Default.

## Регистры

Изменять только принадлежащие функции биты, сохраняя соседние.

| Адрес | Маска | Назначение |
|---|---|---|
| 0x751 | 0x40 | Fan Boost (Max) |
| 0x751 | 0xB0 | Поля профиля APU: Office 0xA0, Balanced 0x00, Turbo 0x10 |
| 0x726 | 0x80 | Custom fan control |
| 0x727 | 0x40 | Разрешение ручного управления вентиляторами |
| 0x7C5 | 0x80 | Раздельные аппаратные каналы; 0 — общий режим |
| 0x7C6 | 0x04 | RAM table commit: 0 — запись, 1 — активация |
| 0x741 | 0x01 | APP presence; сохраняется при выходе |
| 0x78E | 0x40 | Признак поддержки RAM-управления, только чтение |
| 0xF00–0xF2F | — | Таблица CPU, 48 байт |
| 0xF30–0xF5F | — | Таблица GPU, 48 байт |
| 0x783–0x785 | — | Переопределения мощности APU, к таблицам вентиляторов не относятся |

### Default

Сбросить только 0x7C6.2, 0x726.7, 0x727.6 и 0x751.6.
Не менять таблицы, APP presence и общий/раздельный бит.
При запуске/проверке Default не сравнивать CPU/GPU split с конфигом.
Пустая RAM-таблица не является условием штатного режима.
Внутренняя температурная таблица штатного алгоритма EC пока не установлена.

### Max

Установить только 0x751.6, сохранив остальные биты этого байта.
Не вызывать native()/Default перед Max. Не очищать и не перезаписывать таблицы,
не менять RAM commit, split, Custom и APP presence ради Max.
Перед Max не читать полный снимок RAM-таблиц и не ждать остановки OEM-службы.
Использовать короткое владение с проверкой режимных полей; полное владение
приобретать при последующем переходе к ручной записи кривой.
Физический разгон роторов может быть медленнее установки флага.

### Manual — автономный

Выключить Fan Boost, открыть RAM-запись, включить Custom/ручной gate и общий
режим: 0x7C5.7=0. Прочитать CPU-таблицу и сравнить с ecManualCurve.
При совпадении таблицу не писать. При отличиях перезаписать только отличающиеся
байты CPU с проверкой. GPU-таблицу не читать и не писать, включая снимок,
проверку запуска и восстановление; график GPU показывает общую логическую кривую.
Затем установить commit. Текущая реализация переключает APP presence 0→1 для активации.
Программный расчёт текущего PWM в этом режиме отключён.

Формат: Up[16], Down[16], Duty[16]. Duty = PWM * 2. Слот 0 Up/Duty = 0 —
служебный маркер; Down[0] не перезаписывать. Рабочие точки со слота 1,
DownT = UpT − 3. При необходимости добавляется 85 °C / 100%.
Неиспользованный хвост: 255/255/200. Логический максимум — 14 рабочих точек
с учётом защитной. Это не тот формат, которым online выдаёт текущий PWM.

У Manual собственная сохраняемая ecManualCurve; с обычным Manual online её
не объединять. В редакторе/конфиге минимум PWM 25%. Во время клавиатурного
набора разрешать пустое поле и промежуточное число; ограничивать при завершении
ввода/применении. Старые значения ниже 25% нормализуются при загрузке.

### Manual online — программный

Ядро вычисляет текущий PWM по мониторингу и пишет его через RAM-протокол.
С общим режимом редакторов температура для расчёта — max(CPU,GPU).
С раздельным — собственная температура каждого канала и его сохранённая кривая.
В Manual online аппаратный split ВСЕГДА установлен, даже при общей программной
кривой CPU=GPU. Читать/писать таблицы обоих управляемых каналов; общая программная
кривая выдаёт одинаковое задание каждому каналу. Аппаратную связь EC здесь
не включать: в опыте 16.10.2026 задание 20% при аппаратной связи давало CPU 30%
и GPU 25%. По просьбе пользователя аппаратная связь удалена из online.
Оптимизации одного чтения и проверки каждого изменённого байта сохраняются.
CPU-only + аппаратная связь остаются только у автономного Manual.

При переходе общий→раздельный явно выбрать и применить обе сохранённые
online-кривые. Не оставлять GPU в Default в редакторе, если ядро им управляет.
Для работы расчёта нужна работающая программа. После выхода расчёт останавливается,
но последнее содержимое таблиц и флагов намеренно сохраняется.

## Запуск, сон, выход, SETs

- Запуск Manual: проверить режимные флаги и CPU-таблицу, кроме Down[0]. При
  совпадении принять существующее состояние и владение без перезаписи.
- Запуск Max: принять уже установленный Fan Boost без записи таблиц.
- Запуск Default: при выключенных ручных флагах/Fan Boost не применять повторно.
- Запуск Manual online: запустить программный расчёт и применить конфигурацию.
- После подтверждённого сна/гибернации Manual повторно активировать и загрузить
  CPU-таблицу (писать только отличающиеся байты), даже если флаги сохранились: наблюдали неисполняющийся режим при
  сохранённых флагах. Простое скрытие окна не является сном.
- Перед завершением восстановления, в том числе при совпадающих FAN-флагах,
  повторно проверить EC version / system ID / Project ID. Неподтверждённый или
  нечитаемый идентификатор после десятисекундного ожидания снимает допуск
  записи до перезапуска; восстановление не пишет при неподтверждённой плате.
  Проверка на имитации не заменяет опыта реального сна.
- Периодическая проверка автономного режима: только флаги, без расчёта PWM;
  ошибка чтения — неизвестное состояние, а не доказательство сброса.
- В обычном Manual/online poll сверять только принадлежащие FANs маски
  `7C6.2/741.0/727.6/726.7/7C5.7/751.6`, до трёх чтений с паузой20мс.
  Соседние APU/RGB/camera биты не означают смену владельца. Каждый online
  проход проверяет эти маски под EC transaction до возможной Duty-записи,
  даже при неизменившемся target; периодического обхода RAM96байт нет.
- Устойчивая внешняя смена прекращает writes/confirmed и освобождает lease,
  без Default, rollback чужих таблиц и автоматического rearm из обычного poll.
  Неизвестное чтение приостанавливает запись и снимает confirmed до свежего
  результата. Intent для read-only повтора не является разрешением записи.
  Rearm после подтверждённого сна и явное действие пользователя — отдельные
  пути; error cleanup тоже не пишет при неподтверждённом владении.
- Выход: прекратить потоки и освободить ресурсы, без сброса EC. Освобождение
  OEM-службы GCUBridge может вернуть внешнего владельца, если служба установлена;
  это отдельный источник возможного перехвата, не доказательство автономности.
- Если возврат приостановленной OEM-службы завершается ошибкой, сохранить
  исходное намерение возврата и запретить новые FAN/Power-команды. Явный Default
  повторяет именно этот возврат; штатные флаги сами по себе не доказывают,
  что служба восстановилась. Тест использует подставную службу.
- Office/Balanced/Turbo: менять маску 0xB0 в 0x751, сохраняя 0x40 и прочие биты;
  убрать ненулевые переопределения 0x783–0x785. Не переприменять вентиляторы.

## Что подтверждено и что ещё гипотеза

Подтверждено аппаратным опытом: общий режим EC позволял управлять обоими
вентиляторами, раздельный автономный GPU не реагировал ожидаемым образом.
В логах часто CPU PWM 40% / GPU 35%, CPU 30% / GPU 25%, при меньшем задании
GPU останавливался. Пользователь предполагает CPU floor 25% и GPU = CPU−5
с остановкой ниже 25%. Не считать это универсальной спецификацией: точные
пороги/гистерезис и зависимость от режима требуют отдельного опыта.

0x43E — наблюдаемый CPU-температурный канал EC. Он близок к PawnIO Tctl/Tdie,
но тождество источнику автономной кривой не доказано. 0x44F постоянно возвращал
0: не называть его подтверждённым датчиком GPU. Удержание ступени при охлаждении
проверять с учётом DownT, а не объявлять скрытую температурную поправку.

НЕ утверждать, что автономность после полного выхода уже проверена. Ранее
такой вывод оказался преждевременным: программа сама сбрасывала EC при выходе.
Этот сброс теперь удалён, но нужен новый опыт с внешним читателем без записей:
записать различимую кривую, завершить процесс, дать/снять нагрузку, сопоставить
температуру, PWM/RPM, таблицы и флаги до/после. Оставшийся постоянный PWM сам
по себе не доказывает исполнение температурной кривой.

используется для последующей записи, если найдено несовпадение.

режимные флаги. При изменении PWM писать только отличающиеся Duty-байты, используя
проверенное ожидаемое состояние; произвольную потерю чтения не считать перехватом.
В логе ONLINE TABLE отдельно указаны read_compare_ms/changed_bytes/write_verify_ms.

## Оптимизации 1–3: кеш, повторный выбор и переключение online

- `expected` + `tableCacheValid[channel]` содержат последнюю проверенную таблицу.
  Валидность устанавливается после полного чтения/применения; каждый изменённый
  байт подтверждается readback до обновления ожидаемого значения.
- При переключении общей/раздельной Manual online обе таблицы уже известны.
  Использовать кеш, пересчитать задания и писать только отличия, не читать
  таблицы заново. Аппаратный split в обоих вариантах остаётся установленным.
- При такой online-переконфигурации не переключать commit, APP presence,
  Custom или gate. Полный протокол активации нужен при входе из другого режима
  либо при недействительном кеше/обнаруженном несовпадении флагов.
- Повторный выбор применённого режима при неизменившейся кривой и совпадающих
  флагах — no-op. Не переписывать таблицы и не переактивировать EC.
- Кеш недействителен после сна/перехода питания, освобождения владения,
  обнаруженного несовпадения флагов и ошибки. При новом владении начать без кеша.
  Внешняя запись таблиц без изменения флагов сама по себе не обнаруживается;
  не заявлять универсальное обнаружение стороннего вмешательства.
- Логи: `ONLINE reconfigure`, `ONLINE TABLE ... cached=true`,
  `CONFIG FAN confirmed: unchanged selection`. Эти строки позволяют проверить
  отсутствие лишних действий новым аппаратным прогоном.
- Пункт 4 (однократное/пакетное чтение через драйвер) пока не исследован.

## Недоступное управление APU в Default FANs (17.10.2026)

По наблюдению пользователя прошивка в Default FANs не принимает ручное
управление APU. Интерфейс отражает эту фактическую недоступность, чтобы не
предлагать неработающие действия: пресеты мощности APU, Manual и его редакторы
недоступны в подтверждённом Default. Переключатель платформы Limiter EC/Turbo EC
ОСТАЁТСЯ ДОСТУПЕН, включая трей: это отдельная политика EC, не ручные ватт-лимиты.
Подсвечен только Balanced как индикатор Default; это НЕ запускает запись его
45/40/40 в EC и не меняет сохранённый ApuMode. SMU продолжает опрашиваться.
При выходе из Default управление снова доступно; сохранённые лимиты не переприменяются
ради подсветки. Запрет есть в трее и обработчиках, включая отложенное применение.
Default определять по подтверждённому FanControlStatus, не по RPM/PWM или ошибке.
Батарейные 100/95/85% и подсветка клавиатуры остаются независимыми.

## Подтверждение Default при запуске/гибернации (19.10.2026)

Если флаги EC уже совпали с сохранённым Default, ConfigurationRestore оставляет
их без записи. Ревизия FanController считает команды и в этом случае может
оставаться0: это не признак неизвестного состояния. Отдельное observedDefault
получает результат общего readNativeFanFlags: commit/custom/override/boost
должны быть сняты; смешанный набор флагов не считается Default.
Idle-поток контроллера читает только флаги раз в1с (ошибка — повтор через5с),
без RAM-таблиц, захвата OEM-владения, переключения режима или записей APU.
SETs/трей используют это подтверждение: Balanced — индикатор Default,
ручные ваттные контролы недоступны. После suspend/resume подтверждение
сбрасывается до нового успешного чтения; неизвестное не подменяется Default.
Не менять сохранённый ApuMode или лимиты ради восстановления подсветки.

## Проба максимальных RPM из дампа (19.10.2026)

Это явное действие владельца, отдельное от переключения вкладок/мониторинга.
X5 MaximumProbe исполняется тем же worker, не отдельным EC-писателем поверх
Manual online. Меняется только751.6; снимок остальных режимных флагов, кривые,
текущий intent/lease и APU сохраняются. После30с наблюдения возвращается
исходный751.6 с проверкой остальных флагов. При смене сна/питания/владельца
безопасный возврат может быть не подтверждён: report/UI явно сообщают это,
NVML в этом случае не запускается. Не считать success записи доказательством
достигнутых RPM; в fans-ec-max.json записаны все показания и observed_peak_rpm.
Generic измеритель и cleanup общие с NVML, структура samples общая.
Новые аппаратные пробы на реальном ноутбуке в ходе разработки не запускались.


Ревизия19.10.2026: ACPI-транзакции используют Global\MagicControl.EcTransactions.v2
с правами wait/release и общей для сеансов Windows областью. GUI и подтверждённые
CLI-записи используют один Global SingleInstance writer lease; диагностический WMI
helper обрабатывается до него и не создаёт аппаратных контроллеров. Honor cleanup
до снятия manual bit сравнивает текущие targets с собственными, под одной I2EC
сессией. Явная кнопка Default имеет отдельный explicitRequest-контракт.


По запросу владельца Max при диагностическом дампе удерживается полные30с;
раннее плато RPM больше не сокращает пробу. Общий измеритель обслуживает EC/NVML,
сохраняет весь ряд/пики, после30с возвращает исходное состояние. Отмена немедленно
завершает ожидание и выполняет cleanup. Отсутствующий/заблокированный API не
обходится ради этой длительности; неподключённые пробы остаются пропущенными.

`commandApplied`, `responseObserved` и `settled` — разные поля результата:
возврат из begin подтверждает команду, измеренный рост RPM относительно baseline
подтверждает наблюдённую реакцию, плато описывает стабильность. Уже работающий
Max может дать settled без новой наблюдённой реакции. Ни один из этих флагов
не заменяет `restored` и не устанавливает паспортный максимум вентилятора.

Honor HLYL BIOS1.09 имеет отдельный fixed PWM100/100 adapter к тому же измерителю,
а не RAM-таблицы/Boost751. Он требует actual Default и CPU<80°C, сохраняет watchdog,
собирает HWMI fan0/fan1 и actual PWM. Cleanup различает Applied/AlreadyAuto/
OwnershipLost; последняя ветка не пишет чужие targets и не сообщает успех Auto.
Запуск/выход Honor не наследует X5 политику оставленных native RAM-таблиц:
watchdog и выход освобождают только собственный явный fixed manual.
